# フィーバーモード対応の試作（T14）

更新：2026-10-05。ユーザー指示でT14へ進んだ。入力停止問題はユーザーが解決済みと申告した。T9〜T13の残る実機照合・30試合受入れを完了と推定せず、T14と並行して残す。

## 実装した範囲

- 全26キャラのフィーバー倍率1〜17リンクを `scoring.json` に追加。通常倍率とは別の表を参照する。未収録リンクは拒否し、通常倍率で代用しない。
- `fever_battle/mode.py`：相殺によるゲージ、準備時間／残り時間、通常盤面と予告の保管、フィーバー側予告を先に消費する相殺、通常復帰時の予告合算、タネ成功／失敗／全消し、時間切れを扱うイベント審判。
- `seed_search.cpp`・`seed_solver.py`：観測盤面と現在手＋NEXT2で探索。CPU時間・展開数・探索幅を制限し、打切り時にも最初の合法手を返す。最初の消去でタネが交換されるため、消去後を同じ盤面の建築として探索しない。保管通常盤面のおじゃまは相殺に使えるがフィーバー盤面には落とさない。
- `mode_engine.py`：別入口のprotocol 3。通常時は既存の構築／予告探索、フィーバー時はタネソルバーを使う。大量の確定予告等がある場合はゲージを満たせる即時消去も比較する。入力前の照合は試合・ツモ・周期・モード世代・タネIDと両席の状態を使い、自然な時計減少は許容するが締切不足は拒否する。
- `mode_tactics.py`：フィーバー側予告や残り時間の少なさがあれば短手数発火を優先。余裕がある場合は見える範囲で伸ばし／全消しを比較する。相手の通常盤面で現在ツモによる発火が見えない場合や保管予告がある場合も短手数を優先する。相手の本線が存在しないと断定する判断ではない。

通常用のprotocol 2と単独エンジンは引き続き別入口。新しいバイナリは `bin/t14/fever_battle.exe` へ配置し、実行中の既存バイナリを上書きしていない。

## 出典と採用仕様

ユーザー指定の[なもこ氏の考察サイト](http://namob.net/puyof/)をHTTPで取得し、そこからリンクされている本人の解説を参照した。Webツールではサイト本体がタイムアウトしたが、通常HTTP取得は成功した。入口HTMLのSHA256は `e7b293b3e052cd371e837f3692ff3b60e266b7ae3381e5dfd8e95a12a0ccff3f`。

- [基本仕様](https://puyo-camp.jp/posts/86313)：ゲージ上限7、準備時間15秒・上限30秒、相殺時の増加、時間報酬、二種類の予告とタネ更新の根拠。秒からフレームへの変換は60fpsの試作設定。タネ失敗は基準との差1／2／3以上で、据置き／1減／2減として区別する。全消し突入の失敗判定には加算前の基準を使う。
- [倍率の測定表](https://puyo-camp.jp/posts/67754)：全26キャラの通常／フィーバー倍率を転記。ローカルSteamの一致確認へ昇格しない。
- [初回突入後の選択](https://puyo-camp.jp/posts/136789)と[合戦の判断](https://puyo-camp.jp/posts/135498)：伸ばしと即発火、全消しの価値、相手の連鎖終了付近の攻撃などの戦術根拠。現実装のしきい値・相手の1手予測による代用は実装上の仮説で、記事がAIの最適方針を証明したとは扱わない。
- [フィーバー待ち](https://puyo-camp.jp/posts/76553)：通常本線を維持し、相殺での突入を一律の優先方針にしないための参考。

数値・出典・確認状態は `data/fever/mode_rules.json` と `scoring.json` に保存する。タネの生成分布や時計停止フレーム、突入／終了アニメーションの長さはWeb説明から推測しない。

## 時計とイベント

時計は `clock_running` が明示的に真の区間だけゲームフレーム差で減る。`clock` イベントで観測した残りフレームと停止／再開を設定できる。`enter`・`seed`・`exit` は観測境界を明示したイベント。ゲージが満ちると `entry_pending` を返し、連鎖を終えてから `enter` を受け付ける。時間切れでも開始済みの連鎖は最後まで処理し、残り時間0から報酬で時計を復活させない。

タネは明示した盤面の `seed` イベントで供給する。実機未採取のタネを乱数で生成しない。タネIDは交換ごとに増やし、通常／フィーバー切替ではモード世代を増やす。周期位置は切替でリセットせず、観測した通算位置を使う。

おじゃま端数のカーソルもモード切替で勝手にリセットせず、既存のユーザー指定どおり実際に落ちた個数だけ進める。モード間の実機照合は未完了。再生状態には採用ルールのハッシュを含め、別のルール値で再生した結果を同一と扱わない。

ソルバーの時刻予測には通常盤面で校正した幾何時計を参考として用いた。**フィーバー中の時計・演出は未校正**なので `mode_timing_status=normal_geometry_reference_fever_unverified` を返す。時計が連鎖中も減るかは `clock_policy.count_chain_frames` で明示する。発火が締切内なら、連鎖終了が時間切れ後でも発火候補として扱う。追加の未確定予告の到着時刻を発明せず、探索結果には未スケジュールと表示する。

## 起動と入力例

```powershell
./build.ps1 -Target fever_battle -Output bin/t14/fever_battle.exe
python test/test_fever_mode.py
Get-Content -Raw data/fever/examples/t14-seed-request.json |
  ConvertFrom-Json | ConvertTo-Json -Depth 30 -Compress |
  python -m fever_battle.mode_engine
```

1行JSONで1要求。`protocol_version: 3`、`rule: "fever_battle"` を必須とする。例は公開参照盤面に対する架空の観測で、実機観測ではない。

両席は通常版のフィールドに加え、`mode_generation`、`seed_id`、`prepared_frames`、`remaining_frames`、`clock_running`、`seed_base`、`seed_chain`、`stored_field`、`normal_confirmed/unconfirmed`、`fever_confirmed/unconfirmed` を渡す。`confirmed/unconfirmed` は操作中モードの予告と一致する必要がある。通常時の保管盤面はnull、フィーバー時は通常盤面を明示する。観測できない値は0で合成しない。

返答は `action: "place"` または `"wait"`。突入／タネ待ちや操作期限不足の `wait` を配置として入力してはいけない。入力直前は `authorize_mode_reply()` で照合する。`seed_options` で幅・展開数・CPU予算・安全フレーム・経路時間推定・`quick/extend` を指定できる。

## 公開タネによる検証

[平積み](https://puyo-camp.jp/posts/74224)、[挟み込み](https://puyo-camp.jp/posts/74107)、[階段](https://puyo-camp.jp/posts/74093)、[座布団](https://puyo-camp.jp/posts/74096)のシミュレータURLから50盤面を取り込んだ。色は一貫した正規名へ置換し、Steamの実測色・生成表とは扱わない。画像のみの階段4連鎖・座布団6連鎖は未収録として明記した。

`reference_seeds.py` は保存済みHTMLを入力に、各図の連鎖数ラベルとURLを対応させる。RLEの長さ、空の上端、浮いたセルを検査し、元HTMLのSHA256・出典・未収録項目を保存する。データは `data/fever/seeds/namoko-reference.json`。

```powershell
python -m fever_battle.bench_seed --output data/fever/baselines/2026-10-05-t14-reference.json
```

50盤面×5表記（2/L/J/4/0）の250条件で、各条件の有利な現在ツモを色列挙で選択した。248条件が基準以上を発火し、250条件すべて配置・得点・結果盤面の再生が一致した。階段15・座布団15のでかぷよは1手で基準へ達せず、失敗として残した。**この条件付きの幾何検証をランダムツモでの成功率や実戦成功率に換算しない。**
