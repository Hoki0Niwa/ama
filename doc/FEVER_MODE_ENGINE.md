## 1. 構成

| 部品 | 役割 |
| --- | --- |
| `fever_battle/mode_engine.py` | protocol 3 の入口。要求の検査、判断の振り分け、入力前の照合（`authorize_mode_reply`）、次の手の準備 |
| `bin/fever_battle/fever_battle.exe`（`fever_battle/*.cpp`） | 探索と遷移。1行1要求のJSON。対戦時に起動するnativeプロセスはこれ1つ |
| `fever/`（`search.cpp`・`fire.cpp`・`engine.cpp`・`stock.h`） | 構築探索。単独用の `bin/fever/fever.exe` と対戦用バイナリ（`op: "solo"`）が同じコードを使う |
| `fever_battle/transition.h` | 探索が共有する遷移の部品：おじゃま落下（位相既知／端数列の全組合せ）、リンクの得点、相手連鎖の進行 |
| `fever_battle/mode.py`・`model.py` | イベント審判（ゲージ・時計・盤面切替・予告の保管と合算）、得点表、入力検査 |
| `data/fever/battle_policy.json` | 判断の重みとしきい値。`scoring.json`（倍率）・`timing.json`（時間）・`mode_rules.json`（ゲージ・時計の規則） |

通常用の protocol 2（`fever_battle/engine.py`、ゲージ加算0の検証用）と単独エンジンは別入口のまま残る。

## 2. 要求と返答

1行JSONで1要求。`protocol_version: 3`、`rule: "fever_battle"` を必須とする。

両席は盤面・現在手＋NEXT2・周期位置・予告に加え、`mode`、`gauge`、`mode_generation`、`seed_id`、`prepared_frames`、`remaining_frames`、`clock_running`、`seed_base`、`seed_chain`、`stored_field`、`normal_confirmed/unconfirmed`、`fever_confirmed/unconfirmed` を渡す。`confirmed/unconfirmed` は操作中モードの予告と一致する必要がある。通常時の保管盤面はnull、フィーバー時は通常盤面を明示する。**観測できない値を0で合成しない。** `garbage_phase`・`moves_since_chain`、フィーバー途中の `prepared_frames` はnullを許し、その場合は `_status: "unknown"` を必須とする。

| `op` | 内容 |
| --- | --- |
| `think`（既定） | 現在のツモの判断 |
| `prepare`・`prepare_normal`・`prepare_observed` | 次のツモの判断を先に作る。1回の `think` が同じ状態を観測したときだけ再利用する |
| `recover_placement` | 入力が届かなかった後、到達可能な配置（`reachable_placements`）だけから選び直す |
| `score`・`predict_chain`・`referee` | 得点計算、相手連鎖の時刻予測、イベント審判 |

返答は `action: "place"` または `"wait"`。`wait`（突入／タネ待ち）を配置として入力してはいけない。入力直前に `authorize_mode_reply()` で、自分の盤面・ツモ・予告・モード・タネ・時計が判断時と一致することを照合する。相手側の変化では返答を捨てない。でかぷよでは指定色 `color` を付ける。

返答の `reason` と `decision_kind` は判断の種類を示す表示用の値である。`decision_dependencies` は、その判断が自分の状態だけに依るか、相手の観測にも依るかを示す。

## 3. 判断の流れ

1. 突入待ち・タネ待ち（`awaiting_seed`、通常でゲージ7）：`wait`。
2. 準備済みの判断があり、状態が一致する：それを返す（探索しない）。
3. フィーバー中：タネ探索（第5節）。
4. 通常盤面：第4節の順。

### 意図した制約

どの探索も次を守る。整理の対象ではない。

- 色は現在手＋NEXT2だけを使う。未来の色列や相手の内部状態を読まない。
- 端数のおじゃまが落ちる列は決まっている（1・4・3・6・2・5列目の順で、前回最後に落ちた列の次から。2026-10-08の5時間の対戦ログの端数の落下133回はすべてこの並びだった）。ブリッジが位置を渡したとき（`garbage_phase`、2026-10-08から通常盤面で渡す）は、その列に落ちた盤面をそのまま読む。位置が不明なときだけ、次の扱いになる。
- 端数列が未知のおじゃま落下は全組合せで評価し、実際に落ちた後に再観測する。仮の盤面を `next_field` として返さない。フィーバー中のタネ探索だけは、手順を量るために最悪の盤面で先を読む（2026-10-08、5.1。それ以前は読まなかった）。通常盤面の戦術探索は従来どおり読まない。
- タネ交換・全消し・突入の先は読まない（盤面が未知になる）。
- 未確定予告の到着時刻を補わない。観測した相手連鎖があるときだけ、その時系列を使う。
- おじゃまが13段を超えた分は消滅し、列あふれだけでは敗北としない（ツモについてのユーザー確認からの解釈。おじゃまでの実機照合はしていない）。

## 4. 通常盤面

| 順 | 条件 | 判断 |
| --- | --- | --- |
| 1 | 出現位置が塞がり通常の配置を列挙できない | 観測した現在位置の直下設置（`observed_current_pose_drop`／`no_rescue_fast_finish`） |
| 2 | 予告または観測した相手連鎖があり、相殺でゲージが増える設定で、ゲージが7未満 | 戦術探索（4.2） |
| 3 | 2で生き残る手がない | 敗北確定の証明と最短決着（4.3） |
| 4 | 相殺でゲージが増えない設定で、予告または相手連鎖がある | 端数列不明なら1手判断（`uncertainty.py`）、既知なら予告状態の探索（`op: "garbage_search"`） |
| 5 | それ以外 | 構築探索（4.1） |

### 4.1 構築探索

本線（最長の連鎖1本）を組む。**フィーバーは通常盤面の本線が最も大事である（2026-10-07ユーザー）ため、通常構築の目的は本線構築に固定している。**

- 深いビームと仮想ツモ。対戦の既定は幅50・深さ8。評価の重みは `config.json` の `fever`、最初の本線の発火方針（trigger・panic・patience）は `battle_policy.json` の `solo_options` と要求の上書き値。初回の本線発火後、または初回Fever突入後は固定目標を解除する（次段落）。
- 相殺ストック（`fever/stock.h`）を評価に加える重みセット `fever_aim` と、評価値で初手を選ぶ `aim` は実装として残るが、`normal_build.objective` が `mainline` の間は使われない。

通常盤面では相手の連鎖観測を理由に構築先読みを一律拒否しない。相手のリンク・予告・マージンは構築AIの入力ではないため、実盤面・現在ツモ・可視キューの一致する接頭辞・キャラ・形状周期・モード世代・タネ・試合・探索設定で構築結果を再利用する。先読みは可視2ツモ、出現時の最新戦術は現在の観測で再計算する。`normal_build_search_reused` と `normal_build_searched_visible` はこの部分再利用を示し、完成した判断全体の `search_reused` とは区別する。

相手連鎖の観測中、またはレート変化が近いときの準備要求には、**暫定の手**を返す（`prepared: true`、`speculative: true`、`plan.speculative: true`、理由 `speculative_plan_decided_again_on_spawn`）。ツモが出るまでに相手が何を届けるかは分からないので、いま分かっている状況のままなら置く場所を、出現前のキー入力の向け先として渡すものである。エンジンはこの判断を保存せず、出現時の `think` が観測した状況で判断し直す（fork元の `main` と同じく、判断そのものは出現時に行う）。操作側は、出現時の判断が暫定の手と同じ配置ならキーを引き継ぎ、違えば離して置き直す。暫定の手では高速落下を先に押さない。通常盤面・フィーバー中の両方で同じ。構築探索の結果は従来どおり再利用する（`normal_build_prepared`）。相手連鎖の終了が現在の設置＋ちぎり＋おじゃま判定以前に来る場合や、確定予告が盤面を変える場合は、次の盤面が分からないので準備自体を断り、実落下後の観測を待つ。

選択した現在手の操作承認では未確定予告だけの増減を無効化条件から外す。自分のフィーバー中の保留通常予告も現在の盤面を変えないため同様。確定予告は非消去手では厳密に照合し、消去によってその設置のおじゃま落下を止めることが確認された手では取消理由にしない。実盤面・ツモ・キュー・世代・操作状態・時計方針等の検査は維持する。拒否ログには変化した状態キーを追加し、過去ログの一律 `self state changed` だけから原因を断定しない。

可視範囲の異なる構築結果は同一の完全探索結果を保証しない。オフライン比較と実機の入力遅延は別に扱う。詳細と検証根拠は `WORK_LOG.md` の同日追記を参照。

2026-10-08・セカンド以降の発火：最初の本線には設定した目標連鎖数を使う。通常盤面で初回目標から1連鎖小さい以上（既定15なら14以上、下限4）の連鎖を実際に観測した後、または自分がFeverへ突入した後は解除する（10-09再訂正）。4〜5連鎖の全消しだけでは解除しない。`reset_moves_at_chain` の4は履歴のリセット基準であり、本線の完了基準には流用しない。ブリッジは各試合の `normal_chain_max`（実際に観測した通常連鎖の最大リンク数）を保持し、新しい試合で0へ戻す。Fever復帰後はモード世代でも判別できる。操作案・準備案を返しただけでは解除しない。

2026-10-09訂正：解除後も初回と同じく上部まで大連鎖を構築する。未充填では発火条件を `trigger=panic_chain=19` とし、積み切ったら両方1へ下げ、連鎖数を問わず可視ツモで発火する。構築探索の目標 `build_chain` は初回設定より1小さい値（既定14、下限4）として発火条件と分離する。19連鎖を構築目標にしたり、充填時に1連鎖を探索の停止目標にしたりしない。通常の構築候補は、非消去で積める配置が残る限り小消しを避ける。発火方針が選ぶ発火・全消し・防御は別に判断する。`panic_step=0`・`panic_count=0`・`patience=0`。充填の判定は、外側4列12段・中央2列は死亡段下の余白（既定1段）を残した容量に現在ツモを加えると達する場合、または実際にぷよ数が増える安全な非消去配置が無い場合。既定の2個組では66個以上が容量条件。段差・特殊形状で早く行き詰まる場合も後者で検出する。防御・全消し・倒せる攻撃は戦術探索の判断を維持する。

相手Feverへの潰しだけを理由に本線全体を使うことは許可しない（初回・セカンド共通）。部分攻撃とその準備は、下記の時機・本線を失う費用で比べる。ログの `normal_fire_policy` は `initial_target`／`fill_then_fire`、`normal_chain_max` は観測済みリンク数を示す。Feverタネの通常の伸ばし・発火規則は維持する。前日の `completed_mainline` と小さい完成本線の即発火は、この指定で置き換えた。

### 4.2 戦術探索（`op: "tactics"`）

可視3ツモまでを1つの探索で読み、積む・最小相殺・本線発火・受けるを同じ値で比べる。

- 各設置で、設置とちぎりの時間、消去、リンクごとの得点と相殺（相殺したリンクごとにゲージ＋1）、相手連鎖イベントの進行、消さない場合の確定予告の落下（1回最大30個）を進める。
- 「落下が迫る」のは、その設置で消さなければ確定予告が落ちる場合と、残る予告（確定＋未確定、最大30個）が落ちたら敗北する盤面の場合。
- 探索は設置数の上限（`max_nodes`、既定3000）と100msの時計のガードで打ち切る。3手目の段では、各ツモの形の最大配置数を使って必要ノードを見積もり、全初手を評価できる幅まで枝を絞る。完了した最も深い段だけを使う。時間切れでは浅い段へ戻るので、常に3手を保証するものではない。
- 構築探索の手を「ヒント」として値に加える。可視3ツモより先を知っているのは構築探索だけだからである。構築探索が自分で予告を消し切る発火を選んだ場合は、それを早い発火・本線の消費として減点しない。
- 回復判断（`recover_placement`）も、到達可能な配置に限って同じ探索を使う。

値の構成（`battle_policy.json` の `normal_tactics.weights`）：

| 項 | 重み | 内容 |
| --- | --- | --- |
| `entry` | 6000 | ゲージ7に到達 |
| `gauge` | 1000 | 増えたゲージ1つごと。落下が迫っていないのに消した分は、突入しない限り数えない |
| `stock` | 40 | 葉の相殺ストックの重み付きリンク（`fever/stock.h`） |
| `color` | 60 | 1個で何かが消える色の数 |
| `drop` | 150 | 受けたおじゃま1個ごと |
| `consume` | 12 | 消した色ぷよ1個ごと |
| `mainline` | 1120 | 盤面で最長の連鎖から失ったリンク1つごと（突入時を除く） |
| `uncountered` | 2500 | `mainline_min` 連鎖以上の本線を使ったのに予告が残る場合、失ったリンク1つごと |
| `mainline_min` | 4 | 上の項で本線とみなす最短の連鎖数 |
| `early` | 1500 | 落下が迫っていないのに消した設置1回ごと（突入時を除く） |
| `height` | 300 | 中央2列が8段を超えた段数ごと |
| `exposed` | 700 | 残る予告が落ちると敗北する盤面。1個で発火できる色が少ないほど重い |
| `pending` | 0 | 探索の終わりに残る予告1個ごと（最大60個） |
| `builder` | 250 | 構築探索の手（消さない手、または予告を残さず消す手）と同じ初手 |
| `step` | 400 | 設置1回ごと。同じ結果なら早い突入を選ぶ |
| `arrival_pieces` | 2 | 未確定予告がいつ確定するか分からないときに、それまでに置けるとみなすツモ数（下の「本線を打てなくなる見込み」で使う） |

| `fever_reach` | 100 | フィーバーで巻き返せる見込みがある残り予告の目安（個）。2026-10-08ユーザー「相殺して100個くらいまで軽減できればフィーバーで逆転できるチャンスが生まれる」 |
| `growth_cells` | 6 | 待っている間に置くぷよ何個で本線が1連鎖伸びるとみなすか |

**本線の扱い（2026-10-08改訂）。** 本線（`mainline_min` 連鎖以上）は、打った結果に何が残るかで量る。形（縦3や高さ）の指定はしない。

- **残る量**：自分に届く分（確定＋未確定＋観測した相手連鎖がこれから出す分）に、相手がまだ持っている分（下）から自分が送った分を引いたものを足す。
- **丸ごと打った場合**（最長連鎖−1以上）：失ったリンク × `uncountered` × 残る量の割合を引く。割合は残る量 ÷（2 × `fever_reach`）で、上限1。残り100個で半分、200個以上で全部。突入時にも失ったリンク × `mainline` を引く（本線のぷよは突入のための資源でもあるため。2026-10-08変更、それ以前は突入時だけ引かなかった）。
- **小さく消して本線を崩した場合**：従来どおり、予告が残れば失ったリンク × `uncountered` を引く。
- **本線を持ったまま予告を迎える葉**：「後で打つ計画」と「連鎖としては諦める」の良いほうを足す。
  - 後で打つ計画 ＝ 打てる見込み ×（打って得るゲージと突入 ＋ 伸びた連鎖 × `mainline` − 連鎖 × `mainline` − 伸びた後の連鎖 × `uncountered` × 残る量の割合）− 打てない見込み × 連鎖 × `mainline`。
  - 諦める ＝ − 連鎖 × `mainline`。7連鎖で1000個のように、伸ばしても届かない本線はこちらになり、打たずに小さな相殺でフィーバーを繰り返す側の手が選ばれる。
- **落下までのツモ数**：確定済みなら次の1ツモ。観測した相手連鎖があれば終了までに置けるツモ数＋1。どちらも無ければ `arrival_pieces`。落下で盤面が負けず本線も埋まらない場合は、打てない見込みを0とし、少なくとも6ツモ伸ばせるものとする。
- **ツモごとの見込みとぷよ量**：見えているツモは色と形をそのまま使う。その先は、キャラの周期から形だけが分かる。発火色が k 色・必要な個数が n 個のとき、2個組は n=1 で 1−((4−k)/4)²、n=2 で k/16。3個組は n=1 で同じ、縦（L）は n=2 で k/4。4個組（2色×2個）は n≤2 で 1−(4−k)(3−k)/12。でかぷよは色を選べるので n≤2 なら必ず打てる。伸びる量は、置くぷよの数（2・3・4・4）÷ `growth_cells`。列に届くかは見ていない。
- **相手がまだ持っている分（`enemy_hold`）**：相手が通常なら、相手の盤面を引き金1つ（1列に3個まで）で打てる最長連鎖の得点。相手がフィーバー中なら、残りの時計で打てるタネ（現在の連鎖数から1つずつ上がる、1リンク4個の型、フィーバー倍率）の合計に、相手の保管盤面の最長連鎖を足す。相手の連鎖を観測中は、その連鎖は時系列で別に数えるので、通常なら0、フィーバーなら次のタネからを数える。返答の `tactics_forecast.enemy_hold` に出る。

**相手を倒せる見込み（2026-10-08）。** 相手が通常盤面で連鎖中でないとき、相手の守り（`enemy_defense`）を4つの数で渡す：相手の最長連鎖が相殺する量 `hold`、盤面を埋める量 `kill`（中央2列の高いほうが12段に届くまでの段数×6）、相手が引き金を1つずつ足して消せるリンク数 `links`、フィーバーに入るまでに要る相殺の回数 `need`（7−ゲージ）。倒せる見込みは次の積とする（`transition.h` の `Defense::kills`）。

- 着弾の割合：（相手に残る予告 − `hold`）÷ `kill` を0〜1に切り、**2乗する**（盤面の半分を埋める量は、倒すことの半分よりずっと小さい）。
- 逃げられない割合：1 −（`links` ＋ 送った連鎖が終わるまでに相手が置けるツモ数 ÷ 3）÷ `need`。相手はフィーバーに入れば落下が止まるので、ゲージが近いほど、連鎖が長く終わりが遅いほど逃げられる。「3ツモで1リンク」は推定で、実測していない。
- 葉の値は、見込み×`kill`（30000）＋（1−見込み）×それ以外の値。倒せるなら何を崩して送ったかは問わず、相手がフィーバー寸前なら見込みは0で、従来どおり連鎖の得点が決める。
- 相手がフィーバー中・連鎖中のときは `kill` を0として、この見込みを使わない（フィーバー盤面を倒す計算は入れていない）。

**予告が無いときの探索（`normal_tactics.quiet`、既定オン）。** 予告も相手連鎖も無く、自分に本線があり、相手が通常盤面なら、同じ探索を走らせる。消したぷよ × `mainline` ÷ `growth_cells` を引き（本線の伸びを失う分）、`early` は引かない。選んだ手が構築探索の手と違い、送るものがあり、倒せる見込みが0より大きいときだけその手を返す（本線の発火は `tactics_fire`、小さな連鎖は `tactics_harass`）。それ以外は従来どおり構築探索が置く。相手に倒せる見込みが無い局面では、構築は変わらない（計測で確認）。

**通常盤面の全消し（2026-10-08、重み `all_clear` 5000）。** 盤面を全部消す手順に加点する（フィーバールールでは4連鎖のタネが降り、フィーバー中なら時計が増える）。相手がまだ送れる量が `fever_reach` を超えるほど減らし、その2倍で0にする。予告が無いときの探索は、盤面のぷよが `all_clear_puyos`（24）個以下のときにも走り、`tactics_all_clear` を返す。

### 4.3 敗北確定と最短決着

`finish_probe` が可視3ツモと各落下の全端数列を列挙し、生存する消去または生存経路があれば不成立とする。救済がなければ、3回目のおじゃま落下を待たずに中央の列が埋まる配置を、移動・回転・落下・ちぎりの推定時間が最短のものから返す（`no_rescue_fast_finish`）。側列のあふれだけを敗北確定の根拠にしない。

## 5. フィーバー中（`op: "seed_search"`）

観測したタネの盤面と可視3ツモで探索する。最初の消去でタネが交換されるため、消した先は読まない。保管通常盤面の予告は相殺に使えるがフィーバー盤面には落とさない。

### 5.1 1つの値で比べる

すべての手順を「このフィーバーが終わるまでに見込める得点」で比べ、選んだ後に別の手順へ差し替えない。各手順の値は `expected_points`。

- **発火する手順**：その連鎖の全得点（期限内に発火すれば、終了が時計の後でも全リンクを数える）＋ 残る時計で次のタネ以降から見込める得点。
- **消さない手順**：盤面にある最長の発火口の連鎖を、必要な同色ぷよが来たら打つものとして数える。
  - 連鎖の得点と時間は、その盤面で実際に消して計算する（型の得点ではない）。
  - 必要なぷよが来る見込みは、残りの時計で置けるツモの数で決まる。1個なら1ツモごとに `piece_odds`（0.5）。残り1ツモなら0.5、長い時計ならほぼ1。同じ列に2・3個必要な場合は1ツモごとの見込みを個数で割る。
  - 「何ツモ目に来るか」ごとに、そこから打った場合の残りの時計で後続を数えて足し合わせる。来なければ何も打たず、タネと段を保つ。
  - 待てるツモの数は盤面の空きでも制限する（空き `wait_cells`＝3マスにつき1ツモ）。
- **手順の終わり**：手順は、発火した所か、見えているツモを置き終えた所で比べる。消さずに置いた後にまだ見えているツモがある場合、その置き方の値は続きの最善の値で、「待てば来る」という見積もりでは比べない（次のツモは見えているため）。
- **終了時の段**：次のフィーバーの最初のタネの得点の半分として数える。規定未達の発火は段を下げるので、得るものがなければ打たない。
- **保留予告**：相殺に使う得点と送る得点を同じ価値とし、別の項にしない。保管盤面が受けきれない分（`quiet_carry_limit` を超える分）だけ、1個を送る10個分として減点する。これにより、有害な持ち越しがあれば時計0でも小さな発火で相殺する。
- 後続のタネは「1色4個ずつのリンク」「成功の見込み0.85」「成功で1段上がる」という型で見積もる。次のタネの盤面や色の予測ではない。残りの時計が短いタネは、置けるツモの数に応じた見込み（上と同じ `piece_odds`）でしか数えない。着火が1フレームでも間に合えば満額、とはしない。
- 保留予告の減点（下）で相殺に数えるのは得点だけで、終了時の段の評価は数えない。
- **相手の連鎖が進行中のとき**：観測した相手の連鎖がこれから出す分は、どの手順にも全部を数える。相手の残りのリンクは自分の手に関係なく届くためである。2026-10-07の2回目の変更前は、手順が終わる時刻までに届く分だけを数えていたので、長い連鎖ほど多く受けたことになり、1連鎖のような短い発火が有利に見えていた。
- **大きなタネは伸ばさない**：タネの規定を超える連鎖を作るために消さずに置く設置は、盤面の空きが少ないほど失敗しやすいものとして数える（失敗の見込みは `crowded_cells`＝6 を空きマス数で割った値の3乗。空き12マスで約1/8、26マスで約1/80）。失敗すればタネを失う。規定どおりに打つために待つ設置には掛けない（そこで待たなければタネを捨てることになるため）。13連鎖以上のタネは、計測ではほぼ規定どおりに打つ。

返答の `seed_forecast.alternatives` に、正規発火（規定以上）・規定未満の発火・消さない手順それぞれの最善の初手と値が入る。なぜその手になったかを後から読むためのもので、手は変えない。消さない手順の `extension_potential` には、待っている連鎖の得点（`points`）・時間（`chain_frames`）・来る見込み（`odds`）が入る。

2026-10-07の変更前は、来る見込みを時計に関係なく0.75・0.45・0.25に固定し、待っている連鎖を型の得点で数え、見えているツモが残る置き方も「待てば来る」で比べていた。このため、規定の発火口が残っていても規定未満で打つ、正規発火が見えているのに規定−1連鎖を打つ、という手が出ていた（[SEARCH_PLAN.md](SEARCH_PLAN.md) 第12節）。

得点は全26キャラのフィーバー倍率表（`scoring.json`）で計算する。未収録リンクは拒否し、通常倍率で代用しない。

- **伸ばすのが基本、即発火は2つの場合だけ（2026-10-08ユーザー指示。同日の「倒せる見込み」をタネ探索から外した）**：タネは上の値（このフィーバーの終わりまでの得点と、次のフィーバーへ持ち越す段）で比べ、伸ばして段を上げる。次の場合だけ、規定以上の発火を他のどの手順よりも上に置き、早いほど上にする（`seed_forecast.press_reason`）。
  - `lands_on_their_normal_board`：相手が通常盤面で連鎖中でなく、このタネを規定どおりに打った分（1リンク4個の型）から、自分の予告（フィーバー側＋保留）と相手の盤面の最長連鎖が相殺する分を引いても残る（相手の盤面に降って、連鎖を組む時間を与えない）。ただし、相手の盤面にすでに盤面を埋める量（中央2列が12段に届くまでの段数×6）以上の予告があるときは外す（少し足しても意味が無いので伸ばす）。
  - `opponent_in_fever_holds_nuisance`：相手もフィーバー中で、相手に通常盤面用の保留予告がある。
  - 全消しになる規定以上の発火は、即発火の場合でもそれより上に置く。即発火でない場合の全消しは、従来どおり上の値（次のタネ＋2段、時計＋5秒）で量る。
  - 見えているツモで規定以上を打てないときは、どちらの場合でも従来どおりの値で比べる（待つ）。
- **相手のフィーバーへの妨害（2026-10-09）**：規定以上の発火で、相手のFever開始またはタネ連鎖終了から26フレーム以内に自分の連鎖が終了し、相手の残りリンクにも相殺されず予告が残る場合だけ、相手タネ1回分の得点の半分を加点する。時機不明・早すぎ・遅すぎ・規定未満は0。通常のタネ伸ばし・即発火条件は維持。
- **落下の先も読む（2026-10-08）**：消さずに置いておじゃまを受ける手順も、見えている次のツモへ読み進める。列が分からない落下は、最悪の盤面（生存、発火口の連鎖数、必要個数で選ぶ）で読み進める。この盤面は手順を量るためだけに使い、返す `path` はその落下で切る（`next_field` も返さない）。それ以前は落下で読みを止め、「待てば来る」見積もりで量っていたため、確定1個でも見えている規定発火を数えず、規定未満で打っていた。
- **1ツモの時間**：エンジンが自分の判断の間隔（同じモードで連続するツモ、間に自分の連鎖が無いもの）を測り、直近9回の中央値を `pace_frames` として両方の探索に渡す。探索はモデルの最速値（設置＋出現）と大きいほうを使って、期限までに置けるツモ数を数える。3回測るまでは渡さない。

### 5.2 以前の方針

`quick`・`extend` と、それらの規則（伸ばしの幾何評価の加点、伸ばしの手数枠、失敗発火の延期、可視復旧の証明、発火しない終了、消化優先）は2026-10-07に削除した。`seed_options.strategy` という指定も無い。削除前の記述は [FEVER_MARGIN_TIME.md](FEVER_MARGIN_TIME.md) とGitの履歴（`488dbaa` 以前の本書）にある。

### 5.3 時計と期限

- 時間延長の判定には連鎖終了の時刻を使う。連鎖加算は3連鎖から1リンク30F、全消し加算は連鎖終了の16F後。`time_reward_frames`・`remaining_after_rewards` に上限込みで返す。
- 時計0だけでは `wait` を返さない。現在の観測が操作可能なら最後のツモの配置を返す。
- フィーバー中の連鎖時間は通常盤面と別の実測値を使う（[FEVER_TIMING.md](FEVER_TIMING.md)）。採用した定数は `seed_forecast.timing_constants` に返す。
- 端数列が未知で確定予告が端数で落ちる手は、全組合せの最悪で評価して1手だけ返す。

## 6. 時計とイベント（審判）

時計は `clock_running` が明示的に真の区間だけゲームフレーム差で減る。`clock` イベントで観測した残りフレームと停止／再開を設定できる。`enter`・`seed`・`exit` は観測境界を明示したイベント。ゲージが満ちると `entry_pending` を返し、連鎖を終えてから `enter` を受け付ける。時間切れでも開始済みの連鎖は最後まで処理し、残り時間0から報酬で時計を復活させない。

タネは明示した盤面の `seed` イベントで供給する。実機未採取のタネを乱数で生成しない。タネIDは交換ごとに増やし、通常／フィーバー切替ではモード世代を増やす。周期位置は切替でリセットせず、観測した通算位置を使う。

おじゃま端数のカーソルもモード切替で勝手にリセットせず、既存のユーザー指定どおり実際に落ちた個数だけ進める。モード間の実機照合は未完了。再生状態には採用ルールのハッシュを含め、別のルール値で再生した結果を同一と扱わない。

### 2026-10-09 判断の再利用と操作待ちの再調査

通常盤面も相手の観測中の同じ攻撃が進むだけなら、準備した戦術判断を保持・再利用する。以前は相手攻撃中に計算した通常戦術を捨て、出現後に必ず計算し直していた。開始フレームで相手の同じ攻撃を照合し、新しい得点リンク・予告・盤面・モード・種・設定の変化、非消去時の着弾接近は再判断する。自身の遅れたゲージ計上（7未満）・履歴だけでは、同じぷよの操作を取り消さない。

ブリッジの `decision_budget_ms=100` はライブ判断の時間予算。通常構築は最大60ms、戦術は最大40ms、従来のおじゃま探索も残り予算内（最大60ms）、Feverタネは最大40msにする。構築とおじゃま探索は一層を完全に評価してから結果を採用し、未完了の深い層は捨てる。少なくとも現在の配置を全て調べるため、OSのスケジュール・初期化・浅い層・通信の時間を含む厳密な100ms上限ではない。予算のないオフライン要求は従来通り無制限。予告も残る攻撃リンクもなく終了イベントだけの相手連鎖は、おじゃま探索を起動しない。

生存配置なしのおじゃま探索結果は想定内の盤面として現在の合法配置を返す。探索エラーとしてブリッジのセッションを停止させない。その他の入力不整合・未知のエラーは隠さない。操作待ち時間は、ぷよが操作可能になってから数え、途中の先読み待ち・早期探索待ちを含める。実機の全場面で自由落下がなくなったことは未確認。

### 2026-10-09 通常本線の保護・セカンド設定・確定済み攻撃の再利用

- 通常相手への相殺ゲージ加点を0、Fever突入を減点にした。相手がFever中または突入確定の場合だけ従来の突入価値を使う。本線を丸ごと使って必要な返しをした結果の突入には追加減点しない。返し切れない本線を温存する評価は維持。死亡配置は評価より先に除外し、逃げ道のない緊急相殺は許す。

- 潰しは今回新しく送った分が残ることを、送らなかった場合の相手連鎖後の予告と比較する。既存予告だけでは加点しない。早すぎる攻撃を探索先の別の適時攻撃で正当化しない。Fever相手の撃破見積もりも適時の攻撃に限る。通常相手向けの汎用harass加点はFever相手に流用しない。相手種更新0〜26フレーム後に自分の連鎖を終える窓は維持（実機未校正）。潰し発火の先読みは実行時にも窓を検査し、時間経過で外れれば再判断する。ライブログに攻撃終了、相手種更新、許容幅を追加。

### 2026-10-09 本線・副砲の発火判断に双方のゲージを追加

本線／副砲の資源分類はmain由来の残ぷよ・redundancyを維持し、その使い方にゲージを加える。自分が相殺して増えるゲージは実際に予告が残っていたリンクだけを数える。フィーバー合戦では、十分に返せてその相殺で突入できる副砲を、本線を消費する十分な返しより先に比較する。通常相手への小消しで自分の突入を狙う優遇は戻さない。

相手の通常盤面・可視1手目の合法な発火候補について、キャラ別得点・端数・レートと送った予告量を使い、予告がなくなるまでの相殺リンク数を数える。現在ゲージと相殺ゲージ加算を合わせて突入可能性を調べる。3連鎖でも1リンク目で予告がなくなるならゲージは1回分。未知ツモでの追加構築や、相手がその手を実際に選ぶことは保証しない。盤面・キャラ・可視1手目ごとに最大64件キャッシュし、ゲージだけの変化では配置を再列挙しない。

追加のユーザー指示により、まだ双方が一度もフィーバーに入っていない通常戦（双方mode_generation=0）では、相手の突入を誘う副砲を評価する。残ぷよ・左右高さ・2連鎖以下・redundancy4以下の副砲条件を満たし、自分が本線を保持し（quiet最大得点>0）、保持火力が相手以上である場合に限る。副砲で相手が突入可能ならharass重み×min(新規送信数+6,30)を加点し、相手の突入後に本線を撃つ余地を残す。これは試作の評価値で、実戦で調整済みではない。既にどちらかがフィーバーを経験している通常戦では、相手を突入させるだけの副砲に通常潰しの加点をしない。必要な本線返しは相手の突入可能性だけで禁止しない。フィーバー相手への攻撃は引き続き送信先と切替時機を検査する。

候補返答にgauge_before、enters_fever、opponent_entry_possible、invites_opponent_feverを追加。相手の実際の選択を断定する値ではない。

- 同日追加指示：双方フィーバー未経験の通常戦では自分の突入を避ける。相手がゲージ満タンで突入準備中でも、まだ通常ならこの方針を維持し、ゲージ加点・突入加点をしない。突入候補には減点を適用し、十分な返しの同じ比較群では突入しない候補を先にする。相手が実際にFeverへ入った後は合戦用の突入判断へ切り替える。生存に必要な返し・唯一の合法手を禁止する絶対条件ではない。

- 初回戦で相手が突入準備中の場合にも少量予告の受入れ判断を維持し、許容できる予告のためだけに自分が相殺突入しない。単独構築が発火を選んだ場合も、受けられる予告での突入なら非消去候補と比較する。
