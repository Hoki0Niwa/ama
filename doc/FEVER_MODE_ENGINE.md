# フィーバー対戦エンジンの現行仕様

更新：2026-10-07。本書は protocol 3 のエンジン（`python -m fever_battle.mode_engine`）が**いまどう判断するか**を述べる。2026-10-05〜06の追記を重ねた旧版は、探索の再編（[SEARCH_PLAN.md](SEARCH_PLAN.md)）に合わせて本書へ書き直した。経緯と個々の変更の理由は [WORK_LOG.md](WORK_LOG.md) とGitの履歴にある。

確認の範囲：自動テスト（Fever系236件）、記録済み要求の再生、オフラインの計測まで。**通常盤面の戦術探索とフィーバー中の `value` を入れた後の実機での入力・勝敗は、本書の作成時点で確認していない。** 重みと定数はすべて試作値である。

## 1. 構成

| 部品 | 役割 |
| --- | --- |
| `fever_battle/mode_engine.py` | protocol 3 の入口。要求の検査、判断の振り分け、入力前の照合（`authorize_mode_reply`）、次の手の準備 |
| `bin/fever_battle/fever_battle.exe`（`fever_battle/*.cpp`） | 探索と遷移。1行1要求のJSON。対戦時に起動するnativeプロセスはこれ1つ |
| `fever/`（`search.cpp`・`fire.cpp`・`engine.cpp`・`stock.h`） | 構築探索。単独用の `bin/fever/fever.exe` と対戦用バイナリ（`op: "solo"`）が同じコードを使う |
| `fever_battle/transition.h` | 探索が共有する遷移の部品：おじゃま落下（位相既知／端数列の全組合せ）、リンクの得点、相手連鎖の進行 |
| `fever_battle/mode.py`・`model.py` | イベント審判（ゲージ・時計・盤面切替・予告の保管と合算）、得点表、入力検査 |
| `data/fever/battle_policy.json` | 判断の重みとしきい値。`scoring.json`（倍率）・`timing.json`（時間）・`mode_rules.json`（ゲージ・時計の規則） |

通常用の protocol 2（`fever_battle/engine.py`、ゲージ加算0の検証用）と単独エンジンは別入口のまま残る。

## 2. 要求と返答

1行JSONで1要求。`protocol_version: 3`、`rule: "fever_battle"` を必須とする。

両席は盤面・現在手＋NEXT2・周期位置・予告に加え、`mode`、`gauge`、`mode_generation`、`seed_id`、`prepared_frames`、`remaining_frames`、`clock_running`、`seed_base`、`seed_chain`、`stored_field`、`normal_confirmed/unconfirmed`、`fever_confirmed/unconfirmed` を渡す。`confirmed/unconfirmed` は操作中モードの予告と一致する必要がある。通常時の保管盤面はnull、フィーバー時は通常盤面を明示する。**観測できない値を0で合成しない。** `garbage_phase`・`moves_since_chain`、フィーバー途中の `prepared_frames` はnullを許し、その場合は `_status: "unknown"` を必須とする。

| `op` | 内容 |
| --- | --- |
| `think`（既定） | 現在のツモの判断 |
| `prepare`・`prepare_normal`・`prepare_observed` | 次のツモの判断を先に作る。1回の `think` が同じ状態を観測したときだけ再利用する |
| `recover_placement` | 入力が届かなかった後、到達可能な配置（`reachable_placements`）だけから選び直す |
| `score`・`predict_chain`・`referee` | 得点計算、相手連鎖の時刻予測、イベント審判 |

返答は `action: "place"` または `"wait"`。`wait`（突入／タネ待ち）を配置として入力してはいけない。入力直前に `authorize_mode_reply()` で、自分の盤面・ツモ・予告・モード・タネ・時計が判断時と一致することを照合する。相手側の変化では返答を捨てない。でかぷよでは指定色 `color` を付ける。

返答の `reason` と `decision_kind` は判断の種類を示す表示用の値である。`decision_dependencies` は、その判断が自分の状態だけに依るか、相手の観測にも依るかを示す。

## 3. 判断の流れ

1. 突入待ち・タネ待ち（`awaiting_seed`、通常でゲージ7）：`wait`。
2. 準備済みの判断があり、状態が一致する：それを返す（探索しない）。
3. フィーバー中：タネ探索（第5節）。
4. 通常盤面：第4節の順。

### 意図した制約

どの探索も次を守る。整理の対象ではない。

- 色は現在手＋NEXT2だけを使う。未来の色列や相手の内部状態を読まない。
- 端数列が未知のおじゃま落下は全組合せで評価し、仮の盤面の先を読まない。実際に落ちた後に再観測する。仮の盤面を `next_field` として返さない。
- タネ交換・全消し・突入の先は読まない（盤面が未知になる）。
- 未確定予告の到着時刻を補わない。観測した相手連鎖があるときだけ、その時系列を使う。
- おじゃまが13段を超えた分は消滅し、列あふれだけでは敗北としない（ツモについてのユーザー確認からの解釈。おじゃまでの実機照合はしていない）。

## 4. 通常盤面

| 順 | 条件 | 判断 |
| --- | --- | --- |
| 1 | 出現位置が塞がり通常の配置を列挙できない | 観測した現在位置の直下設置（`observed_current_pose_drop`／`no_rescue_fast_finish`） |
| 2 | 予告または観測した相手連鎖があり、相殺でゲージが増える設定で、ゲージが7未満 | 戦術探索（4.2） |
| 3 | 2で生き残る手がない | 敗北確定の証明と最短決着（4.3） |
| 4 | 相殺でゲージが増えない設定で、予告または相手連鎖がある | 端数列不明なら1手判断（`uncertainty.py`）、既知なら予告状態の探索（`op: "garbage_search"`） |
| 5 | それ以外 | 構築探索（4.1） |

### 4.1 構築探索

本線（最長の連鎖1本）を組む。**フィーバーは通常盤面の本線が最も大事である（2026-10-07ユーザー）ため、通常構築の目的は本線構築に固定している。**

- 深いビームと仮想ツモ。対戦の既定は幅50・深さ8。評価の重みは `config.json` の `fever`、発火方針（trigger・panic・patience）は `battle_policy.json` の `solo_options`。
- 相殺ストック（`fever/stock.h`）を評価に加える重みセット `fever_aim` と、評価値で初手を選ぶ `aim` は実装として残るが、`normal_build.objective` が `mainline` の間は使われない。

通常盤面では相手の連鎖観測を理由に構築先読みを一律拒否しない。相手のリンク・予告・マージンは構築AIの入力ではないため、実盤面・現在ツモ・可視キューの一致する接頭辞・キャラ・形状周期・モード世代・タネ・試合・探索設定で構築結果を再利用する。先読みは可視2ツモ、出現時の最新戦術は現在の観測で再計算する。`normal_build_search_reused` と `normal_build_searched_visible` はこの部分再利用を示し、完成した判断全体の `search_reused` とは区別する。

相手連鎖や未来レート変化を含む通常の準備要求は、構築だけを保存した場合 `prepared=false`、`normal_build_prepared=true` と返す。事前入力用 `plan` は出さない。相手終了が現在の設置＋ちぎり＋おじゃま判定以前に来る場合や、確定予告が盤面を変える場合は仮想次盤面を使わず、実落下後の観測を待つ。自分のフィーバー中の相手攻撃を含む完全な判断の先読みは引き続き保守的に拒否する。

選択した現在手の操作承認では未確定予告だけの増減を無効化条件から外す。自分のフィーバー中の保留通常予告も現在の盤面を変えないため同様。確定予告は非消去手では厳密に照合し、消去によってその設置のおじゃま落下を止めることが確認された手では取消理由にしない。実盤面・ツモ・キュー・世代・操作状態・時計方針等の検査は維持する。拒否ログには変化した状態キーを追加し、過去ログの一律 `self state changed` だけから原因を断定しない。

可視範囲の異なる構築結果は同一の完全探索結果を保証しない。オフライン比較と実機の入力遅延は別に扱う。詳細と検証根拠は `WORK_LOG.md` の同日追記を参照。

### 4.2 戦術探索（`op: "tactics"`）

可視3ツモまでを1つの探索で読み、積む・最小相殺・本線発火・受けるを同じ値で比べる。

- 各設置で、設置とちぎりの時間、消去、リンクごとの得点と相殺（相殺したリンクごとにゲージ＋1）、相手連鎖イベントの進行、消さない場合の確定予告の落下（1回最大30個）を進める。
- 「落下が迫る」のは、その設置で消さなければ確定予告が落ちる場合と、残る予告（確定＋未確定、最大30個）が落ちたら敗北する盤面の場合。
- 探索は設置数の上限（`max_nodes`、既定3000）で打ち切り、同じ要求には同じ返答をする。完了した最も深い段だけを使う。
- 構築探索の手を「ヒント」として値に加える。可視3ツモより先を知っているのは構築探索だけだからである。構築探索が自分で予告を消し切る発火を選んだ場合は、それを早い発火・本線の消費として減点しない。
- 回復判断（`recover_placement`）も、到達可能な配置に限って同じ探索を使う。

値の構成（`battle_policy.json` の `normal_tactics.weights`）：

| 項 | 重み | 内容 |
| --- | --- | --- |
| `entry` | 6000 | ゲージ7に到達 |
| `gauge` | 1000 | 増えたゲージ1つごと。落下が迫っていないのに消した分は、突入しない限り数えない |
| `stock` | 40 | 葉の相殺ストックの重み付きリンク（`fever/stock.h`） |
| `color` | 60 | 1個で何かが消える色の数 |
| `drop` | 150 | 受けたおじゃま1個ごと |
| `consume` | 12 | 消した色ぷよ1個ごと |
| `mainline` | 1120 | 盤面で最長の連鎖から失ったリンク1つごと（突入時を除く） |
| `uncountered` | 2500 | `mainline_min` 連鎖以上の本線を使ったのに予告が残る場合、失ったリンク1つごと |
| `mainline_min` | 4 | 上の項で本線とみなす最短の連鎖数 |
| `early` | 1500 | 落下が迫っていないのに消した設置1回ごと（突入時を除く） |
| `height` | 300 | 中央2列が8段を超えた段数ごと |
| `exposed` | 700 | 残る予告が落ちると敗北する盤面。1個で発火できる色が少ないほど重い |
| `pending` | 0 | 探索の終わりに残る予告1個ごと（最大60個） |
| `builder` | 250 | 構築探索の手（消さない手、または予告を残さず消す手）と同じ初手 |
| `step` | 400 | 設置1回ごと。同じ結果なら早い突入を選ぶ |

この重みで、テストが確かめている手は次のとおり。未確定予告だけなら本線を打たずに積み、構築探索の手を置く。落下が迫れば単発で止め、3連鎖・7連鎖の本線は残す。ゲージ6からは単発で即突入する。本線で予告を消し切れるなら打って突入する。相手連鎖の観測中は予告が0でも本線を打たない。

返答：`reason` は `tactics_stack`（消さない・落ちない）、`tactics_take_drop`（消さずに受ける）、`tactics_offset`（消して相殺）、`tactics_clear`（消すが相殺なし）。予測は `tactics_forecast`（候補ごとの値・到達ゲージ・生存）。必要色の状況は `normal_color_needs` として添えるだけで、手は変えない。

### 4.3 敗北確定と最短決着

`finish_probe` が可視3ツモと各落下の全端数列を列挙し、生存する消去または生存経路があれば不成立とする。救済がなければ、3回目のおじゃま落下を待たずに中央の列が埋まる配置を、移動・回転・落下・ちぎりの推定時間が最短のものから返す（`no_rescue_fast_finish`）。側列のあふれだけを敗北確定の根拠にしない。

## 5. フィーバー中（`op: "seed_search"`）

観測したタネの盤面と可視3ツモで探索する。最初の消去でタネが交換されるため、消した先は読まない。保管通常盤面の予告は相殺に使えるがフィーバー盤面には落とさない。

### 5.1 方針 `value`

エンジンは常に `value` を使う。すべての手順を「このフィーバーが終わるまでに見込める得点」で比べ、選んだ後に別の手順へ差し替えない。各手順の値は `expected_points`。

- **発火する手順**：その連鎖の全得点（期限内に発火すれば、終了が時計の後でも全リンクを数える）＋ 残る時計で次のタネ以降から見込める得点。
- **消さない手順**：盤面にある最長の発火口の連鎖の得点と、その後の見込み。必要な同色1・2・3個が間に合う見込みを0.75・0.45・0.25とし、来なければタネと段を保つ。
- **終了時の段**：次のフィーバーの最初のタネの得点の半分として数える。規定未達の発火は段を下げるので、得るものがなければ打たない。
- **保留予告**：相殺に使う得点と送る得点を同じ価値とし、別の項にしない。保管盤面が受けきれない分（`quiet_carry_limit` を超える分）だけ、1個を送る10個分として減点する。これにより、有害な持ち越しがあれば時計0でも小さな発火で相殺する。
- 後続のタネは「1色4個ずつのリンク」「成功の見込み0.85」「成功で1段上がる」という型で見積もる。次のタネの盤面や色の予測ではない。

得点は全26キャラのフィーバー倍率表（`scoring.json`）で計算する。未収録リンクは拒否し、通常倍率で代用しない。

### 5.2 明示指定の方針

`seed_options.strategy` で `quick`・`extend` を指定できる。比較と記録の再生のためのもので、エンジンは選ばない。その内部の規則（伸ばしの幾何評価、失敗発火の延期、可視復旧、発火しない終了）は [FEVER_MARGIN_TIME.md](FEVER_MARGIN_TIME.md) とGitの履歴にある旧版の記述を参照する。

### 5.3 時計と期限

- 時間延長の判定には連鎖終了の時刻を使う。連鎖加算は3連鎖から1リンク30F、全消し加算は連鎖終了の16F後。`time_reward_frames`・`remaining_after_rewards` に上限込みで返す。
- 時計0だけでは `wait` を返さない。現在の観測が操作可能なら最後のツモの配置を返す。
- フィーバー中の連鎖時間は通常盤面と別の実測値を使う（[FEVER_TIMING.md](FEVER_TIMING.md)）。採用した定数は `seed_forecast.timing_constants` に返す。
- 端数列が未知で確定予告が端数で落ちる手は、全組合せの最悪で評価して1手だけ返す。

## 6. 時計とイベント（審判）

時計は `clock_running` が明示的に真の区間だけゲームフレーム差で減る。`clock` イベントで観測した残りフレームと停止／再開を設定できる。`enter`・`seed`・`exit` は観測境界を明示したイベント。ゲージが満ちると `entry_pending` を返し、連鎖を終えてから `enter` を受け付ける。時間切れでも開始済みの連鎖は最後まで処理し、残り時間0から報酬で時計を復活させない。

タネは明示した盤面の `seed` イベントで供給する。実機未採取のタネを乱数で生成しない。タネIDは交換ごとに増やし、通常／フィーバー切替ではモード世代を増やす。周期位置は切替でリセットせず、観測した通算位置を使う。

おじゃま端数のカーソルもモード切替で勝手にリセットせず、既存のユーザー指定どおり実際に落ちた個数だけ進める。モード間の実機照合は未完了。再生状態には採用ルールのハッシュを含め、別のルール値で再生した結果を同一と扱わない。

## 7. 出典と採用仕様

ユーザー指定の[なもこ氏の考察サイト](http://namob.net/puyof/)をHTTPで取得し、そこからリンクされている本人の解説を参照した。Webツールではサイト本体がタイムアウトしたが、通常HTTP取得は成功した。入口HTMLのSHA256は `e7b293b3e052cd371e837f3692ff3b60e266b7ae3381e5dfd8e95a12a0ccff3f`。

- [基本仕様](https://puyo-camp.jp/posts/86313)：ゲージ上限7、準備時間15秒・上限30秒、相殺時の増加、時間報酬、二種類の予告とタネ更新の根拠。秒からフレームへの変換は60fpsの試作設定。タネ失敗は基準との差1／2／3以上で、据置き／1減／2減として区別する。全消し突入の失敗判定には加算前の基準を使う。
- [倍率の測定表](https://puyo-camp.jp/posts/67754)：全26キャラの通常／フィーバー倍率を転記。ローカルSteamの一致確認へ昇格しない。
- [初回突入後の選択](https://puyo-camp.jp/posts/136789)と[合戦の判断](https://puyo-camp.jp/posts/135498)：伸ばしと即発火、全消しの価値、相手の連鎖終了付近の攻撃などの戦術根拠。現実装のしきい値・相手の1手予測による代用は実装上の仮説で、記事がAIの最適方針を証明したとは扱わない。
- [フィーバー待ち](https://puyo-camp.jp/posts/76553)：通常本線を維持し、相殺での突入を一律の優先方針にしないための参考。

数値・出典・確認状態は `data/fever/mode_rules.json` と `scoring.json` に保存する。タネの生成分布や時計停止フレーム、突入／終了アニメーションの長さはWeb説明から推測しない。

## 8. 公開タネによる検証

[平積み](https://puyo-camp.jp/posts/74224)、[挟み込み](https://puyo-camp.jp/posts/74107)、[階段](https://puyo-camp.jp/posts/74093)、[座布団](https://puyo-camp.jp/posts/74096)のシミュレータURLから50盤面を取り込んだ。色は一貫した正規名へ置換し、Steamの実測色・生成表とは扱わない。画像のみの階段4連鎖・座布団6連鎖は未収録として明記した。

`reference_seeds.py` は保存済みHTMLを入力に、各図の連鎖数ラベルとURLを対応させる。RLEの長さ、空の上端、浮いたセルを検査し、元HTMLのSHA256・出典・未収録項目を保存する。データは `data/fever/seeds/namoko-reference.json`。

```powershell
python -m fever_battle.bench_seed --output data/fever/baselines/2026-10-05-t14-reference.json
```

50盤面×5表記（2/L/J/4/0）の250条件で、各条件の有利な現在ツモを色列挙で選択した。248条件が基準以上を発火し、250条件すべて配置・得点・結果盤面の再生が一致した。階段15・座布団15のでかぷよは1手で基準へ達せず、失敗として残した。**この条件付きの幾何検証をランダムツモでの成功率や実戦成功率に換算しない。**

## 9. 検証と計測

