## 1. 結論と今回の一本の仮説

次に試す構築方式は **H1：発火口側の構造を保ちながら、末尾を増点する短い部分計画を維持する構築器** とする。末尾への1リンク追加と、末尾の消去群を増やす操作を、同じ「目標得点までの不足を減らす」目的で扱う。15リンクを作ることだけを成功条件にしない。

得点目標への変更自体とH1の効果を分離するため、先に新しい審判と **S0：既知3ツモで目標点へ届く初回本線を発火する対照版** を作る。S0の通常構築はB0のまま。S0が改善した分をH1の効果に含めない。

H1は、最長3手の合法な配置計画を公開観測から生成し、次手でもその計画を検証・継続する。最初の手を替えた直後にB0へ戻したR1との違いは、構築の部分目標を複数の実配置にわたって維持する点にある。初期試作では未知色のロールアウト、全15リンクの逆算、NN、MCTS、B2の予約枠を加えない。これは階層的計画の最小検証であり、40手完成確率を推定できる完成版ではない。

## 2. 得点と終端の契約

### 2.1 主指標

`Pscore_first@H = Pr(最初の実10連鎖以上の発火がH手以内、実本線得点>=T(character)、同時死亡なし)`、H=30/35/40。

| キャラ | ID | 固定目標T | ローカル通常倍率表との関係 |
| --- | --- | ---: | --- |
| ラフィーナ | raffina | 160520 | 各段4個・1色消しの15連鎖 |
| ラフィソル | rafisol | 166840 | 同上 |

初回本線の境界は、過去との整合のため **最初の実10連鎖以上** を維持する。今回の成功判定に15以上という追加条件を入れない。10〜14でもT以上なら成功、T未満ならその場で失敗終了。後で作り直した本線、途中の整理消しとの合計点で成功させない。

得点は、その発火で実際に消えた全リンクの通常モード得点の和。落下点、以前の発火得点、全消しの別ボーナス、相殺／おじゃま換算、Fever中倍率、仮想発火の点を足さない。この定義をmanifestと報告の両方に書く。画面の累積スコアとは区別する。

正本は `data/fever/scoring.json`。Python審判は `sum(Scoring().chain(character, executed_links, 'normal'))` を使用し、C++は `fever::normal_scoring::score` を使用する。`next_score`、`expected_chain`、`Candidate.score`、Tsuの `chain::get_score` を実績得点として流用しない。native transitionは各段の `groups` と `colors` を返すため、保存記録から再計算できる。

各リンクiの点は `10 * sum(groups_i) * clamp(normal_power_i + color_bonus + sum(group_bonus), 1, 999)`。マルチ消し・連結数ボーナスとキャラ別倍率を省略しない。指定2キャラ以外のTは未設定とし、追加時に明示する。全キャラへ同じ160520を暗黙適用しない。

### 2.2 試行の停止順序

```text
空盤面、通常モード、周期位相0、可視3、t=設置済みPiece数
while t < 40:
    公開Observationだけでchooseする
    timeout / error / 配置不能なら失敗として終了
    参照環境で実配置し、t += 1
    実linksからキャラ別通常得点を再計算して記録
    deadなら失敗終了（T到達と同時でも失敗）
    if actual_links >= 10:
        points >= Tなら成功、それ以外はfirst_below_scoreで失敗終了
    1〜9連鎖は記録して継続。絶対tを戻さない
40手終了ならno_mainlineで失敗
```

40手目の発火を含み、41手目は含めない。1〜3／4〜6／7〜9の回数・点・消去数を別々に保存する。10未満でTへ届いた例も `sub10_at_target` として記録し、今回の初回定義では成功へ変換しない。今回再集計した528記録には該当なし。閾値8での感度分析は保存prefixで可能な範囲のみ行い、旧停止後の未来は補完しない。

全開始試行が分母。死亡・配置不能・手ごとのtimeout・エラー・40手未発火を除外しない。実験全体の時間上限による打切りはunfinishedで、ゲーム上の失敗と区別する。unfinishedを分母から消さず成功率の上下界を報告し、1件でもあれば採否を保留する。

### 2.3 従来の空間評価で変える点

- 14連鎖でも目標点に届く。計算例として、13段を4個消し、14段目を8個1色消しにすると、ラフィーナ160840／ラフィソル167160点。この例は得点式のテストであり、合法な到達盤面を示すものではない。
- 後半の消去群の大きさは得点へ寄与する。群余剰を一律に罰したり、「必ずあと1リンク追加」を強制しない。
- `60個 = 4×15` は15連鎖の必要条件である。得点目標に対して色数不足を証明するには、キャラ別の得点上界が別途必要。旧 `mass_slack40=C+供給−60` をそのまま得点不可能判定へ流用しない。H1初期版では供給・空きは診断と安全制約に使い、新しい厳密上界は実装しない。
- P13/P14/P15/P16は引き続き記録するが、目標点を満たす短い本線へ移行したことだけを不採用理由にしない。目標未達本線の点数分布も報告し、単なる小発火の増加を検出する。

## 5. S0：点数で選ぶ可視発火の仕様

既存 `fever::fire::best_visible` は連鎖長を先に比較する。これを呼んで返された1候補の点をチェックするだけでは、短い高得点候補を見落とす。研究用の新規関数で、実際に見える `min(3,40−t)` 個のPieceを列挙する。

1. 各層で `fever::normal_space::moves` → `Field::drop_piece` → `Field::pop` を使用する。drop_piece単独で操作可能と判定しない。BIGのrは絶対色、L/J/QUADの配置は既存幾何に従う。
2. 死亡枝は終了。最初の実10以上でその枝を終了し、点数T未満の本線の後へ探索を続けない。実1〜9は、記録付きで後続を調べてよい。
3. 実10以上・通常得点T以上・同時死亡なしの経路だけを達成候補とする。優先順は、発火までの設置数が少ない、実本線得点が高い、途中廃棄が少ない、配置列の辞書順。
4. 最浅の成功深度の候補を全て比較してから採用する。途中で打ち切った深度の1件だけを確定最良候補としない。開始時に見えるツモだけで到達する証明を保存する。
5. 証明済み経路の最初の1手を返す。毎手S0を再計算し、現在見える範囲の目標達成を優先する。該当なし／探索未完了ならB0、H1条件では次節へ進む。

通常構築を強くするための重み変更、目標未満本線の一律禁止、B0の幅・深さ・保持ガード修正は入れない。過去の小消し・整理を認める契約も維持する。

## 6. H1：末尾増点計画の具体仕様

### 6.1 公開API・永続状態

Python側は既存 `choose(Observation)` を実装する。Observationの7項目を維持し、Tと研究予算は初期設定として渡す。環境seed、保存試行ID、隠れた未来、実列の生成RNGを渡さない。初期版は決定的で、未知色Samplerを持たない。

研究C++workerの1試合分の状態は以下。試行開始・キャラ変更で必ず初期化する。

```text
GoalPlan:
  character, created_t, phase, expires_t
  origin_field_hash, origin_visible[3]
  head_anchor_ids_by_link, tail_anchor_ids
  trigger_column, trigger_color, maximum_key_count
  base_geometric_score, planned_geometric_score
  actions[1..3], expected_fields_after_each_action
  goal_kind = append_link | enlarge_tail_group
  status = active | completed | invalidated | expired
```

`expires_t <= created_t+3` かつ40以下。経路自体の期限と、旧 `moves_since_chain` を混同しない。計画IDは公開観測と目標内容から作り、元seedを使わない。

### 6.2 幾何Witnessを得る

`fever/evaluation.cpp` の単列鍵の考え方は再利用するが、旧評価で選ばれた1個のpotentialだけを目標にしない。新規研究関数で列x・色c・鍵1〜3個を列挙し、既存popと通常得点計算から消去マスク列を保存する。鍵を足せる高さは既存potentialと同じ `min(3,12−height[x])` の範囲とし、各x/cでは最初に発火する鍵数のWitnessだけを採る。上端を越える仮想セルを作らない。既存製品potentialは編集しない。

Witnessの記録は `x,c,key,links,points,masks,remaining,headroom`。仮に足した単色鍵は、実際のPieceとして置いたものではない。**G=幾何Witness、P=合法な構築prefix、F=可視ツモで実発火まで到達する証明**を区別し、G/Pの点数を実績や成功確率へ変換しない。

目標候補は4リンク以上のWitness。上位の現在幾何得点が既にT以上なら、その判断では末尾増点を新規提案せずS0/B0へ戻す。不要な過剰構築を避け、鍵の到達問題は別診断として残す。T未満なら `(points降順,key昇順,headroom降順,x,c)` で選び、異なる `(x,c)` を最大3個保持する。この3は内部部分目標数であり、B2のビーム予約枠ではない。

### 6.3 発火側・末尾の同一性

盤面hashが違うだけでは別の連鎖尾と認定しない。既存の実ぷよへ元座標由来のIDを付け、仮の鍵／計画で追加したぷよには別IDを付ける。popが返す各段マスクを順にID盤面へ当て、除去後は列内の順序を保持してIDを落とす。色盤面の結果が既存popと一致することを検査する。新しい物理シミュレータを正本にしない。

元Witnessの先頭 `max(1,L−2)` 段に属する実ぷよID群を発火側のアンカーとし、最後の2段のID群を末尾とする。候補のWitnessは同じx/cの鍵で再評価し、必要鍵数は元以下とする。

- 発火側アンカーは元と同じ段番号で消える。計画で追加したぷよが先頭側の消去群へ混ざった候補は、今回の末尾操作から除く。
- 元Witnessで消える実ぷよIDを失わない。末尾IDは発火側へ繰り上がらず、最後の2段又は追加段で消える。
- 連鎖数を維持したまま末尾群が増える、又は末尾が伸びることで、キャラ別の幾何得点が厳密に増える。

これで尾の対応が判定できない候補は `tail_identity_unavailable` とし、別構造の高得点Witnessへ勝手に置き換えて目標達成としない。対象が少なければ保留材料にする。

### 6.4 実際のPieceによる計画生成

現在の可視3個、深さ `min(3,40−t)` の前向き合法配置木を1回列挙する。最初は深さ制限DFSで十分で、長期ビーム/MCTSは新設しない。S0の非消去prefixを共有してよい。全可視3手の木の分岐上限はローカルの合法手生成に従い、ペアだけを前提に22へ固定しない。

H1のactive計画のprefixは、各手で実消去0、廃棄0、死亡なし、margin1を満たすものへ限定する。これは最長3手の目標操作の条件であり、試合全体で整理消しを禁止する条件ではない。条件を満たす計画が無ければB0へ戻り、B0の1〜9連鎖は継続可能。

深さ1〜3の各prefix終端で、保持した最大3Witnessについて上の同一性と点数増加を評価する。同じ鍵を維持できない／鍵が増える／元本線を崩す経路は不適格。新しい有望候補をB0の返却rootに限定せず、全合法prefixから生成する。

適格計画は、次の辞書順で1つ選ぶ。巨大な加点や新しい調整係数を入れない。

```text
  目標Tまでの残り幾何得点 max(0,T−Qgeo) が小さい
  必要鍵数が少ない
  使用手数が少ない
  経路内の最小中央安全余白が大きい
  終端の空きセル数が多い
  配置列・目標IDの辞書順
```

目標点へ届いた後の過剰な幾何得点は第1項で優遇しない。群余剰・残り色数・供給量は記録し、一律の罰点にしない。この順位は成功確率の推定器ではなく、未検証の初期方策である。改善しなくても実験途中で重みや順位を変えない。

### 6.5 実行・中断

毎手の優先順は、S0の目標点発火 → 有効なactive計画の次手 → 新規H1計画 → B0。active計画中は、単に別の幾何点が高くなったという理由で目標を交換しない。

現在盤面が保存した予測盤面と一致し、次Piece・絶対t・周期が一致し、次配置の合法性／廃棄0／margin1が再確認できる場合だけ継続する。見えてきたツモによってS0がT以上を発火できるなら、即座に計画を中断してS0を採用する。観測不一致・外部消去・期限・不正な遷移なら計画を破棄して再判断する。

計画の最終prefixを実行しても、本線を実発火したとは記録しない。達成したのは部分目標であり、実績は審判の初回本線得点だけで決まる。作り直し・セカンド状態へは入らない。

B0が目標未満本線を発火する局面でも、上記を満たすH1計画があれば研究器はその計画を選べる。H1の手を製品の `_solo_build` に再投入して元の手へ上書きしない。研究器自身の介入とB0の推奨・容量理由をログで区別する。製品の保持・戦術ガードを編集することは認めない。

## 7. 計算量と時間予算

初期定数は最大3目標・可視深さ3・TTL3。1判断での合計transition試行上限を16000、追加Witnessのpop上限を48000とし、S0とH1で共有する。各prefix・各目標の再評価は最初に発火する鍵で1回のpopとする。S0とH1で同じ可視prefixを無駄に再列挙しない。上限に達した比較は未完了と記録し、その未完了の候補集合からH1を採用しない。B0へ戻せる時間を確保する。

研究用上限は各条件1秒/choose。研究workerは協調的な期限検査を行い、残り300msをB0 fallback用に残す。B0は既存250×8をそのまま呼ぶ。研究workerは1 thread、B0は既存最大6 thread、両者は逐次実行し、入れ子の6×6並列を作らない。B0/S0/H1とも要求開始から返却までの外側watchdogを持ち、返却できなければtimeout失敗とする。既存10秒IPC timeoutを1秒の保証に読み替えない。

1秒は実用採用の予算ではない。同じ1秒上限の対照と比べても、H1のCPU増分は必ず別掲する。ノード上限、wall予算、比較打切り理由を全て保存する。

研究比較が継続条件を満たした場合だけ、同じ方式を250ms/chooseで測る。研究処理枠を最大25ms、B0 fallbackのため残りを確保し、元のノード上限は増やさない。共通watchdogを全条件へ適用し、期限超過は分母に残す。予定枠25ms内で候補を完了できなければ、実用化の証拠不足として保留する。B0自体の250ms返却を保証済みとはしない。

時間打切りで配置が変わり得るため、意味的再現は固定ノード上限・十分な時間のモードで確認し、時間制限実験の実際の停止点を記録する。1秒上限の成功を250ms版の成功として流用しない。
