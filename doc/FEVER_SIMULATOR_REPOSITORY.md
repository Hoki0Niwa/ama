# 独立Feverシミュレーターとの接続

オフラインの完全対戦・学習環境は `C:/Users/ho_ki/git/fever-simulator` が所有する。AmaはAI・探索・評価・エンジンAPI、ブリッジは観測・入力・ランチャーを担当する。

## 用途と実行

C++20のイベント駆動審判で、通常→突入→タネ交換→復帰→勝敗を進める。全26キャラ、52タネ、倍率、相殺、2系統予告、時計、マージン、並列試行、記録・再生、学習用batch APIを扱う。学習（PPFAI）向けに、試合を作らず多数の盤面の置ける手・連鎖・点数・次の判断までのフレーム・潜在連鎖をまとめて返すDLL（`build/fever_board.dll`、`tools/board_api.py`）もある（2026-10-19、試合の経過は不変で revision 20 のまま）。

```powershell
python C:/Users/ho_ki/git/fever-simulator/tools/ama_selfplay.py --ama-root C:/Users/ho_ki/git/ama-fever --seed 0 --matches 4 --workers 2 --output bin/simulator-check --audit
```

Amaの `ModeBattleEngine`／nativeを2席へ接続し、現在手＋NEXT2と同時刻の公開観測を渡す。席別設定は `--seat-config`・`--seat-width`・`--decision-budget-ms` を使い、正確な引数形式は同ツールの `--help` を参照する。再生はシミュレーターの `fever_simulator.exe --replay`。Ama側 `fever_battle.replay` は別の明示イベント形式用。

## 色源と時間

`steam_seed32` は元処理の21000手、タネ抽選・強制色補正455例との照合を記録している。タネ抽選の乱数は色表の生成（1,587回）後のゲーム管理乱数から始まり、飛散（1個5回）とも共有する（revision 7）。`training_chacha12` は長い学習列用で、独立実装147456色と照合。両色源を同一の評価分布としない。`training_chacha12_opening` は同じ列の前に実機の初手（R・G・B・R/G/Bから1色）を付ける学習用の方式（2026-10-19）。

simulation_revision 20（2026-10-18時点）。元処理の生成・飛散・列抽選・地形運動を照合し、保存Steam148区間の連鎖時間で誤差0F。元コードから移植したもの：

- 得点式・倍率表・マージン（revision 6）
- 攻撃の発射と到着・同一フレームの処理順（revision 7）
- 組ぷよの操作処理（`src/control.*`）。審判では任意の `control_model=source_control`（revision 8）。既定は従来の到達判定と代表値14F。
- パッドの席の出現待ちの入力バッファ（revision 9）
- でかぷよの色変更回転（revision 11）。A で次の色（赤→緑→青→黄）、B で前の色。位置と向きは変わらない。
- 攻撃オブジェクトの開始処理とおじゃまトレーの3段階（revision 10、既定 `delivery_model=source_tray`）。攻撃は発射時に受け手の予告へ飛行中として入り、保留に数える。相殺は作成時と到着時の2回。

revision 9 では、実機ログ（`docs/CAPTURE_FORMAT.md`）の入力をそのまま再生する行動と、比較ツール `tools/compare_capture.py` も加えた。

- 実機と合わせて直したもの：
  - revision 12：下入れの得点、リンク開始の1F、上端の敗北の時刻。
  - revision 13：ゲージと準備時間の加算が相殺の到着から32F後、ちぎりの数え方、連鎖した手のフラグ（Feverが連鎖の途中で時間切れになると、復帰でおじゃまを落とさない）、時間切れのタネ交換。

## 確認範囲と制約

実機の記録と照合済み：色列とタネ、攻撃の発射・到着フレーム、相殺、通常全消し交換、落下なし復帰、共有乱数、マージン。未照合：入力時間の代表値14F（既定の `direct`。記録の入力を再生する経路だけが一致する）、別キャラ・別の日。環境の連鎖時間一致をAmaの時間予測・入力一致へ自動的に読み替えない。Amaの審判・モデルはrevision 10の時点のままで、revision 12〜15の相違は [対戦ルール](FEVER_BATTLE_RULES.md) と [時間モデル](FEVER_TIMING.md) に書いた。

実機と同じ席設定の5seed比較では、全5リプレイが再生一致し、同条件の再走も同一。実機の勝者とは3/5一致で、手数・最大連鎖・Fever突入は相違した。prefetch・実入力遅延・壁時計探索を完全再現しておらず、5標本の勝敗一致を精度として使わない。

出現列が塞がった局面で、接続が現在Pieceの実姿勢を渡せず停止する制約がある。未完走を敗北や成功へ置き換えず、比較の全試行へ含めて報告する。

## 学習用に凍結する条件

simulation_revision 20を学習用に凍結する（19からは置ける手をAmaに揃えただけ）。同じシード同士の対照（Ama同士、200シード×キャラ入替で比較ごとに400組、2026-10-18、`tools/ama_option_ab.py`。revision 17で測定）と実機の記録で、残る相違の扱いを次のように決めた。

- 原因の分からないおじゃま落下の1〜3F（捨てられるおじゃまがある落下だけ、実機が長い）は、既知の相違として残す。捨てがある落下を+3Fしても、勝者が変わったのは捨てがある317組のうち4組で、連鎖・突入・試合の長さの差は有意でなかった。
- 入力時間は、学習と評価の既定を `direct`（1手14F）のままにする。実機の記録の1手の操作時間（AIの遅れとブリッジの入力を含む）は平均15.6F・中央14F（1,482手）。移植した操作処理の `source_control` は定型の入力列のため平均21.8F・中央24Fで、実機より遅い。`source_control` にすると勝者が37％の組で入れ替わり、連鎖と降下量が増える。`direct` に残る差は、時間が列や回転の距離によらないこと（実機は8〜24F）。
- 置ける手は、revision 18でAmaの `placements` と同じ規則にした（取り込んだAmaはコミット `0407f998`）。同じ盤面での置ける手の集合の違いは、20試合の判断で49回から14回に、Amaの選び直しは4試合で11回から0回になった。revision 19では、3個組の出現段からの持ち上げの停止と `lift_allow`（コミット `62c850c9`）も取り込み、`lift_allow` をシナリオの `options.lift_allow` で渡せるようにした（ブリッジの表は `data/lift_allow.json`、自己対戦は `--lift-allow`）。revision 20では、これから置く3個組で、移植したゲームの操作処理（`fever/control_moves.*`）が固定できる持ち上げも、Amaと同じく置ける手に加えた（コミット `233c60a`、`normal_space::moves` の `current`。シミュレーターの組み込み方策の先読みでは加えない）。Amaのバイナリとの置ける手の違いは、表なし・表ありとも20試合の判断で0（revision 19のままでは14回・13回、どれもAmaだけが許す3個組）。操作処理は地形を静止として扱うので、おじゃま落下の直後に実機で外れる差は、シミュレーターの `direct` に無い。
- 観測の飛行中の攻撃（量・最も早い到着）は、学習の観測に残す。記録ツールはこれをメモリーから読め、記録との照合で一致している。ブリッジの対戦用の観測にも足した（要求の `observation.in_flight`、2026-10-18）。`self`／`enemy` に入れないのは、承認（`authorize_mode_reply`）が自分の側を厳密に比べ、到着だけで判断を捨てるため。今のAmaはこの項目を使わない。実機の対戦での確認は未実施。

同じ試験で、シミュレーターのFever倍率表が17値のままでAmaの要求が拒まれ、Amaの自己対戦が止まることが分かった。シミュレーター側で19値を渡すように直した（得点の計算は変わらない）。数値と限界は同リポジトリの `docs/VALIDATION.md`「凍結の感度試験」、決定は `docs/OPEN_ISSUES.md` 6・8・19。
