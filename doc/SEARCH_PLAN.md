# 探索と評価の再編計画（通常構築・フィーバー狙い・フィーバー中）

作成：2026-10-06。状態（2026-10-07）：**P0〜P4は実施済み。P5は切替式で実装し、既定は従来のまま。P6は未実施**（理由と未決事項は第9節）。P7（実機確認）は未実施。第1〜6節は当初の計画で、実施結果は第7節以降にある。

依頼：通常状態・フィーバー狙い・フィーバー状態で立ち回りが大きく異なるため、探索をどう分けるかの方針をまとめる。後付けで積み重なり今後悪影響を及ぼしそうな実装をなくす計画も含める。

## 1. 結論

- 探索ループを状態ごとに増やさない。**分けるのは評価・終端条件・発火方針、共通化するのは探索機構と遷移シミュレーション**とする。
- 探索の型は2つに絞る。
  - **構築探索**：深いビームと仮想ツモ、盤面だけのノード。予告のない通常盤面で使う（`fever/search.cpp`）。
  - **戦術探索**：可視3ツモ、フレーム・予告・端数列・相手連鎖を持つノード。予告のある通常盤面とフィーバー中で使う。
- 目的は3つ。本線構築、フィーバー狙い（相殺7回）、タネ発火・伸ばし。それぞれ評価関数として実装し、上の2つの型に載せる。
- 判断を順に試す梯子と、決まった手を後段で置き換える処理は、同じ尺度で候補を比べる探索へ吸収してから削除する。

## 2. 現状と問題

### 2.1 探索はすでに分かれている

| 局面 | 実装 | 型 |
| --- | --- | --- |
| 通常・予告なし | `fever/search.cpp`（別プロセス `fever.exe`） | 深い構築ビーム＋仮想ツモ |

| フィーバー中 | `seed_search.cpp` | 可視3ツモのビーム |

### 2.2 問題

1. **目的が分かれるべき所で分かれていない。** 通常盤面の構築は段階Aの「最大の連鎖1本」を評価する。フィーバー狙いに必要な「複数の発火口から取れるリンク数の合計」は評価になく、Python側の1手読みで後から補っている。
2. **遷移の実装が重複し、食い違っている。** おじゃま落下、得点、相手連鎖の時系列、端数列の全組合せが探索ごとに別実装になっている（第4節B）。列あふれを敗北とするかは実装ごとに異なる。
3. **探索どうしの点数を比べられない。** `mode_engine._normal` は判断を順に試し、最初の答えを採る。2026-10-06の実対戦ログの「予告0で相手連鎖中に最長連鎖を打つ」不具合は、この順序の隙間で起きた。
4. **1手読みの上書きが構築を崩した実績がある。** `tools/bench_fever_normal_build.py` の記録で、必要色による置き換えありは平均9.0連鎖、外すと12.67、独自順位の貯め込みは1.5だった（試作用色列・相手なし）。

## 3. 目標の構成

### 3.1 共通の遷移部品

1手の遷移（設置 → ちぎり時間 → 消去 → 得点 → 相殺 → 非消去ならおじゃま落下 → 敗北判定 → 相手イベントの進行）を1か所に実装し、戦術探索の全入口が使う。

- 置き場所は `fever_battle/` の新規ヘッダー。`core/`・`ai/` は変更しない。
- 端数列は「既知の位相で1通り」「未知で全組合せ」の2つの呼び方を同じ関数で提供する。
- 列あふれの扱いを1つに決める。**列あふれだけでは敗北としない**（2026-10-06ユーザー確認：フィーバールールでは14段目に置かれたぷよは消滅する。2個組を縦にして14段目へ置けばツモをそのまま消せる）。敗北は出現位置の判定だけで決める。おじゃまが13段を超える分も同じく消滅すると解釈して適用する。この解釈はツモについての確認からの類推で、おじゃまでの実機照合はしていない。
- Python側の同等処理（`uncertainty.outcomes`、`model.drop_garbage` など）は、nativeの結果を使う形へ寄せる。

### 3.2 相殺ストック関数（フィーバー狙い用）

盤面から「消さない手を挟まずに取れそうな相殺リンク数」を返す関数を `fever/` に新設する。

- 既存の `quiet::search_count` は発火点ごとに連鎖数と発火後の盤面を返す。必要ぷよが最少の発火点を取り、残り盤面で再び探すことを繰り返して合計する。上限は 7−現在ゲージ。
- 加点：1〜2個で発火できる色の種類数。
- 減点：発火に必要なぷよ数、1リンクあたりの消費ぷよ、中央2列の高さ。
- 得点は使わない。予告を一度に消し切ると残りのリンクが相殺にならないため、消費の少ないリンクを優先する。

### 3.3 構築探索：重みセットの切替

- `fever::evaluate` に相殺ストックの項を足す（`hill` と同じ専用項）。`ai/search/beam` は変更しない。
- 重みセットは「本線構築」と「フィーバー狙い」の2つ。フィーバー狙いでは単独用の発火方針（trigger・panic・patience）を止め、予告がない間は消さない。
- 使い分けは**切替式**とする（2026-10-06ユーザー決定）。状況に応じて重みセットを丸ごと切り替え、2つの評価を重み付きで足す混合式は採らない。切替条件は段階P2の計測結果から決める。

### 3.4 戦術探索（通常・予告あり）

貯める・最小相殺・本線発火・受けるを、1つの探索の候補として同じ尺度で比べる。

- 尺度：生存 → 到達ゲージ＋葉の相殺ストック → 本線の維持 → 消費の少なさ。
- 端数列が未知の落下は現行どおり全組合せの最悪値で評価し、仮の盤面の先を読まない。落下後は再観測する。
- 相手連鎖の時系列がある場合も同じ探索で扱う。
- `finish_probe` は敗北確定の証明であり、目的が異なるので独立のまま残す。

### 3.5 戦術探索（フィーバー中）

独立したタネ探索の形を保つ。最初の消去でタネが交換されるため終端が特殊で、時計と持ち越し予告を正確に扱う必要があるからである。

- 消さない手の評価を、`potential()`（同色を縦に1〜3個足す検査）から構築側の連鎖検出（`quiet::search_count`）へ置き換える。
- 順位を「フィーバー終了までに稼げる見込み得点」の1つの尺度にする。発火手は「この連鎖の得点＋残り時間で次のタネから稼げる見込み」、非消去手は「伸ばした後の得点×見込み＋減った残り時間での見込み」、終了時は持ち越し予告を減点とする。見込みは `seed_turnover_plan` の概算を葉の評価へ移す。
- 可視3ツモより深くは読まない。

### 3.6 モード境界

突入・タネ交換・通常復帰で盤面が未知になるため、探索は境界を跨がない。境界の価値（突入の価値、持ち越し予告と保管盤面の耐久）は葉の評価として各探索に持たせる。

## 7. P2の実施結果（2026-10-07）

### 7.1 実装

- `fever/stock.h`：相殺ストック。盤面の各列・各色に1〜3個足して消える最少個数の発火点を探し、最少のものを取って残り盤面で繰り返す（最大4回、合計リンク数は 7−ゲージ まで）。1個で発火するリンクを4、2個を2、3個を1として数え（`units`）、1個で何かが消える色の数（`colors`）を別に返す。得点は使わない。
  - 3.2の案との違い：`quiet::search_count` は2連鎖以上しか返さないため使わず、単発も数える専用の走査にした。
- `fever::evaluate`：重みセットの `stock`・`stock_color` が0でなければ評価へ加える。既定の重みセット（`fever`）には無く、従来の評価は変わらない。
- 候補の選び方（`Configs::aim`）：従来は「その手の先で見つかった最大連鎖の得点」で初手を選んでいた。フィーバー狙いでは、その手の先の最も深い層で到達した最良の評価値で選ぶ。得点で選ぶ限り、評価を変えても初手の選択が変わらないためである。
- 重みセット `fever_aim` を `config.json` に追加（`chain` 300、`stock` 500、`stock_color` 400、`score` 0、他は `fever` と同じ）。
- 切替：`data/fever/battle_policy.json` の `normal_build.objective`。`mainline`（既定）と `fever_aim`。`fever_aim` は相殺でゲージが増える設定かつゲージ未満のときだけ有効で、連鎖数による発火（trigger・patience・shave）を止める。盤面が埋まったときの発火（panic）は残る。
- 対戦用バイナリに `op: "stock"` を追加（テストと計測用）。

### 7.2 計測

`tools/bench_fever_baseline.py entry`、ラフィーナ、各条件24色列。条件は「最初の予告の手数・間隔・1回の確定予告数」。

| 条件 | 本線構築：突入／死亡・手数・被弾 | フィーバー狙い：突入／死亡・手数・被弾 |
| --- | --- | --- |
| 12手目から3手ごとに4個 | 24／0・10.46手・5.21個 | 24／0・8.62手・2.33個 |
| 6手目から2手ごとに6個 | 16／8・14.69手・31.5個 | 16／8・14.12手・30.69個 |
| 10手目から毎手3個 | 22／2・10.55手・19.05個 | 23／1・8.22手・11.17個 |
| 8手目から5手ごとに20個 | 9／15・11.11手・22.11個 | 10／14・11.2手・26.6個 |
| 4手目から毎手2個 | 23／1・13.91手・19.22個 | 24／0・13.38手・18.12個 |
| 合計（120） | 突入94・死亡26 | 突入97・死亡23 |

手数は最初の予告から突入までの平均、被弾は突入までに降ったおじゃまの平均（どちらも突入した色列だけ）。記録は `data/fever/baselines/2026-10-07-p2-entry-objectives.json`。

- 少量の予告が続く2条件では、突入までの手数と被弾が減った。重い予告とまとまった予告の条件では差がない。合計の突入・死亡の差（3件）は、色列を替えれば逆転しうる大きさである。
- 別の重み（`chain` 0、`stock` 800、`stock_color` 600）も同じ条件で測った。合計は同じ突入97・死亡23で、条件ごとの優劣が入れ替わるだけだった。重みの調整で動く幅は小さい。
- 効果が限られる理由：予告が来た後の手は、構築探索ではなく防御側の判断（`fever_defense.py`・`gauge_wait`）が選んでいる。構築の目的が効くのは予告前の盤面だけで、消化の手順はP3の対象である。
- 思考時間の最長値は両方とも約160msで、差は見られない。
- 試作用の色列・台本どおりの予告での値で、実機の対戦結果ではない。本線を残せたか（突入後・復帰後の強さ）は測っていない。

## 9. P5の実施結果と、P6を実施しなかった理由（2026-10-07）

### 9.1 計測の追加

`tools/bench_fever_baseline.py fever`：1回のフィーバーを最初のタネから時計の終わりまで通しで進める。発火のたびに公開タネの次の段（成功で＋1、失敗で据置き〜−2、全消しでさらに＋2）へ交換し、連鎖の時間と時間加算はタネ探索自身の予測値を使う。合計得点・消化タネ数・規定達成率・最長連鎖・残った保留予告を数える。

### 9.2 実装

タネ探索に3つ目の方針 `value` を追加した（`seed_search.cpp`）。すべての手順を「このフィーバーが終わるまでに見込める得点」の1つの値で比べる。

- 発火する手順：その連鎖の得点 ＋ 残り時計で次のタネ以降から見込める得点
- 消さない手順：いま盤面にある最長の発火口の連鎖の得点と、その後の見込み。必要な色ぷよ1・2・3個が間に合う見込みを0.75・0.45・0.25とし、来なければタネと段を保つ
- フィーバー終了時の段は、次のフィーバーの最初のタネの得点の半分として数える
- 相殺に使う得点と送る得点は同じ価値とし、保留予告は別の項にしない。保管盤面が受けきれない分だけを減点する
- `value` では、選んだ後の経路差し替え（失敗発火の延期、発火しない終了）を行わない。発火済みの手順を優先する差し替えだけは `extend` 専用で元から対象外

見込みは「1色4個ずつのリンク」「後続のタネは0.85で成功」という型による概算で、次のタネや色の予測ではない。定数はすべて試作値。

切替：`data/fever/battle_policy.json` の `fever_seed.strategy`。`auto`（既定、従来の選択）と `value`。要求の `seed_options.strategy` でも指定できる。

3.5の案との違い：「伸ばしの評価を `quiet::search_count` へ置き換える」は行っていない。`potential()` も同じく列へ同色を1〜3個足す検査で、置き換えても見える範囲は変わらないと分かったためである（3.5の「縦にしか見ない」という記述は誤りだった。盤面上の連結で判定するので横につながる発火も検出している）。

### 9.3 計測

ラフィーナ、時計900F、各条件40色列。`auto` は現行のエンジンの選択、ほかは全タネで方針を固定。

| --- | --- | --- | --- | --- |
| 5連鎖・0個 | 12,347点 | 15,000 | 17,100 | 21,036 |
| 9連鎖・0個 | 31,702 | 47,313 | 34,786 | 60,078 |
| 3連鎖・0個 | 7,791 | 12,618 | 11,188 | 16,866 |

- `value` は5条件すべてで平均得点が最も高い。最長連鎖の平均（8.5／11.4／7.7）も `extend`（8.1／10.7／7.3）以上で、保留300個の条件で残る予告も最も少ない（9連鎖開始で0.7個、`auto` は67.1個）。
- **`auto` は5条件中4条件で最も低い。** 保留予告が0のときも「予告を消化できる見込み」として消化優先（`prefer_turnover`）が選ばれ、短い連鎖を多く打つ。固定の `quick`（消化優先なし）より、9連鎖開始で約1万5千点低い。
- この計測は得点だけを見る。次のフィーバーへ持ち越す段の価値、保管盤面の安全、相手の状況は数値に入らない。試作用の色列・公開タネ・モデル上の時計での値である。

### 9.4 P6を実施しなかった理由

`value` をエンジンの既定にすると、既存のテスト237件のうち次の挙動を定めた約10件が成り立たなくなる。

- 少量のおじゃまを受けた後も、規定連鎖（3連鎖など）をすぐ打たずに積んで復旧・伸ばしを続ける（`test_fever_garbage_repair`・`test_fever_long_extension`・`test_fever_deadlines`・`test_fever_mode` の計6件前後）。`value` は見えている規定発火を打つ
- 保留予告があるとき早い失敗発火をしない（`test_fever_final_failure`）
- 時計0の最後のツモでも発火する（同上）
- 有害な持ち越しがあるときは最後の相殺を残す、保管盤面が受けきれないなら無害と扱わない（`test_fever_tactics`）

これらは2026-10-06のユーザー指示（伸ばしの強化、少量おじゃまでの失敗発火の抑制、終了時の扱い）から作られた挙動である。得点だけの計測を根拠に、指示で決めた挙動を消すことはしなかった。したがって既定は `auto` のままで、第4節A表のフィーバー側（選択後の経路差し替え、`quick`／`extend` と `prefer_turnover`、`seed_strategy`）は削除していない。
