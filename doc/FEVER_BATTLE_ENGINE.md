# 通常対戦エンジン試作（T8〜T13）

更新：2026-10-05。全キャラ共通の対戦基盤の着手版。従来の `bin/fever/fever.exe` は単独用のまま、別の入口で対戦状態を扱う。既存ブリッジのランチャーにはまだ接続していない。

## 構成と実行

- `fever_battle/main.cpp`：評価・探索をリンクしない盤面ワーカー。保守的な合法配置、遷移、リンクごとの消去群、試作用色列を返す。
- `fever_battle/model.py`：キャラ別通常得点、予告パケット、相殺、確定、落下、全消し待機の審判。
- `fever_battle/engine.py`：対戦JSONの検査と共通判断。建築には別プロセスの単独エンジンとClaude調整済み設定を使う。
- `fever_battle/observation.py`：同一フレームでの観測と入力前の決定再検査。メモリの読み書きやパッド操作は行わない。
- `fever_battle/simulate.py`・`replay.py`：イベント方式の自己対戦とログ検証。

```powershell
./build.ps1 -Target fever
./build.ps1 -Target fever_battle
python test/test_fever_battle.py
python -m fever_battle.engine
```

各プロセスは1行JSONを受けて1行JSONを返す。別の設定は `--config`、別のバイナリは `--native`・`--solo` で指定できる。エンジン返答の待機上限を超えたプロセスは終了し、遅れた返答を次の要求に流用しない。これはCPUの待機上限であり、攻撃到着までの実フレームを保証するものではない。

## 対戦要求

例は全て架空の観測。ゲージ設定の実機確認には使えない。

```json
{
  "protocol_version": 2,
  "rule": "fever_normal_battle",
  "match_id": "match-001",
  "frame": 120,
  "observation": {"frame_before": 120, "frame_after": 120, "match_status": "running"},
  "gauge_gain_on_offset": 0,
  "target_point": 120,
  "self": {
    "observed_frame": 120, "phase": "controllable",
    "moves_since_chain": 0,
    "character": "raffina", "mode": "normal", "gauge": 0,
    "dropset_index": 0, "piece_id": 0,
    "field": ["......", "......", "......", "......", "......", "......", "......",
              "......", "......", "......", "......", "......", "......", "......"],
    "queue": ["2:RG", "2:BY", "L:RRG"],
    "confirmed": 0, "unconfirmed": 0, "remainder": 0
  },
  "enemy": {
    "observed_frame": 120, "phase": "controllable",
    "moves_since_chain": 0,
    "character": "arle", "mode": "normal", "gauge": 0,
    "dropset_index": 0, "piece_id": 0,
    "field": ["......", "......", "......", "......", "......", "......", "......",
              "......", "......", "......", "......", "......", "......", "......"],
    "queue": ["2:RG", "2:BY", "2:RG"],
    "confirmed": 0, "unconfirmed": 0, "remainder": 0
  },
  "solo_options": {"beam_width": 250, "beam_depth": 16, "margin": 1}
}
```

`phase` は `controllable`／`placing`／`chain`／`waiting_seed`。自分は操作可能なときだけ判断する。相手が連鎖中等なら現在手で即発火できるとは報告しない。`field` は上から14段、最上段は空、浮いたセルは拒否。`queue` は現在手＋NEXT2まで。色はR/Y/G/B、おじゃまは#。キャラIDは周期から一意に推定せず、明示する。

観測不能なゲージ、予告、端数等を0で埋めない。現段階では必要な観測が不足する要求は拒否する。メモリ取得方法はブリッジ側で確定する必要がある。`moves_since_chain` は4連鎖以上の直後に0へ戻す建築手数で、ブリッジ側の観測履歴から管理する。

返答は `x`（0始まり）、`r`（U/R/D/L）、リンクごとの `link_points`、`next_field`、判断理由、決定を識別する試合・フレーム・ツモ・周期IDを含む。でかぷよの `r` は色添字で、`color` を併記する。ゲーム内の回転ボタン回数とは別で、実際の入力経路はブリッジが作る。

入力前に `authorize_reply(要求, 返答, 最新の観測)` を使う。時刻が進んでも両者の判断対象の状態が変わっていなければ使える。ツモ・盤面・予告・モード・試合等が変わった返答は捨てて再計画する。ポーズ・終了中の要求や混在フレームは拒否する。この検査を実機入力へ接続する作業は未実施。

## 現在の共通判断と残り

予告がある場合は、今の1手で消せる候補をキャラ別得点で評価し、相殺量・攻撃量・連鎖数から選ぶ。消去のない手では確定おじゃまが落ちても生存するかを確認する。建築には単独探索を使い、単独探索の配置が保守的な到達モデルに入らなければ代替する。全キャラで同じ処理・設定を使用する。`data/fever/battle_policy.json` に既存ブリッジの採用方針（狙い15、満杯付近13、余裕1段、46手から妥協）を固定した。対戦向けに調整済みの値という意味ではない。

相手の即時発火の可能性は表示するが確定攻撃と区別し、まだ判断への脅威評価に使用していない。攻撃到着の締切、見える複数手での対応、催促・潰し・本線の選択、実時間の打切り代替手は未実装。単独探索内部の通の得点による候補順位も残る。従ってT13の攻防判断は初期版で、完成扱いにはしない。

## 自己対戦と再生

```powershell
python -m fever_battle.simulate --characters raffina schezo --seed 1 --max-moves 80 --placement-frames 48 --link-frames 48 --output bin/t8-t13/example.json
python -m fever_battle.replay bin/t8-t13/example.json
```

48はこの例の任意の試作値で、実測した設置時間・連鎖時間ではない。配置と連鎖のフレーム値は必須指定。`data/fever/timing.json` は既存ブリッジの部分計測だけを記録し、対戦コストの既定値は未校正としてnullにした。平均や最小値から攻撃締切の上限を作らない。

ログに両者の配置決定、リンク別の送受、明示したイベント順、終状態を保存し、再生では全イベントの効果と終状態を照合する。色列はSteam版を再現しない `prototype_splitmix4`。相手のまだ表示されていない次手は判断に渡さない。

全消し後のタネは `--seeds` のJSONで採取済み盤面を指定できる（キャラID→14行盤面の配列）。足りなければ `awaiting_seed` で停止。保守的な候補に生存手がなければ `no_surviving_move` で停止し、その時点を実際の敗北とは呼ばない。`finished` は審判が盤面上の敗北を判定した場合。これらを実機の試合完走率や勝率に換算しない。

審判単体は `op: "referee"`、`characters`、`events` で任意の明示イベント列を再生できる。得点単体は `op: "score"`、`character`、`links` を指定する。詳細と確認状態は [FEVER_BATTLE_RULES.md](FEVER_BATTLE_RULES.md) を参照。

# 2026-10-05の追加実装

以下の旧「未実装」「未統合」のうち、確定おじゃまの見える複数手探索と、検証できた相手連鎖の開始時予測には着手した。完成・実機校正済みという意味ではない。

`fever_battle/search.cpp` の `garbage_search` は現在手とNEXT/NEXT2までの各候補へ、得点端数・リンクごとの相殺・確定化・1回最大30個の落下を状態遷移として適用する。おじゃまが乗った後の盤面で、後続の到達判定・消去・死亡と評価を計算する。中央列だけの危険判定へ限定しない。全消しで未知のタネが必要になったら架空の空盤面へ進めず探索を止める。

端数順は1→4→3→6→2→5。2026-10-05のユーザー指定に従い、カーソルを実際に落ちた個数だけ進め、前回最後の次から再開する。相殺で軽減された個数は進めない。古いWindows版の作者による[調査](https://www.ne.jp/asahi/root/inoue/p12_102.htm)の「落下1回につき1つずらす」とは区別し、後者をSteamで確認済みと推定しない。実機での連続端数の十分な照合は未完了。

ブリッジの実験対戦入口は、配置予定を確認できた相手の連鎖開始時に全リンクを解決し、キャラ別点数・未到達リンク・終了イベントを探索へ渡す。途中の相殺で相手の攻撃が減る場合も各リンクで処理する。読めなかった情報を0として合成せず、検証できない連鎖は判断を拒否する。現状はこれが操作停止に結び付く例があり、通常対戦の完成には至っていない。

盤面形状からちぎりと各リンクの落下距離・ぷよ数を算出する。時間仕様v1で0～9段の実測増分と10～13段の推定増分を適用し、列別の距離と量による連鎖時間を校正した。相手の時刻は1リンク±2フレームの実測誤差幅の早い側を使い、観測したリンク開始で合わせ直す。得点発生、連鎖終了、操作再開を分ける。詳細は [FEVER_TIMING.md](FEVER_TIMING.md)。

ユーザー指示により時間測定は対CPU・連鎖しばり・ゲージ加算0へ切り替え、ブリッジに `fever-measure` を追加した。単独構築AI・仮想パッド1つで実測し、通常対戦の不具合修正・T13受入れと分けて記録する。
