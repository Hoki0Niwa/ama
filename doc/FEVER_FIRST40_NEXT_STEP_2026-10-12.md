## 2. 多様性と原因について実際に分かったこと

[F40-1診断](FEVER_FIRST40_DIAGNOSTICS_2026-10-12.md) の98観測は、初回13/14で終わった23試行の92途中局面と、成功2試行の6局面である。無作為な98試行ではない。13終端群35/36、14終端群52/56、成功対照2/6でrootの子孫が縮小したが、局面の時期・盤面容量が異なるので、この差を失敗原因の割合にしない。

幾何15の脱落を詳細追跡した5観測の内訳は次の通り。

| 観測 | 実試行の結末 | 生存盤面と異なる脱落盤面数 | 仮の幾何盤面の時刻 | 同じ層に残った最大Lg |
| --- | --- | ---: | --- | --- |
| ラフィーナ31002・38手 | 初回13 | 10 | 44手 | 16 |
| ラフィーナ31014・24手 | 初回14 | 36 | 30〜31手 | 15〜16 |
| ラフィソル31006・32手 | 初回14 | 8 | 38手 | 15 |
| ラフィーナ31004・30手 | 初回15成功 | 101 | 36〜37手 | 15〜16 |
| ラフィソル31010・27手 | 初回15成功 | 6 | 31〜32手 | 15 |

全5観測で、B0は仮想列の実popとしても15を既に発見していた。未知色の仮想列上のpopは、実際の可視3手からの成功ではない。単色の仮鍵を足したLgも、合法Pieceで鍵を置ける証明ではない。発火口・連鎖尾の同一構造を継続追跡したものでもない。summaryは代表例の保存なので、上の5件を幾何15脱落の完全な発生率とは呼ばない。

したがって、「15候補が全て落ちて13/14しか残らなかった」という説明は、この5観測では支持されない。「残った15より、落ちた15の方が実ツモに頑健だった」という可能性は残るが、それを比較した継続実験は無い。**有害な候補消失は否定も証明もできていない。**

初回13/14の23件について、保存B0の終端とprefixを今回読み直した。

- 容量解除は23/23。`no_safe_stack` が16、`no_main_retaining_continuation` が7。後者は保持候補ゼロではなく、混雑・available_chain>2・improving==0の条件である。23件を超えた初回10〜14全29件では、従来報告どおり19/10になる。
- 途中に `expected_chain>=15` を一度以上返した13/14失敗は10/23（ラフィーナ8/14、ラフィソル2/9）。同じprefixで保存容量応答の `available_chain>=15` は0件。仮想予測と可視で実行できる連鎖の隔たりはあるが、校正された成功確率の誤差ではない。
- 終端での群消費は成功11件が平均4.47個/リンク、13/14の23件が4.80。群余剰は7.00対10.91個、消去後の残色は5.00対7.17個。空間の使い方との関連はある。5/6個消しへの強罰が悪化した既往実験を再提案する根拠にはならない。
- ラフィソル31020は26手・64個・現在QUADで生存する0〜2消去手が無い。残り14手があっても、その局面の合法な延長余地は期限だけでは増えない。

ここでsafeは、廃棄なし・消去0〜2・既存margin内という容量検査の条件を満たす手である。`no_safe_stack` を「ゲームの全合法手がゼロ」や「純粋な総セル容量不足」と読み替えない。1〜3連鎖の整理消しを許可するベンチの停止契約と、この局所safe判定の閾値も別である。

直接観測できたのは「安全な延長が局所検査で見つからず容量解除へ至る」こと。その状態を作った評価・構造、仮想色への依存、枝刈りの寄与を分離する反実仮想比較は未実施である。**容量という出口は強い証拠、評価とツモ不確実性は有力な説明仮説、50枠予約の必要性は未立証**と整理する。対戦戦術の上書きはこのB0実験に含まれない。

## 3. 期限処理が作用できる範囲を保存ログで確認

幅250・最大深さ8のまま、配置前の絶対手数をt、残りをr=40−tとすると、深さを短くするのはt≥33、すなわち**34手目から**。33手目ではt=32、深さ8の末端がちょうど40手になる。

`steps.jsonl` の `move` は今回置く手の1始まり番号。保存行の `placed_total` / `remaining` は実配置後なので、配置前の計算には **t=move−1、r=41−move** を使う。この1手差を実装へ持ち込まない。

| 保存B0の範囲 | ラフィーナ | ラフィソル | 合計 |
| --- | ---: | ---: | ---: |
| 全prefix判断数 | 810 | 825 | 1,635 |
| 33手目までの判断数 | 763 | 748 | 1,511 |
| 34〜40手の判断数 | 47 | 77 | 124 |
| 1本以上の実探索深度が40手を越える判断 | 42 | 70 | 112 |
| 可視容量候補の必要手数がrを越える判断 | 3 | 5 | 8 |
| 採用したfire計画の必要手数がrを越える判断 | 0 | 1 | 1 |
| 初回13/14で33手目までに終了 | 6/14 | 4/9 | 10/23 |
| 初回13/14で34手目以降に終了 | 8/14 | 5/9 | 13/23 |
| 全失敗のうち34手目以降まで継続 | 10/18 | 12/19 | 22/37 |

「40手を越える判断」は `any(t+d>40 for d in search_depths)` で数えた。探索した事実であり、期限後の価値が実際に選択を変えた証明ではない。同じ試行の複数手を独立な成功率標本には数えない。

具体例はラフィソル31002の40手目。B0は `fire=true, fire_moves=3, expected_chain=14` を返し、今の実消去は1連鎖だった。3手は現在手を含むため、計画上の14は42手目になる。ベンチは正しく40手未達で止めており、集計バグではない。探索・採用の目的がベンチの期限と揃っていない例である。ただし、期限内の代替15が存在した証拠ではない。

この実験には明確な限界がある。期限限定なら33手目までの配置は不変なので、**P15_first@30は改善しない**。既に33手目までに失敗した15試行も救えない。残る失敗を仮に全て救っても、この保存48試行での上限はラフィーナ16/24、ラフィソル17/24に過ぎない。これはこの標本での作用範囲の上界であり、予測成績ではない。

それでも先に一度試す理由は、実在する期限外計画を少ない変更で除けること、配置が変わる時期を厳密に予測できること、B2より結果の解釈が容易なことである。効果が無ければ早く停止できる。根本的な構築改善や80%の達成方法と位置付けない。

## 4. B2を保留する理由と再検討条件

50枠は探索幅の20%に当たる。旧案はroot、群余剰、残色、鍵、発火列、安全高さを同時に選別へ使い、どの要素が効いたかも分かれにくい。診断ONの追加potentialや全tuple出力を常用すると高コストになる。B2自体の費用を測ったわけではないが、既存診断をそのまま選別へ埋め込む設計にはしない。

現時点で5枠や10枠に縮めるだけの案も選ばない。必要なのは予約率の調整より、**失われた構造に実行可能性上の利点があるか**という証拠である。

将来B2を再検討するなら、期限内の候補を対象に、同じ観測・同じ継続条件で、落ちた候補の方が残った候補より合法な初回15へつながる例が再現することを先に求める。幾何Lg15、別board hash、root数増加だけでは十分ではない。この追加実験やB2実装を今回の次タスクへ足さない。

| 代替 | 今すぐ選ばない理由 |
| --- | --- |
| 既存6仮想列の支持数でrootを再順位付け | 安価な可能性はあるが、固定6列は独立な確率標本でなく、支持数を成功確率と扱えない。root順位変更の有効性は未測定 |
| 群余剰・安全高さの評価を強化 | 容量に直接関係するが、関連から適切な重みは決まらず、強罰の既往失敗がある |
| 連鎖尾・発火口の階層計画 | 構造面では有望だが、合法到達性・目標切替まで必要で、今回の最小工数に収まらない |

## 5. Sol High向け：唯一の実装タスク「B1期限限定」

### 5.1 対象とファイル境界

基準は上記研究ブランチ。既存 `LegacyBackend`、`Observation`、`NativeEnvironment`、`run_trial`、集計・provenanceを再利用する。新規研究ファイル案は以下。

- `fever_battle/first40_deadline_backend.py`：ON/OFFの研究backend。
- `tools/bench_fever_first40_deadline.py`：同一nativeでB0/B1期限限定を対応比較する専用入口。
- `test/test_fever_first40_deadline.py`：期限・非先読み・配置同値の検査。

最初はC++変更も再ビルドも不要。同じ研究用参照native `e0cc8f91d5edb7d851b9f1cd6cfce01de26f09f45178f72b491e0c0200365eda` を両条件で使う。環境も同じ参照native。製品search/fire/evaluation/capacity・共通コード・既存ModeBattleEngine・config・battle_policy・既定バイナリに変更を加えない。旧B0とF40-1の成果も保存する。

既存CLIの `--candidate` はnativeを替えるだけでLegacyBackendを使うので、この新しいPython方策を選べると誤認しない。専用CLIが2つのbackend factoryを既存 `run_trial` へ渡す。物理や停止判定を複製しない。大きな共通化を始めない。

### 5.2 入出力と唯一の介入

外側APIは `choose(Observation)` のまま。Observationは常に現在＋NEXT2の3Piece、絶対設置数t、実盤面、キャラ、周期index、観測した履歴。未来色と環境seedは入力しない。

```text
OFF:
    LegacyBackend.choose(observation)へそのまま委譲

ON:
    0 <= observation.placed_total < 40 を検査
    初回本線未発火（normal_chain_max < 10）を検査
    r = 40 - observation.placed_total
    D = min(8, r)
    V = min(3, r)

    LegacyBackendと同じown/requestを研究側で作る
    own.queue = observation.visibleの先頭V個のコピー
    solo_options.beam_depth = D
    既存 _normal_options(request, own) を呼ぶ
    既存 _solo_build(own, options) を呼ぶ
    従来と同じ返答 + 研究診断を返す
```

外側の観測や環境queueを短くしない。研究内部で実行できる範囲だけを切り出す。これにより同じ短いqueueを容量検査、可視発火、構築へ渡し、Python保持・延長採用も期限内の容量応答を参照する。soloだけを短縮し、容量応答やPython上書きに期限外の手順を残す実装は不可。

`beam_depth`だけの変更も不可。`fever/engine.cpp`はdepthをqueue長以上へclampし、`search_multi`も長い入力queueを自動短縮しない。残り1/2手では検索queueも1/2個にする。

| 配置前t | 今回の手 | r | D | 内部の可視queue長 |
| ---: | ---: | ---: | ---: | ---: |
| 32 | 33 | 8 | 8 | 3 |
| 33 | 34 | 7 | 7 | 3 |
| 37 | 38 | 3 | 3 | 3 |
| 38 | 39 | 2 | 2 | 2 |
| 39 | 40 | 1 | 1 | 1 |

仮想6列は既存生成器の同じprefixをDまで使う。追加サンプリング、支持数によるroot再順位付け、幅/重み/PRUNE_CHAIN/早期停止/next_roomの独自変更はしない。最後の1手でqueue長1となり、期限後のNEXTに対するnext_room検査が行われなくなる差は、この介入に含めて記録する。

margin1とB0既存の「margin内の候補が無い場合」の救済経路をそのまま使う。期限を理由に新たなmargin緩和、13/14の発火禁止、強制15優先の別ランキングを入れない。合法fallbackはB0既存経路を再利用し、失敗をnomoveや未発火から除外しない。

キャッシュは少なくとも絶対t、キャラ/位相、内部queue、D、ON/OFF、既存評価条件を区別する。同じ盤面や整理後にtを巻き戻さない。`moves_since_chain`をrの代用にしない。既存キャッシュはown.piece_id=tとoptions等を含むが、研究側でこの前提を明示して検査する。

**この限定版は旧B1の全機能を完成させるものではない。** 静的potentialの仮鍵に必要な実手数を推定する新評価、探索木全体への新しい初回吸収状態、質量slackによる枝刈りは導入しない。非rootの実5以上枝刈りとrootの従来の扱いも変えない。有限期限を明示的な探索・可視計画へ反映する実験であり、全葉が期限内の初回完成確率を表すとは主張しない。実試行の初回10以上での吸収終了は既存ベンチが厳密に担う。

### 5.3 必須のログ

既存の実配置・実links・停止理由・費用に、研究sidecarとして以下を加える。保存JSONLの配置後tと混同しない名前にする。

- `placed_before`, `remaining_before`, `deadline_enabled`, `requested_depth`, `effective_depth_limit`, `visible_count_observed=3`, `visible_count_searched`。
- nativeへのsolo/normal_capacityそれぞれのqueue長・depth、返却 `search_virtual_depths`、`fire_moves`、容量のavailable_moves/chain・safe/retaining/improving/release/reason。
- solo提案、Python保持/延長上書き後、実配置の区別。B0との同一観測比較で最初に変わった手・変更段階。
- 明示的な範囲違反件数：`t+completed_depth>40`、`fire=true && fire_moves>r`、`available_moves>r`。ONでいずれも0を要求する。

全ノードのF40-1診断は通常の費用比較ではOFFにし、observer無しの参照nativeを用いる。必要な固定局面の説明だけ既存の診断で補い、その費用を分ける。未知色に対する成功確率や有益な構造消失率を、これらのカウンタから推定しない。

### 5.4 検証の順序

1. **境界と同値**：OFFがLegacyへ直接委譲すること、ONのt=32/33/37/38/39、t=40拒否、既発火観測拒否、整理消しでも絶対t維持、全4形状・BIG選色を検査。内部queueを短くしても周期の最初のindexは進めない。
2. **情報制約と実応答**：同じ観測のまま環境seed/隠れた未来を変えても配置一致。nativeの実探索深度と発火/容量計画がr以下。40手で15は成功、41手の計画は成功でない。最初の10〜14で必ず終了する既存13意味的テストを再利用。
3. **既知4試行の回帰**：seed31004/31010を両キャラでOFFとB0照合。ONも実行するが、34手以降の差は新しい結果として保存し、無理に一致させない。
4. **既知24seed/キャラのB0対ON**：空盤面から対応実行。最初に変化可能な手は34手目なので、ONの33手目までの1511配置が旧prefixと一致することを確認。短縮で作用しなかったケースも全て分母へ入れる。
5. **有望な場合だけ追加開発40seed/キャラ**：履歴を確認し、結果を見る前にseed一覧と条件をmanifestへ固定する。下記の開発判定を満たさなければこの追加には進まず停止する。200以上の最終評価や製品統合はこのタスクで開始しない。

実装後は既存Tsu protocol8件と同seed1/2のbench非時間列も確認する。B0/F40-1既存検査の再利用を優先し、物理モデルを模した別テスト実装を増やさない。

### 5.5 比較条件、合格と停止

幅250、最大深さ8、仮想6列、同一CPU/6threads、逐次実行、margin1、試作色モデル、同一native/DLL/configを固定する。B0とONの実行順をseed単位で交互にする。絶対40手とCPU時間上限を混同しない。

今回は既存B0と同じ総wall打切り無しで比較する。Dの短縮は実験対象の差そのもの。250ms強制キャンセルの導入は別の大きな介入なので含めない。choose平均/P95/max、超過率、各試行総CPU・wall、processメモリを測り、実用250ms以内の保証とは呼ばない。終盤124保存観測での対応時間も測り、早期失敗による平均時間の見かけの低下を区別する。

| 判定 | 事前に固定する扱い |
| --- | --- |
| 実装の必須条件 | OFF同値、ONの33手まで同値、未来漏洩なし、明示的な期限違反0、停止/全試行分母/物理不変、ハッシュ一致。いずれか失敗なら性能判定前に修正 |
| 既知24seedで次へ進める条件 | P40のgain>loss、両キャラともnet非負、既存の成功11試行を失わず、死亡/配置不能を増やさない。@30は必ず同じ。満たさなければ追加40seedへ進まず、性能改善案として停止 |
| 追加40seedでも確認する条件 | 同じ固定条件でgain>loss、各キャラnet非負。@30不変、P35・初回P13/P14・死亡/配置不能の悪化を併記し、観測上悪化があれば継続採用を保留。P95/maxが対応B0より10%以上増えるなら原因を調べ、実用候補への昇格を保留 |
| gain=loss、特に配置差0 | 期限整合は検証できてもP40改善は未確認。時間減だけを構築改善として採用しない。深さ係数・quotaの追加調整へ進まない |
| 有望な結果 | 各キャラの分母・Wilson区間、対応gain/loss・差を提出する。追加群も開発データ。安定化・80%達成・製品採用は宣言しない |

この小実験で+10ptを必須としないのは、作用範囲を終盤に限定したため。少数の正のgainを統計的な優越証明へ格上げしない。最終的な方式採用は、凍結版と同じ実時間予算での未使用評価が必要で、その開始は別判断とする。

### 5.6 提出物と工数

提出は新規研究adapter/専用比較CLI/テスト、既存B0との対応結果、差が出た全seedの最初の変更箇所、費用表、manifest、ソース・設定・native/DLLのSHA256、短い診断レポート。出力は未使用の `data/fever/baselines/…-f40-deadline/` へ保存し、過去データを上書きしない。

Python研究方策のソースと、再利用nativeを生成した凍結ソース/build manifestは別々に特定する。新しいPythonをnativeのコンパイル時ソースに含まれていたと記録しない。F40-1のobserver付きOFFバイナリを速度対照へ混ぜない。

工数の目安は実装0.5〜1人日、境界/回帰/対応測定と報告1〜2人日、計1.5〜3人日。CPUのみ、GPU・学習・大きな新規探索器は不要。実装者・環境に依存する見積もりであり、性能向上の保証ではない。結果を提出したところで停止し、B2や次の評価改造へ自動で進まない。

import json
from pathlib import Path
p = Path('data/fever/baselines/2026-10-12-f40-diagnostics/b0-commit')

for ch in ('raffina', 'rafisol'):
    ss = [s for s in steps if s['character'] == ch]
    late = [s for s in ss if s['move'] >= 34]
    crossed = [s for s in ss if any(s['move'] - 1 + d > 40 for d in (s.get('search_depths') or []))]
    fire_over = [s for s in ss if s.get('fire') and (s.get('fire_moves') or 0) > 41 - s['move']]
    cap_over = [s for s in ss if (s.get('capacity') or {}).get('available_moves', 0) > 41 - s['move']]
    failed = [r for r in runs if r['character'] == ch and r['first_main_chain'] in (13, 14)]
    print(ch, len(ss), len(late), len(crossed), len(fire_over), len(cap_over),
