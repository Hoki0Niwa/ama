# 実機の起動・判断・入力

AIはAma、メモリ読取・仮想パッド・入力実行・判断要求のスケジュールは `C:/Users/ho_ki/git/ama-memory-bridge` が担当する。

## 起動

Ama側で対戦バイナリと操作DLLをビルドする。

```powershell
./build.ps1 -Target fever_battle
```

ブリッジのランチャーで **AI同士の対戦（フィーバー）** を選び、2席のパッド割当・ゲーム側ゲージ設定・フォーカスを確認する。CLIはブリッジ側で実行する。

```powershell
python control.py session --mode fever-battle --backend hidmaestro --execute
```

`--execute` 省略は入力なし。F6は両AIのオン／オフ、F9は停止、Ctrl+F9は終了。`fever-duel` は単独構築AIを測る別モード。バイナリ・Python・設定の変更を稼働セッションへ反映するには再起動する。

## 探索と入力の所有権

ブリッジは、通常判断・次手の準備・おじゃま着地予測・緊急防御を別々の常駐エンジン経路へ送る。各要求は所有者のスレッドで確定し、裏スレッドでは要求の複製と計算だけを行う。完成結果を入力側へ公開するのは所有者だけとし、着地予測が通常判断の完成キャッシュを取り去ることを禁止する。着地予測は指定幅・深さの1回の探索とし、浅い予備探索と後からの上書きを行わない。

完成判断は盤面・現在手・モード世代・タネと結び付けて保管する。最初の非ゼロ入力で判断全体と実際の等価配置を固定し、キーを離しても失効させない。入力のないレシピ待ちを「入力済み」と見なさない。準備結果の大きな複製は裏スレッドで行い、公開・入力開始・再利用の経路では完成した値の所有権を引き渡す。将来の準備が入力中の配置を差し替えてはいけない。

不要になった着地予測・別局面の判断は、経路ごとのWindowsイベントで中止する。Pythonのnative要求境界と通常ビーム・タネビーム・戦術木の探索境界で検査し、中止はエラーとして返す。途中結果を配置判断として公開しない。有効な探索を経過時間だけで中止して浅い探索へ替えるためには使わない。

Amaは1回のprotocol 3要求内で、完全に同一のnative要求を再利用する。盤面・ツモ・幅・深さ・得点設定などをすべてキーに含め、設定変更は再利用の境界とする。中断結果・エラーは保管せず、要求をまたぐ新しい共有キャッシュは導入しない。

パッドのAI・手動入力・更新・解放は、合成マスクの算出からデバイス書き込みまで同じロックで直列化する。対戦ログのファイル・コンソール出力は専用スレッドへ渡し、入力スレッドでI/O完了を待たない。キュー溢れは破棄数を記録する。OSのスケジューリング・機器の遅延・メモリを読めない時間まで解消する保証ではなく、実機受入れは別に行う。

## 事前判断と読むツモ数

同色2個組の等価配置は、入力開始前の出現姿勢または現在の観測姿勢から推定設置時間を最優先に選ぶ。先行入力を始めた実配置は出現後も保持し、現在姿勢から別の等価配置を選び直さない。落下中に反転して早く設置できるなら回転を使い、入力数は設置時間が同じ場合の比較にだけ使う。実測レシピも、回転数が少ないという理由だけで別の経路へ差し替えない。実行姿勢がAIの表記と異なる等価配置はログの `placed_as` に残す。

先行入力は固定盤面・現在手・モード世代・タネを検査する。盤面が同じなのに遅れた予告の表示数だけでキーを解除せず、新規攻撃への安全性は準備再利用と入力承認の経路で検査する。通常接近の予測はFeverの自然落下速度10/256と2個組の1/4セルの衝突境界を使い、移動と回転を安全に並行できる経路を過剰に拒否しない。これらの検査にAI探索は追加しない。

完成済みの判断が同じ盤面・現在手・既知ツモ・予告・戦術設定・攻撃・期限をカバーする場合、停止盤面やおじゃま着地からの追加準備を起動しない。キュー切替中の一時的な短い観測では、完成判断の既知の尾を捨てず、出現時に全ツモの一致を検査する。エンジンもobserved準備で明示されたツモを切り詰めず、同じ条件の完成判断を再利用する。条件と比較結果は [事前判断の探索条件](FEVER_PREPARATION_QUALITY.md) を参照。

GUIの先読みオン／オフ項目は両AI・全モードから削除した。保存済み設定の旧項目は無視し、GUIから事前判断を無効化する起動引数は生成しない。

protocol 3のPython入口とnative workerを使う。対戦構築はworker内の `op=solo`。配置判断後に、既知の次盤面と残りの既知ツモで次の手を事前判断する。盤面・ツモ・世代が一致すれば構築探索または完成した判断を再利用し、先行入力も使う。連鎖や相手の着地で次盤面が確定しない場合は構築探索だけを準備し、出現後に戦術を確認する。連鎖後・タネ交換後は観測できた停止盤面とツモで準備する。

次に出現するツモは「読むツモ数」ぶん（現在手を含む）を見て判断するので、事前判断も同じ数で探索する。配置後の事前判断は、既知のツモに、ゲームの3スロットより先を色表と形状周期から読んで足し、現在手を除いた読むツモ数にそろえる（既定3なら、置いているツモのNEXT3まで）。自分の通常盤面の連鎖を撃つ手の次も、連鎖後の盤面・相殺後に残る確定分の落下（端数列はカーソルで既知）・次のツモを予測して、置いている間に完成した判断（戦術を含む）まで準備する。相手の連鎖・レート変化・相手Feverが絡む場合と、落下列が不明な場合は構築探索だけを準備し、出現後に戦術を判断する。署名が一致しない盤面では再利用しない。次盤面を予測して置いている間に行う通常構築は、直前の計算時間にかかわらず指定幅を維持する。着地後の観測など、出現までの時間が短い `cold_spawn` と出現後の緊急計算では、完成済みの指定幅の構築を先に探し、なければ幅50以下で計算する。タネ探索は絞らない。停止盤面に既に落ちたおじゃまは、もう一度落とさない（二重に落として「落下で死ぬ」と誤予測し、準備しなかった。2026-10-21〜23のログの63件中25件は、その後にツモが出て続行した）。どの配置も負ける局面の最速の締め（`no_rescue_fast_finish`）も、準備して出現時に再利用する（おじゃま着地後の次の手の多くがこれで、出現後に探索し直すと平均72ms、最大268ms待っていた）。連鎖後・おじゃま着地後・タネ交換後に停止盤面から行う事前判断も同じく、その盤面の次のツモが出現時に見る数までを色表で補う。色表で特定できなければ仮定で補わず、見えているツモだけで準備する（出現時に数が合わなければ捨てて判断し直す）。1〜2ツモの設定は、次のツモが出現時に見る数（1〜2）で準備する。beam探索内の仮想列は別の機能として維持する。

ランチャーの「読み込むツモの数」とCLIの `--queue-depth`（2席目は `--ai2-queue-depth`）は現在手を含む1〜12。既定3は現在手・NEXT・NEXT2。1〜3は表示キューを指定数へ絞り、4〜12は判断時に色表と形状周期から明示指定分を読む。追加分を特定できないときは仮定で補わず再観測する。事前判断はこの要求に入った既知ツモだけを引き継ぎ、次の要求では準備に使った全ツモの一致を確認する。停止盤面の準備では、その時点で実際に観測できたツモだけを使う。探索幅・深さは別設定。

連鎖後・おじゃま着地後・タネ交換後に停止盤面から行う事前判断（出現の十数フレーム前）の通常構築は、`cold_spawn` で幅50に絞る。Feverのタネ探索は、どの場面でも絞らず、設定の幅で行う。新しいタネ（突入時とFeverの連鎖後）は、落下の演出中（盤面処理段階5）に、描画セル表のセルが7フレーム増えなくなった時点で全体が揃ったとみなし、セルを列ごとに下へ詰めた盤面で、最初のツモの事前判断を始める（ブリッジの `Context.seed_drop`）。2026-10-16/17の実機記録の79回のタネ落下で、詰めた盤面は固定後の盤面と全て一致し、セルは5フレーム以内の間隔で入り、全体が揃ってからツモが操作可能になるまで29〜40フレーム、この待ちの後でも22〜36フレーム（中央値26）あった。要求の `spawn_in_frames`（22）は、Fever時計から差し引く出現までのフレーム数で、停止盤面からの準備の14に代わる。出現後に探索を始める場合より400〜600ms早く始まる。準備した配置が観測した盤面で届かない場合の再探索（`recover_placement`）は、通常構築の幅を50に絞る。タネ探索は設定の幅のままにする。自分の盤面・ツモ・世代を判断の前後で照合し、相手だけの表示変化で現在手の判断を取り消さない。実盤面・確定落下・Fever時計・攻撃期限は検査する。

突入・タネ交換・復帰で盤面が変わるのは正常な交換として扱い、前の通常盤面との不一致を理由に救済探索を始めない。前の手の予測盤面を照合するのは、同じモード世代・タネで、直後の非消去手に限る。経路失敗のフラグも同じ手にだけ保持し、新しい手へ持ち越さない。これにより、準備中の新しいタネ判断を待つ経路を誤って飛ばし、2本目のタネ探索を待つことを防ぐ。探索そのものが出現に間に合わない場合の待機までなくなる保証はない。

入力開始済みの記録は、現在保持しているキーと別に保管する。 実観測の幾何から到達不能と確定した配置は `RouteUnavailable` として失効させ、古い完成判断・早期判断を再採用せず専用の防御再判断へ進む。同じ失効済み配置を待ち時間だけ増やして再実行しない。一時的な読み取り中断・相手の表示更新では配置を保持する。観測の切替でキーを離しても記録を消さず、同じ手を再決定しない。先行入力を開始した手は、同じ盤面・現在手・モード世代・タネなら、後から完成した準備や相手の表示変化で配置先を更新しない。準備側の応答も元のものを保持する。固定盤面や現在手が変わった場合は入力を止め、観測に基づく再判定を行う。新規予告で非消去手の安全根拠が失われた場合も入力を止め、現在位置から到達可能な配置だけで防御を判断する。 この `recover_placement` は専用の初期化済みエンジンへ送り、通常の判断パイプの処理待ちに並べない。完成済みの構築情報も渡す。到達検査の落下一段の余裕を2個組にも適用する。2個組の衝突原点と、落下の安全余裕を判定する行を区別する。通常2個組の移動はSteamの1/4セルの重なり境界に合わせ、衝突原点を `floor(y - 0.25) + 1` とする。落下・高速落下の余裕は従来のceilで検査する。回復候補は現在位置と落下余裕の双方で到達可能なものに限り、操作列の一致は要求しない。14段目のクリアランスは保守的なままにする。通常移動の期待位置には観測した端数を残し、整数高さへの持ち上げ完了と混同しない。観測位置が離散的な衝突原点より下にあり、最初から想定以上の持ち上げ量を必要とする経路は採用しない。原点より上にある出現位置−0.5などの持ち上げは一律に拒否しない。

準備応答の `incoming_projection` は既知攻撃の識別と全残量を持つ。予測済みの得点リンクがトレーへ移っただけで、同じ攻撃・総量の範囲内・着弾期限前なら準備を保持する。新規の攻撃、予測量の超過、確認済み予告への変化や着弾期限は再検査する。

入力をまだ始めていない場合、自分が通常盤面で本当に新しい予告が増えた場合は、非消去の完成判断をそのまま実行せず、完成済み構築を残して防御を更新する。準備済みの潰しも、双方通常・双方予告なし・飛行物体なしの条件を入力直前に再確認し、相手の発火・突入では本線へ戻る。

相手のゲージ増加だけでは、同じ自分の盤面・現在手・種の完成準備を破棄しない。自分がFever中なら相手モードの変更でも入力先を保持する。通常発火の `offset_timing` があれば、入力直前に最新の予告・飛行中相殺物体とフレームで待ちだけを更新する。自由落下による相殺待ちは、本線が既知の攻撃総量を超えて返せる場合、または明示設定・観測からマージン開始を確認できた場合に限る。弱い本線で突入を待つ代わりに、相手の連鎖終了前に着地・おじゃま確認が済む間は完成済みの通常構築で伸ばす。追加の配置探索・worker通信はしない。planningログの `gauge_wait` と、待ちを適用した後の実DOWNフレームを用いて確認する。

## 操作の実行

実測・移植済み入力プログラムは、観測フレームを入力とする `ProgramCursor` で進め、同じボタン状態の再送を増やさない。必要な解放／押下のフレームを見逃した場合は複数のエッジをまとめて送らず、解放を観測した後、同じ配置目標へ現在姿勢から操作を継続する。時刻を逃したことだけを理由に現在列へ落とさない。出現時の判断待ちが上限に達した場合も、現在位置から到達可能な候補による専用防御へ進む。

操作DLLの現在位置からの経路を使い、入力の各結果を観測する。高段回転はDOWNを離して行う。限定された2個組壁越え終端の同時入力は [操作API](../docs/OPERATIONS.md) に従う。

経路開始前に盤面・可視ツモ・世代を照合し、経路中は自分の設置番号・モード・処理段階・期限を確認する。同じ組ぷよを操作する間は相手の表示変化だけで経路を止めない。設置・連鎖・落下・タネ交換・終了で入力を離す。経路不一致では実姿勢と到達先を確認し、観測の高さを緩めて成功扱いしない。

特殊形状の切替直後は、新しいPieceと前の固定位置の座標が一時的に混在し得る。操作可能な現在Pieceの観測を待つ。`wait`・演出・結果画面では入力しない。終了時は入力を離してworkerと子プロセスを閉じる。

## 状態と診断

`garbage_phase` や途中接続で不足した履歴を推定しない。不明端数列はエンジンで評価し、実落下後に再観測する。相手の連鎖中は最後の直接観測固定盤面へ元フレームと状態を添え、今発火できる盤面と誤認しない。

ログは `planning`、`locked`、`fire`、`seed decision`、`surprise landing`、承認拒否理由を照合する。`search_reused` と `normal_build_search_reused` を分けて記録する。`locked` の `frames` は、判断時・操作開始時・最初のキー・最初のDOWN（自由落下の長さ）のゲームフレームと、操作開始時の最上段の行（`start_y`）を記録する。`wait_ms` は現在手の観測から判断採用まで、`search_ms` はエンジン内の判断時間を表す。観測の制約は [FEVER_MODE_OBSERVATION.md](FEVER_MODE_OBSERVATION.md)、確認範囲は [VALIDATION.md](VALIDATION.md)。

症状の局所再現は [DEBUGGING.md](DEBUGGING.md)。判断要求・`match seed`・`seed config`・`arrival` の時刻診断を保存し、再走は症状シードへ限定できる。3個組は [測定済み許可](DISABLED_TRIPLE_OPERATIONS.md) の対象だけを持ち上げる。

横移動と回転の連打は、直前の押下時刻だけで次の押下を決めない。キーを実際に離す指示を出したフレーム・時刻を保持し、観測が飛んだ場合も解放を挟んでから次を押す。観測抜けで連打を長押しへ変えてしまい、オートリピートまで横移動が停止する経路を防ぐ。
