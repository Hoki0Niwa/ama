## 2026-10-06 実対戦による再調査・訂正

前回の自動テストだけでは実機の問題を解消できていなかった。入力を追加せずユーザーの対戦を採取し、次の原因を確認した。

- 描画コード `0x16` は落下中専用ではなく、通常おじゃま4個の2×2表示。ゲームのRVA `0x46250` は4セルのコード6を照合して22へ変更している。これを拒否したため、操作可能な115フレームにわたり固定盤面が取得できなかった。6と22を同じおじゃまとして読み、フェーズ・上端・浮いた列の検査は維持する。
- DOWN送信直前の再読取で設置番号が1進んだ場合、正常な設置完了として解除する。旧処理は経路異常として再試行した。修正前の1試合に8回あり、修正後の複数試合では再発0。
- タネ探索中は相手の落下得点の剰余まで厳密比較し、1手で6〜9回返答を破棄していた。自分への予告・短い時計・明示戦術だけで方針が決まる場合は自分の情報を、他の場合は相手の戦術参照情報だけを比較する。自分の盤面・予告・世代・期限の検査は維持する。
- 特殊形状の切替では、ツモとセル数が先に変わり、先頭セルの座標だけ前の設置位置に残る。セル数一致を必須にしていた旧座標判定を修正し、両形状に共通する先頭セルで出現を確認する。修正後ログに残った到達不能9回のうち、採取できた形状切替時の例を回帰テストへ追加した。

読取・設置完了・タネ承認の3修正後は、ログで通常／Feverの設置・発火252件、致命的例外0。着地した22の盤面を9サンプル取得し、AI2は695個の予告から30個を受けた後にも次の判断・高速落下・設置を行った。異なる試合なので単純な率の比較や最短性の保証はしない。形状切替の追加修正後の実機確認は別記録へ追記する。

## 起動

Ama側で `./build.ps1 -Target fever_battle` を実行する。操作用は `bin/fever_battle/fever_battle.exe`、単独構築用は引き続き `bin/fever/fever.exe`。Tsuバイナリは使わない。

ブリッジのランチャーを再起動し、プリセット **フィーバー対戦（突入・タネ対応／試作）** を選ぶ。2つの仮想パッドに2人対戦の席を割り当て、ゲーム側のフィーバーゲージ増加を有効にする。設定値は観測から渡す。既存の `fever-duel` はゲージ増加0で単独構築AIを測定する別モードとして維持する。

CLIはブリッジ側で次のように起動する。

```powershell
python control.py session --mode fever-battle --backend hidmaestro --execute
```

`--execute` を省くと入力しない。現在手・NEXT・NEXT2だけを読む。2026-10-06の修正で、両AIの先読み・先行入力を有効にした。ランチャーと対戦セッションを再起動し、同プリセットを選び直す。F6は両AIのオン／オフ、F9は両AIの停止、Ctrl+F9は終了。2席の割当・進む試合時計・ゲームへのフォーカスを確認してから入力する。CPUの固定盤面はまだ未校正なので、この入口はAI同士の2人対戦用。

## 接続の動作

- 新規 `fever_mode_play.Session` が独立した実行ループでprotocol 3を使う。探索は別スレッドで行い、観測を続ける。通常では攻防エンジン、フィーバーではタネソルバーへ切り替える。通常探索の既定は幅50・深さ8。対戦プリセットは両AIに50×8・先読みオンを明示する。ユーザーの明示設定は優先する。先読みオフの場合は出現後に可視3ツモで探索するため、その間は自由落下する。
- `wait`、演出、タネ読込中、結果画面では入力しない。思考終了後に両者を読み直し、`authorize_mode_reply` で盤面・ツモ・世代・予告・時計を照合する。鮮明な同じ固定盤面の採取時刻が進むだけなら許可する。
- 経路開始前に盤面・可視ツモ・世代を照合する。経路中は両席の同一性・実行中状態と、自分の設置番号・モード・盤面処理フェーズ・期限を非ゼロ入力直前に読み直す。相手のツモ・演出は自分の経路を打ち切らない。同じ組ぷよの操作フェーズ中だけ操作を継続し、接地後も設置番号が進むまでDOWNを保持する。設置・連鎖・おじゃま・タネ切替・試合終了では入力を離す。通常時に次の盤面・配置を準備し、実盤面と一致した場合だけ出現前からのキー保持を引き継ぐ。
- 相手が連鎖・設置中なら、同じモード世代で最後に直接読んだ固定盤面を、元フレームと `last_observed_fixed` の状態付きで渡す。相手がいま発火可能な盤面として扱わない。モード切替ではキャッシュを捨て、新盤面が読めるまで待つ。相手の連鎖途中の配送予測は今後の強化対象。
- 終了時は入力を離してからワーカーを閉じる。PythonワーカーにはEOFを送り、内部のnative／solo子プロセスも終了させる。通常は3プロセス×2席で、Tsuのワーカーとは別系統。

## 通常時の先読み・先行入力（2026-10-06）

非消去・予告なしの手では、現在の操作が目標へ達した時点で `prepare_normal` を送る。現在手の遷移後盤面と、NEXT1・2の2ツモだけを使って次の構築を準備する。消去・ゲージ満タン・予告・相手の配送予測があれば準備しない。新しい未知のツモは補わない。

準備返答の `plan` は試合、次の設置番号・周期位置、モード／タネ世代、盤面、既知2ツモと配置を持つ。通常時の固定直後に、操作オブジェクトがまだ指す固定済みぷよも残した描画盤面 `resting_field` と照合する。一致すれば横・経路で許可された高速落下を保持し、可視ツモが更新した出現直前に回転を押す。出現後は操作中セルを除いた実盤面を照合する。ツモ・落下フラグだけ更新し、座標が前の固定位置に残る1フレームでは判断しない。

実際の `think` は改めて両者の最新観測を受ける。自分の試合・設置番号・周期位置・世代・盤面・既知2ツモ・探索設定が一致し、予告／配送予測がなければ構築結果だけ再利用する。新しい3つ目の可視ツモはこの再利用探索には使わず、`searched_visible: 2` と明示する。nativeの配置・得点・最新の判断IDは再計算し、入力は従来の事前承認を通す。同じ配置に限り保持したキーを引き継ぐ。

読取失敗、試合・盤面・世代・予告の変化、休止・フォーカス喪失、判断保留／承認拒否では解除する。消去後やフィーバー突入・タネ交換を跨いだ先行入力は行わない。明示的な `--no-prefetch`・`--no-preinput` とAI 2の同等CLIは維持する。操作用の観測は診断用シミュレータ・全色コードの重複読取を省く。

記録済み通常8要求の時間測定と、選択した非消去配置に続く可視2ツモの合成次状態での再利用確認を [速度記録](../data/fever/baselines/2026-10-06-mode-latency.json) に保存した。Tsu benchとの同時実行時、探索既定の変更で平均450ms→93ms、準備済みの次の返答は平均4.1ms（最大4.9ms）。単独での予備測定は307ms→57msで、負荷によって変動する。これらは実機の入力・配置成功時間ではない。

## 2026-10-06 追記：相手を待たない承認と、両モード共通の準備（`prepare`／`prepare_observed`）

上の「接続の動作」「通常時の先読み・先行入力」「未知のおじゃま履歴」のうち、次の点を改めた。実機ログと記録の再生による根拠はブリッジの `FEVER.md`（同日の節）。

- **承認は相手側を照合しない。**`authorize_mode_reply` は自分の盤面・ツモ・届いた予告・モード・タネ・時計と、共通の試合・ルールだけを照合する。`decision_dependencies` は返答に残るが、承認では使わない。相手の変化は次の判断で読む。
- **相手が読めない間も判断する。**ブリッジは、相手を今の採取から記述できないとき（NEXTの繰り上がり、モード切替、タネの読込）、最後に完全に読めた相手の状態をまるごと `last_observed_fixed` で渡す。「モード切替ではキャッシュを捨て、新盤面が読めるまで待つ」は廃止（古いモードの盤面を新しいモードの盤面として渡さない、という点は維持）。
- **準備は両モードで1本。**フィーバーは通常時の動作を継承し、違いは例外として書く。
  - `prepare`（`prepare_normal` は別名）：`placement` に現在手のx・r。消去せず、確定予告がなく、可視3ツモがあるとき、置いた後の状態で **`think` と同じ判断**を行い、返答ごと保持する。通常の例外：ゲージ満タンなら準備しない。フィーバーの例外：時計を1手の見積もり（設置14＋出現28フレーム）だけ進める。
  - `prepare_observed`：`self` が次のツモの状態そのもの（ツモの間に止まっている盤面と、見えている2ツモ）。連鎖・おじゃま着地・タネ交換の後に使う。フィーバーでは時計を14フレーム進める。
  - 次の `think` は、自分の状態（`_signature`：試合・設置番号・周期位置・モード／タネ世代・盤面・先頭2ツモ・ゲージ・予告・探索設定など。毎フレーム変わる採取時刻・端数・時計は除く）が準備時と同じなら、保持した返答を新しい判断IDで返す（`search_reused: true`、`searched_visible: 2`、従来の `normal_search_reused`／`seed_search_reused` も付く）。フィーバーの例外：飛来中・通常側に保留中の予告は照合しない。残り300フレーム以下では時計の進みすぎ30フレームまで。期限（`input_required_frames`）は常に観測した時計で判定する。1回使うか、別の `think`・`recover_placement` が来れば捨てる。
  - 返答の `plan` は `mode` と、判断が前提にした予告 `nuisance`（フィーバーは確定分だけ）を持つ。
- フィーバーの `think` から、使っていなかった相手の現在手の全配置・得点計算（`enemy_possible_score_now`）を除いた。
- **タネ探索（native）**：ノードごとのJSON組み立てをやめ、返す手順だけJSONにする。`potential` の配置列挙は色ごとではなく1回。実機局面133要求で打ち切りなしの出力が変更前と完全一致、3ツモの探索は中央値43→10ミリ秒、50ミリ秒予算での打ち切り31件→0件。`./build.ps1 -Target fever_battle` で再ビルド済み（以前のものは `bin/fever_battle/fever_battle-prev.exe`）。
