# 実装計画

## 目標と現在地

Steam版Feverで、通常盤面の大連鎖を繰り返し構築し、相殺・突入・タネ消化・復帰を含む対戦判断を行う。通常本線は13〜14連鎖の安定を目標とし、15連鎖を実機の必須受入れ条件にはしない。実装の詳細は [対戦エンジン](FEVER_MODE_ENGINE.md) に置く。

| 範囲 | 状態 | 残る受入れ |
| --- | --- | --- |
| 形状・周期・配置・単独探索（段階A、T0〜T7） | 全26キャラの基盤を実装 | 色列は試作用。全キャラの入力・上端条件の網羅確認は未完了 |
| 得点・相殺・通常対戦・時間（T8〜T13） | API・自動検証・部分的な実測あり | 倍率、配送、端数、全消し境界の実機校正と総合受入れ |
| ゲージ・時計・タネ探索（T14） | protocol 3で実装 | 特殊ツモのタネ消化、終了境界、戦術の実戦効果 |
| 実機接続（T15） | 2席操作、事前判断と1〜12ツモ設定、完成判断の所有権・裏探索の分離／中止、パッド書き込みの直列化と非同期ログを実装 | 2Pの8〜9手目、観測フレーム欠落・機器遅延を含む実機での入力継続、勝率と時刻予測の受入れ |
| 全26キャラの総合評価（T16） | 未完了 | 全キャラ、被弾・全消し・復帰・死亡を含む受入れ |

## 作戦選択の受入れ

作戦追加は共通設定からの差分登録に統一し、全消し・防御・本線／セカンド・Fever判断の入口を共有する。未登録の作戦名を仮登録して共通判断を継承する回帰検査を持つ。作戦名による共通処理全体の省略は追加しない。

ランチャーの各席で大連鎖・乱戦・ハイブリッドを選択できる。本線・セカンドの通常構築と序盤の全消し判断を3作戦で共有し、全消しの優先度を乱戦＞ハイブリッド＞大連鎖とする。双方通常・予告なしの中盤から育った本線を保持する潰しを回数制限なく比較し、相手の発火・Fever突入では本線へ戻る。送信・残存資源の下限と予告受け入れ上限を設ける。潰し後に2個までの起爆で5連鎖を維持し、本線の消費を1リンク以内に抑え、残存色ぷよが少ないほど許す攻撃を短くする。送信下限は維持する。同じ探索枠でNEXT2までの準備手を比較する。先行入力開始後は同じ盤面・手の目標を固定し、キー解放後も入力開始の記録を維持する。予測済み連鎖のトレー更新を新規攻撃と誤認しない。端数位置の通常移動を1/4セルの衝突境界で判定し、現在位置と落下余裕の両方で有効な回復候補を使う。本当に到達不能と分かった確定手は失効させて防御へ戻す。同色ぷよは設置時間を最優先に等価配置を選び、落下中の反転も使う。実測レシピを回転数だけで差し替えない。通常接近はFeverの自然落下速度と1/4セル境界で予測し、正当な出現時の持ち上げを誤って拒否しない。盤面が同じなら予告の表示数だけで保持中のキーを解除しない。推定ペースの更新だけで完成判断を破棄せず、同じ手の計測を二重計上しない。予測準備は前回の計算時間で探索幅を落とさない。記録局面の判断時間と準備再利用を確認したが、実機の自由落下・入力成功率、作戦の勝率、相手の火力と時刻に基づく精密な切替・複数タネへの押し付けは未完了。[作戦の仕様](FEVER_MODE_ENGINE.md#ランチャーで選ぶ作戦) を参照。

## 次の作業

1. 所有権を整理した探索・入力パイプラインで、同じシードの2Pの8〜9手目と不規則な操作中断を再対戦で確認する。通常・Fever・復帰、同色回転、被弾、フレーム欠落、ログ負荷を対象とし、裏探索の破棄と現在手の実入力を照合する。オフライン成功を実機成功と数えない。失敗した局面を固定し、配置候補・実経路・実着地を照合する。3個組のスポーン行の持ち上げは、移植したゲームの操作処理のプログラムで提示・実行する（[操作制限](DISABLED_TRIPLE_OPERATIONS.md)、オフライン確認のみ、実機未確認）。2個組の壁寄り経路とは区別する。
2. 初回本線とセカンドの保持・発火を確認する。可視探索と通常構築ビームを再利用する2〜4連鎖選択 `conversion.reuse_visible` を既定で有効にした。同じ記録ツモの4開始局面中2局面で実採用し、3連鎖後に13連鎖へ到達した。本線最大得点は前方式以上だった。準備計算は増える局面があるため、入力直前は枠を無効にして完成済み構築を再利用する。実機の操作待ち、相手の応手を入れた比較と全キャラへの拡張は残る（[検証](VALIDATION.md)）。満杯付近の規定未満本線を5連鎖以下へ変換し、残る盤面を再構築する探索を実装した（[変換探索](FEVER_CAPACITY_CONVERSION.md)）。局面再生で3連鎖への変換は確認したが、記録ツモ30手では13連鎖への復元は未達。目標点数、実連鎖数、初回手数、再構築時間、満杯での死亡と計算待機を測る。小さい容量発火や仮想列の見込みを大連鎖目標の達成として数えない。送信のない単発整地はビームの重み `level_root` で嫌う（単独構築24局で小消し−54%、13連鎖以上22→19局。[検証](VALIDATION.md)「単発整地の抑制」）。実機で整地の回数・本線・セカンドを確認して強さを調整する。
3. 通常盤面の発火時機とFeverへの攻撃を比較する。最後のタネ消化中の目標未満発火（`final_seed_fire`）は、同じシードと席入替で有無を比べ、発火回数・返された量・勝率を測る。小連鎖変換は相手の初回本線・Fever前、Fever伸ばし中、または種消化終了に送信が合う場合に限る。埋まった通常相手への致死量の追い打ちは、予測送信時間が長いほど許容ゲージを下げ、既存予告で足りる場合は構築へ戻る。保持する返し、送信先、実着弾、残る本線を記録し、同じシードと席入替で効果を測る。相殺を急ぎすぎる発火は、既知の攻撃総量を超えて返せる本線、または確認済みのマージン開始後に限り、2目盛り以上改善するか突入に届く場合に自由落下で待たせる。返せない通常本線は相手の連鎖終了より前に着地・おじゃま確認が済む限り設定幅の完成構築で伸ばし、期限で防御へ戻す（`gauge_wait`、[対戦エンジン](FEVER_MODE_ENGINE.md)）。攻撃の入りの予測時刻と自分のリンクの発射時刻で待ちを決める。実機で待ちの回数・返された量・突入の増減と、入りの予測の誤差を確認する。
4. おじゃま確認時刻の誤差を、相手連鎖終了予測・入力時間・ちぎり時間から分ける。実測ペースで今回のちぎり増分が相殺される計算、`window_build` の配送確認、得点済みリンクの飛行中相殺物体を攻撃量から落としていた経路と非消去の事前判断再利用を修正した。記録要求の死亡配置は再投入で落下・死亡を検出し、消す手へ変更することを確認した。再発射後の飛行時間を含む配送モデルの校正、修正後の実機での死亡回避と `nuisance_check_margin` の効果は残る。
5. 代表キャラで破綻する入力・判断を解消した後、全26キャラへ広げる。通常対戦の30試合受入れや、倍率・時計・全消し・端数列の網羅校正は残件として扱う。

## 設計・保守の制約

- 通常の構築・戦術、Feverのタネ探索は同じ可視情報と物理・得点・時系列で比較する。指定した既知ツモより先は、通常の構築と同じ仮想列（形はキャラの周期、色は6つの固定の色袋）でだけ読み、未観測の色を確定したものとして返さない。返す手順は渡された既知ツモの範囲に限る。事前判断と再利用は、要求で渡された既知ツモだけを使う。エンジンは表示前のツモを暗黙に追加しない。ブリッジが、出現時に見るツモ数にそろうよう色表から読んだ分を要求へ入れる。
- 判定値・設定の正本はコードと `data/fever/`。文書へ係数表を複製せず、目的と制約を説明する。
- 残る整理候補は `model.py` の責務分割、JSON境界と盤面変換の共通化、コード内定数の設定化。共有ビームの統合はTsuの対戦経路を含む検証方法を定めてから扱う。
- Tsuの改善は `irregular-form` で先に実施し、`fever` へ一方向で取り込む。詳細は [AGENTS.md](../AGENTS.md)。
