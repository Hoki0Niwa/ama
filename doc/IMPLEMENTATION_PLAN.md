# 実装計画

## 目標と現在地

Steam版Feverで、通常盤面の大連鎖を繰り返し構築し、相殺・突入・タネ消化・復帰を含む対戦判断を行う。通常本線は13〜14連鎖の安定を目標とし、15連鎖を実機の必須受入れ条件にはしない。実装の詳細は [対戦エンジン](FEVER_MODE_ENGINE.md) に置く。

| 範囲 | 状態 | 残る受入れ |
| --- | --- | --- |
| 形状・周期・配置・単独探索（段階A、T0〜T7） | 全26キャラの基盤を実装 | 色列は試作用。全キャラの入力・上端条件の網羅確認は未完了 |
| 得点・相殺・通常対戦・時間（T8〜T13） | API・自動検証・部分的な実測あり | 倍率、配送、端数、全消し境界の実機校正と総合受入れ |
| ゲージ・時計・タネ探索（T14） | protocol 3で実装 | 特殊ツモのタネ消化、終了境界、戦術の実戦効果 |
| 実機接続（T15） | ブリッジの2席操作と先読みを使用 | 残る入力失敗、時刻予測、再利用と取消の実機確認 |
| 全26キャラの総合評価（T16） | 未完了 | 全キャラ、被弾・全消し・復帰・死亡を含む受入れ |

## 次の作業

1. 失敗した局面を固定し、配置候補・実経路・実着地を照合する。3個組は測定済み許可の条件外を一律に解放せず、2個組の壁寄り経路と区別する。
2. 初回本線とセカンドの保持・発火を確認する。目標点数、実連鎖数、初回手数、再構築時間、満杯での死亡を測る。小さい容量発火を大連鎖目標の達成として数えない。
3. 通常盤面の発火時機とFeverへの攻撃を比較する。相手が保持する返し、送信先、実着弾、残る本線を記録し、同じシードと席入替で変更の効果を測る。
4. おじゃま確認時刻の誤差を、相手連鎖終了予測・入力時間・ちぎり時間から分ける。`nuisance_check_margin` の実機効果を確認する。
5. 代表キャラで破綻する入力・判断を解消した後、全26キャラへ広げる。通常対戦の30試合受入れや、倍率・時計・全消し・端数列の網羅校正は残件として扱う。

再現入口と既知の制約は [DEBUGGING.md](DEBUGGING.md)、検証結果の読み方は [VALIDATION.md](VALIDATION.md) を参照する。新しい学習・自己対戦環境は独立の `fever-simulator` と責務を分ける。

## 設計・保守の制約

- 通常の構築・戦術、Feverのタネ探索は同じ可視情報と物理・得点・時系列で比較する。未観測の未来を補わない。
- 判定値・設定の正本はコードと `data/fever/`。文書へ係数表を複製せず、目的と制約を説明する。
- 残る整理候補は `model.py` の責務分割、JSON境界と盤面変換の共通化、コード内定数の設定化。共有ビームの統合はTsuの対戦経路を含む検証方法を定めてから扱う。
- Tsuの改善は `irregular-form` で先に実施し、`fever` へ一方向で取り込む。詳細は [AGENTS.md](../AGENTS.md)。
