# フィーバー対応AI 実装計画

作成：2026-09-27、改訂：2026-10-01

状態：Fever固有機能は計画のみ。実装開始前。2026-10-04に共通Ama基盤の速度改善を適用・検証済み（[記録](SPEED_REFACTOR.md)）。

基準：ama v2.0.1 / `dea210bcd92965ae08fbc311f23565b0fab6dbbb`

## 1. 目的

amaの高速な盤面処理と連鎖構築探索を活用し、ぷよぷよeスポーツのフィーバールールで戦えるAIを作る。最初に段階Aとしてラフィーナの特殊ツモで単独の大連鎖を組む能力を確立し、以後、時間モデル、フィーバー中ソルバー、対戦戦略、クライアント接続の順で拡張する。

段階Aの確認目標は10連鎖、その後の改善目標は12〜15連鎖とする。これは段階的な目標であり、現時点の実績や達成率の保証ではない。

## 2. 現コードの前提と改装点

現在のamaは「2個ぷよ・通ルール・おじゃまレート70・連鎖倍率は通テーブル固定・おじゃまは必ず落ちる」を前提に、コアからクライアントまで一貫して書かれている。改装は次の3層に及ぶ。

1. ルール層：ツモ形状の抽象化、死亡判定、連鎖倍率テーブル、おじゃまレート、全消し処理、連続相殺、ゲージ・タイム・タネの状態機械。
2. 探索と評価：仮想ツモ列、手生成、quiescence探索、評価関数のしきい値、重みの再調整。
3. 戦略層：攻防ロジックをゲージとタイムを含む状態で組み直し、フィーバー中専用のソルバーを新設。

新規に作る部品は次の2つ。

- **フィーバー中ソルバー**：降ってきたタネを制限時間内に「タネ連鎖数以上」で発火する手を探す。残り時間、フィーバー側に撃たれたおじゃま、延長するか即発火するかの判断を扱う短い探索。
- **相手フィーバーの読み**：相手のゲージとタイムを追跡し、相手フィーバー中に妨害で撃つか自分の建築を進めるかを選ぶ分岐。

## 3. 設計方針

- **探索は維持し、学習は方針選択に限る。** ビーム探索とquiescence探索は強く、置き換えると弱くなる期間が長い。自己対戦で改善するのは相殺・ゲージ・発火タイミングの判断に絞る。
- **時間の単位はフレームに統一する。** 現在の `frame` と `frame_real` は「設置1手を1、ちぎりを+1、連鎖1つを+2」という仮単位で、相対比較には足りるが絶対時間には使えない。段階Bで実測値に置き換え、仮単位との混在を許さない。
- **時間は状態でなく行動コストに載せる。** ビーム探索のノードは盤面ハッシュで重複排除しているため、時間を状態に含めると置換表が効かなくなる。ちぎりを `action` スコアに足している現在の方法に揃える。
- **通用コードを保持し、専用の層を追加する。** 具体的なファイル配置と公開インターフェースは実装開始時に確定する。中断された試作の設計を既定としない。

## 4. 時間管理の難しさの評価

時間管理そのものは強さの難しさをそれほど上げない。計算機は人間より正確にフレームを数えられるため、むしろAI側の優位になりうる。難しさの中心はツモ形状と戦略層の再設計にある。

| 要素 | 難しさ | 性質 |
| --- | --- | --- |
| フレーム実測と時間コスト化 | 中 | 計測と地道な検証 |
| フィーバー中ソルバー | 低〜中 | 小さな最適化問題 |
| ツモ形状対応と手生成 | 中〜高 | コア全体の改修 |
| 連続相殺とゲージを含む対戦戦略 | 高 | 設計の正解がまだ無い |
| キャラ別テーブルと重みの再調整 | 中 | データ整備とチューニング |

## 5. 自己対戦の扱い

全面的な置き換えはしない。「探索が手を作り、学習が方針を選ぶ」構成を取る。前提として、フレーム・予告・連続相殺・ゲージ・タイム・タネ・ドロップセットを含む自己完結した2P対戦ループ、訓練用の軽量探索、重みを変えた複数個体や固定相手による多様性が必要になる。

1. **閾値のチューニング**：`think` の分岐条件をパラメータ化し、自己対戦の勝率を目的関数に進化戦略やCMA-ESで最適化する。`tuner/` が1P得点で行っていることの2P勝率への拡張。
2. **小さな選択器の学習**：探索が出す候補行動を「建築」「小連鎖で相殺」「本線発火」「タネ延長」「即発火」などに分類し、ゲージ、タイム、予告量、両者の資源量、相手本線の見積もりなどの特徴から1つ選ぶ方策を学習する。
3. **価値関数の学習**：2で明確に伸びた場合にだけ検討する。

## 6. 全体ロードマップ

### 段階A：ラフィーナのとこぷよ

対応するもの：

- ラフィーナの16手の形状周期。
- 4色、2個組、縦3個組、横3個組、2色4個組、でかぷよ。
- 形状ごとの回転・色選択・衝突・着地後のちぎり。
- 4個以上の同色接続による消去、重力、連鎖、中央2列の敗北判定。
- 現在のツモとNEXT2個を入力とする連鎖構築探索。
- 複数のツモ列での性能測定、手順の記録とリプレイ。

後の段階へ回すもの：フィーバーゲージ、フィーバー時間、連鎖のタネ、通常盤面との切り替え、相手の読み、相殺、おじゃま配送、全消しの特殊報酬、キャラ別攻撃倍率、Steam版の画面読み取り・操作入力、ラフィーナ以外のキャラクター。

想定する構成：

1. **ツモ生成**：形状周期と色列を分ける。実際に供給する列と、探索内で仮定する未来の色列は独立させる。
2. **配置・盤面遷移**：現在の盤面とツモから、到達可能な配置・配置後の盤面・連鎖結果を返す。
3. **探索**：配置候補を比較し、目標連鎖を構築・発火できる手を選ぶ。
4. **測定とリプレイ**：実際に選んだ手、盤面遷移、連鎖数、思考時間を記録する。

#### P0：仕様と測定条件を確定する

- `RULES_AND_ASSUMPTIONS.md` に形状、周期、色配置、回転、ちぎり、上端の扱いを整理する。
- 実機で確認した内容、資料から読める内容、試作上の仮定を区別する。
- 初期の色列モデルを明記する。独立乱数を使用する場合は、Steam版の乱数生成の再現と称さない。
- 目標連鎖数、手数上限、探索予算、測定対象のツモ列を設定として定義する。

完了条件：実装者が形状と遷移を曖昧に解釈せず実装でき、未対応の動作が明記されている。

#### P1：特殊な組ぷよの配置を再現する

- 全形状とでかぷよの選色を表現する。
- 衝突を避けた移動経路から、到達可能な着地候補を生成する。
- 着地後はセル単位に落下させる。3個・4個組を固定ブロックとして盤面に残さない。
- 同じ盤面になる候補は適切に重複排除する。
- 最初は壁蹴り・床蹴りなどを省略した保守的な移動判定を候補とする。省略により使えない手があることを明示する。

完了条件：以下の基準局面が期待結果と一致する。

- 全形状・全回転・端の列で、セル数と色数が保存される。
- 同色2個組と同色3個組を正しく扱える。
- 段差への着地とちぎりの順序が正しい。
- 高い壁の向こうへ不正に移動しない。
- 消去と重力が単純な配列による参照実装と一致する。
- 上端・隠れた段・中央2列の敗北を決めた仕様どおりに扱う。
- 共通の到達可能配置では、従来の2個組処理と結果が一致する。

#### P2：連鎖構築探索を接続する

- 入力は盤面、現在のツモ、NEXT2個、ラフィーナ周期の位置、探索設定とする。
- 未知のツモは形状のみ既知とし、色は複数の仮の列で比較する。
- 実際の未来列を探索へ渡さない。乱数の状態も共有しない。
- 配置・消去・敗北判定は共通の遷移処理へ集約する。
- 重複排除は盤面だけで十分かを検討する。同じ盤面でも未来ツモや周期が異なる状態を混同しない。
- 潜在連鎖の見積もりと、実際の合法手で発火できた連鎖数を区別する。

完了条件：全形状で合法な手を返し、未来情報を使わず連続プレイできる。これだけでは大連鎖能力の達成とはしない。

#### P3：連鎖構築と発火の方針を調整する

- amaの重みを初期の比較基準とし、3個・4個組に応じた調整を行う。
- 主な評価対象は、完成した連鎖数、潜在連鎖、発火しやすさ、盤面の余裕、不要な小消し、必要手数・投入ぷよ数。
- でかぷよを単発消しに浪費し続けないか確認する。
- 「目標到達で発火」と「さらに伸ばす」を別の方針として設定する。
- 通得点を使う場合は診断用とし、フィーバー得点や連鎖数と同一視しない。
- 10連鎖の実例を確認し、その後12〜15連鎖へ改善する。

完了条件：実際のプレイ列で大連鎖を発火でき、その手順を再生・検証できる。安定性はP4で測定する。

#### P4：再現性と速度を測る

- 調整用と評価用の固定ツモ列を分離する。
- 同じツモ列・手数上限・探索予算で比較する。
- 初回の評価用系列数は100を目安にし、測定時間を見て確定する。数を変えた場合は記録する。
- 結果と一緒にコード版、色列生成法、シード、設定、実行環境を保存する。
- リプレイは実際の実行ログから作成し、探索内の仮想連鎖と区別する。

記録する指標：

| 指標 | 定義・注意 |
| --- | --- |
| 最大連鎖数 | 実際に発火した連鎖数の最大値 |
| 各試行の最大連鎖数の平均 | 各系列で1つの最大値を求め、その平均を取る |
| 10／12／15連鎖達成率 | 規定手数以内にその連鎖数以上を実際に発火した試行の割合 |
| 死亡率 | 規定手数・終了条件の下で死亡した試行の割合 |
| 発火までの手数・投入ぷよ数 | 成功した試行について記録。未達試行数も併記 |
| 小連鎖の頻度 | 例として1〜3連鎖を小連鎖と定義し、定義を固定する |
| 思考時間 | 1手当たりの平均と上位側の遅延。探索設定と実行環境を併記 |

10連鎖で終了する設定の結果から、12／15連鎖達成率を評価しない。目標ごとの試行か、同一の伸ばし方針・手数上限での試行かを明記する。

完了条件：成功例だけでなく失敗を含む結果をまとめ、未達の原因を物理・探索・評価・処理時間に分けて説明できる。

### 段階B：時間モデル

- 実機の動画をフレーム単位で見て、設置、ちぎりの落下待ち、連鎖のリンクごとの消去と落下、ソフトドロップ、タネ落下演出の所要フレームを表にする。
- `frame` と `frame_real` の仮単位を実測フレームに置き換える。
- キャラ別の連鎖倍率表とおじゃまレート70/120を外部データ化し、`chain::get_score` をテーブル引数化する。
- 得点単位のしきい値をおじゃま個数単位へ変換する。

完了条件：連鎖と設置の所要時間が実機と秒単位で一致し、通の挙動が既存の計測でリグレッションしていない。

### 段階C：フィーバー中ソルバー

- タネの盤面、残り時間、フィーバー側予告を入力に、制限時間内にタネ連鎖数以上で発火する手を探す。
- 「延長して次のタネを大きくする」と「即発火して時間を残す」の価値を比較する。
- タネ盤面データとタネ失敗時の減少量は、確定するまでパラメータ化する。

完了条件：与えたタネ集合に対し、時間内の発火率と平均獲得連鎖数を記録できる。

### 段階D：対戦戦略

- `gaze::Player` にゲージ、タイム、予告量、フィーバー中フラグ、フィーバー側予告、タネ連鎖数を追加する。
- 連続相殺を前提に `think` の防御ロジックを再設計し、分岐条件をパラメータ化する。
- 2P対戦ループを作り、第5節の順で自己対戦による調整を進める。

完了条件：固定相手に対する勝率を同一設定で比較でき、変更の効果を再現できる。

### 段階E：クライアント

- 形状別の移動・回転・蹴り・出現位置を `path` に実装する。
- 実機の入力速度と接地猶予を考慮し、到達可能性と実機入力可能性を分けて扱う。
