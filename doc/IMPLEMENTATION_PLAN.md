# フィーバー対応AI 実装計画

作成：2026-09-27、改訂：2026-10-03

状態：段階Aの実装を開始する。

対象：ぷよぷよeスポーツ（Puyo Puyo Champions）Steam版。

## 1. 目的

amaの高速な盤面処理と連鎖構築探索を活用し、ぷよぷよeスポーツのフィーバールールで戦えるAIを作る。最初に段階Aとして、全キャラの形状周期に対応したうえでラフィーナの単独連鎖構築を確立し、以後、時間モデル、フィーバー中ソルバー、対戦戦略、クライアント接続の順で拡張する。

段階Aの確認目標は10連鎖、その後の改善目標は12〜15連鎖とする。これは段階的な目標であり、実績の保証ではない。

## 2. 基盤の選択：irregular-form を土台にする

`irregular-form` ブランチには、フィーバー版でもそのまま使える改良が入っている。2026-10-03 に `irregular-form` を `fever` にマージした（T0 完了）。競合は `AGENTS.md` だけで、両方の内容を併記して解決した。

Tsu と Fever を混ぜないための運用は `AGENTS.md` の「ブランチの分離」に従う。要点は、マージは `irregular-form` → `fever` の一方向だけ、フィーバー固有のコードは新規ファイルに閉じ込める、既存ファイルの共通化は `irregular-form` に先にコミットする、Tsu の挙動はプロトコルテストと `bench` の同一シード結果で固定する、の4つ。

引き継ぐ改良と、フィーバーでの使い方：

| irregular-form の改良 | 内容 | フィーバーでの扱い |
| --- | --- | --- |
| エンジンJSONプロトコル（`pvp --engine`） | 1行JSONで盤面・ツモ・相手状態を受け、配置を返す。`solo`、`fire`、`include_path`、`include_next`、`reuse_search`、`tactics_only` などの追加フィールド | フィーバー版エンジンも同じ枠組みにし、`rule`、`character`、ツモ文字列の拡張を加える。Tsu用 `pvp.exe` は変更しない |
| `ai/fire.h` の発火方針 | 手持ちで発火できる連鎖がトリガー以上なら即発火、盤面が74個以上なら手持ちの連鎖を撃つ | 判定を「連鎖数」または「キャラ別テーブルの点数」に差し替えて流用 |
| 見える3ツモから探索（`QUEUE_VISIBLE = 3`） | ビーム探索が現在手＋NEXT2を使い、残りをサンプリング | 形状は周期で既知なので、サンプリングは色だけになる |
| `prepare` コールバック | 戦術判断が必要とする建築探索だけを遅延実行 | 対戦段階でそのまま使う |
| `bench/` と `render.py` | シード範囲の一括計測、盤面スナップショットのSVG描画 | `bench_fever` を同じ出力形式で作り、`render.py` を共用 |
| `pvp/` 対戦シミュレータ | 2エンジン対戦、おじゃまの送受、ログ | 段階Dで `fever_pvp` に拡張（ゲージ・タイム・タネ・2つの予告） |
| 実行時 BMI2 選択、`build.ps1`、`test_engine_protocol.py` | 可搬な Windows ビルドとプロトコル回帰テスト | そのまま使い、フィーバー用のテストを追加 |
| 定型評価の既定オフ（`form = 0`） | GTR 等のパターン一致を外した評価 | 特殊ツモでは定型が成立しにくいので既定オフを維持 |

`irregular-form` の `AGENTS.md` にあるとおり、フィーバーは別バイナリとして提供し、Tsu のブリッジがフィーバー用エンジンを誤って実行しないようにする。ブリッジ側（`ama-memory-bridge`）のメモリ読み取りとフィーバー用プロファイルはこのリポジトリの範囲外で、段階Eで扱う。

現在のamaは「2個ぷよ・通ルール・おじゃまレート70・連鎖倍率は通テーブル固定・おじゃまは必ず落ちる」を前提に書かれている。

## 4. 設計

### 4.1 ツモの表現：`core/piece.h`

```cpp
namespace piece {

enum class Shape : u8 { PAIR, TRIPLE, QUAD, BIG };

struct Piece {
    Shape shape;
    cell::Type colors[4];   // 形状ごとに決めたセル順
};

}
```

- `PAIR`：`colors[0]` が軸、`colors[1]` が子。既存の `cell::Pair` と相互変換する。
- `TRIPLE`：`colors[0]` が軸、`colors[1]` が軸の上の腕、`colors[2]` が軸の右の腕。縦3個組は `(A, A, B)`、横3個組は `(A, B, A)` で、同色3個は `(A, A, A)`。形状は同じL字で、色の位置だけが違う。回転は軸を中心に4状態。
- `QUAD`：2×2。`colors[0..3]` を左下、左上、右下、右上とし、回転で色が1つずつ回る。4状態。
- `BIG`：2×2の単色。回転の代わりに色が変わるので、配置の `r` を色の添字として使う。4状態。

配置は既存の `move::Placement{x, r}` を流用し、`r` の意味を形状ごとに定義する。2列幅の形状は `x` を左列とし、`x` は 0〜4。

### 4.2 形状周期：`core/dropset.*` と `data/fever/dropsets.json`

- 全26キャラの周期を `data/fever/dropsets.json` に置く。L/J は `triple_a` / `triple_b` として読み、縦横への対応は1か所の設定で切り替える。
- 実行時にJSONを読まず、`core/dropset.cpp` に定数表として持つ。表とJSONの一致はテストで確認する。
- `dropset::shape_at(character, index)` で `index` 手目の形状を返す。

### 4.3 ルール：`core/rule.h`

```cpp
struct Rule {
    bool fever;                 // フィーバールールか
    u8 death_columns;           // ビットマスク。通は 0b000100、フィーバーは 0b001100
    const u32* power_normal;    // 連鎖倍率（通常盤面）
    const u32* power_fever;     // 連鎖倍率（フィーバー盤面）
    i32 target_normal;          // 70
    i32 target_fever;           // 120
    i32 margin_seconds;         // 128
};
```

段階Aでは `death_columns` だけ使い、テーブルは段階Bで埋める。

### 4.4 ツモ生成

- 形状は周期から確定し、色だけを乱数で決める。
- 初期の色モデルは4色の独立一様乱数。`QUAD` の2色は異なる、`TRIPLE` は `(A,A,B)` か `(A,B,A)` を周期の L/J に従って作る、`BIG` は1色。
- Steam版の生成法則（色1つにつき乱数1回、初手の制約、22ぷよの置換規則）の再現は後回しにし、再現していないことを結果に明記する。
- 探索内の仮想列と、評価に使う実際の列は別の乱数状態にする。

### 4.5 探索

- `beam::expand` を `Piece` 対応にする。子ノードは `drop_piece` → `pop` → `is_dead` の順。ちぎりコストは `get_drop_piece_frame` から。
- `beam::search_multi` の仮想列は、周期から形状列を作り、既存の6本の色袋を各ツモのセルへ順に割り当てて作る。同色3個組や22ぷよの色制約もここで満たす。
- 置換表のハッシュに周期位置を含めるかは、同じ盤面でも次に来る形状が違えば価値が違うため、含める方向で試し、効果を測って決める。
- 枝刈りの `PRUNE` は得点でなく連鎖数で判定する。
- quiescence探索と評価関数は、到達判定と上限段を4列目にも適用する以外は維持し、重みは後で調整する。

### 4.6 発火方針

`ai::fire::decide` を `Piece` 対応にし、トリガーを連鎖数で与える。段階Aでは「目標連鎖数に達したら発火」と「伸ばす」を設定で切り替える。盤面が満杯に近いときの退避発火は維持する。

### 4.7 フィーバー用エンジンとプロトコル：`fever/main.cpp`

`pvp/main.cpp` の構造を踏襲し、別バイナリ `bin/fever/fever.exe` を作る。プロトコルは `pvp` の形式に次を加える。

| フィールド | 意味 |
| --- | --- |
| `rule` | `"fever"` |
| `character` | キャラ id（`dropsets.json` の `id`） |
| `dropset_index` | 現在のツモが周期の何手目か |
| `queue` | ツモ文字列の配列。例 `"2:RG"`、`"L:RRG"`、`"J:RGR"`、`"4:RGRG"`、`"0:R"` |
| 返答 `x`, `r` | 形状ごとの意味。`BIG` は `r` が色 |

段階Aでは `solo` のみ対応する。

### 4.8 計測：`bench_fever`

`bench/main.cpp` と同じTSV形式に `character` 列を加える。盤面スナップショットは `render.py` が読める形式のまま出す。puyop の URL は使えないので、再生用に1手ごとのJSONログを出す。

## 5. 作業順序（段階A）

各タスクは、変更するファイル、完了条件、確認方法を持つ。順序は依存関係に従う。

### T0：基盤の統合

- `fever` に `irregular-form` をマージし、`AGENTS.md` の競合を解決する。
- Linux と Windows で `pvp`、`bench`、`test` がビルドでき、`python test/test_engine_protocol.py` が通ることを確認する。

完了条件：マージ後の `fever` で既存の通エンジンが変更前と同じ結果を返す。

### T1：`Piece` と `dropset`

- `core/piece.h`、`core/dropset.h`、`core/dropset.cpp` を追加。
- `data/fever/dropsets.json` と定数表の一致テスト。
- `Pair` ↔ `Piece` 変換。

完了条件：全26キャラの周期がコードから引け、りすくまは `unknown` として扱われる。

### T2：配置と遷移

- `Field::drop_piece`、`Field::get_drop_piece_frame`、`Field::is_colliding_piece`、`Field::is_dead`。
- `move::generate(field, piece)`。最初は壁蹴り・床蹴りを省略した保守的な到達判定。14段目の扱いは2個ぷよと同じ規則を仮定する。
- 散在する死亡判定を `is_dead` に置き換える。通ルールでは結果が変わらないことを確認する。

完了条件：次の基準局面が期待結果と一致する。

- 全形状・全回転・端の列で、セル数と色数が保存される。
- 同色2個組と同色3個組を正しく扱える。
- 段差への着地とちぎりの順序が正しい。
- 高い壁の向こうへ不正に移動しない。
- 消去と重力が単純な配列による参照実装と一致する。
- 上端・隠れた段・中央2列の敗北を決めた仕様どおりに扱う。
- 2個ぷよの到達可能配置は従来の `move::generate` と一致する。

### T3：ツモ生成

- `fever::Queue` と生成器。形状は周期、色は独立乱数。
- 探索用の仮想列生成（色袋の割り当て）。

完了条件：任意のキャラとシードで決定的な列が得られ、色制約を満たす。

### T4：探索の接続

- `beam::expand`、`beam::search`、`beam::search_multi` の `Piece` 対応。
- quiescence探索と評価の4列目対応。
- `fire::decide` の `Piece` 対応と連鎖数トリガー。

完了条件：全形状で合法な手を返し、未来情報を使わず連続プレイできる。

### T5：`fever/main.cpp` と `bench_fever`

- `solo` モードのエンジンと JSON プロトコル。
- `bench_fever`、JSONログ、`render.py` 用スナップショット。
- `test/test_fever_protocol.py`。

完了条件：ラフィーナで100シードの計測が回り、結果TSVと盤面が出る。

### T6：調整

- 重みは `config.json` の `build` を出発点にし、特殊ツモ向けに `bench_fever` で比較する。
- でかぷよを単発消しに浪費しないか、22ぷよの置き場所、3個組のちぎりを確認する。
- 10連鎖の実例を確認し、12〜15連鎖へ。

完了条件：100シードで10連鎖達成率、死亡率、思考時間を記録し、未達の原因を物理・探索・評価・処理時間に分けて説明できる。

### T7：全キャラ照合

- 各キャラで16手プレイし、形状周期を実機と照合する。
- L/J と縦横の対応を確定し、`dropsets.json` の状態を更新する。
- りすくまの周期を取得する。

完了条件：全26キャラの `status` が `official` または実機照合済みになる。

## 6. 記録する指標

| 指標 | 定義・注意 |
| --- | --- |
| 最大連鎖数 | 実際に発火した連鎖数の最大値 |
| 各試行の最大連鎖数の平均 | 各系列で1つの最大値を求め、その平均を取る |
| 10／12／15連鎖達成率 | 規定手数以内にその連鎖数以上を実際に発火した試行の割合 |
| 死亡率 | 規定手数・終了条件の下で死亡した試行の割合 |
| 発火までの手数・投入ぷよ数 | 成功した試行について記録。未達試行数も併記 |
| 小連鎖の頻度 | 1〜3連鎖を小連鎖とし、定義を固定する |
| 思考時間 | 1手当たりの平均と上位側の遅延。探索設定と実行環境を併記 |

調整用と評価用のシードは分ける。結果にはコード版、色列生成法、シード、設定、実行環境を添える。

## 7. 段階B〜E

### 段階B：時間モデル

- 実機の動画をフレーム単位で見て、設置、ちぎりの落下待ち、連鎖のリンクごとの消去と落下、ソフトドロップ、タネ落下演出の所要フレームを表にする。
- `frame` と `frame_real` の仮単位を実測フレームに置き換える。時間は状態でなく行動コストに載せる。
- キャラ別の連鎖倍率表とおじゃまレート70/120を `Rule` に入れ、`chain::get_score` をテーブル引数化する。
- 得点単位のしきい値をおじゃま個数単位へ変換する。

### 段階C：フィーバー中ソルバー

- タネの盤面、残り時間、フィーバー側予告を入力に、制限時間内にタネ連鎖数以上で発火する手を探す。
- 延長と即発火の価値を比較する。タネ盤面データと失敗時の減少量はパラメータ化する。

### 段階D：対戦戦略

- `gaze::Player` にゲージ、タイム、予告量、フィーバー中フラグ、フィーバー側予告、タネ連鎖数を追加する。
- 連続相殺を前提に `think` の防御ロジックを再設計し、分岐条件をパラメータ化する。
- `pvp` をフィーバー審判に拡張し、自己対戦で閾値を調整する。学習は「探索が候補を作り、学習が方針を選ぶ」構成に限り、閾値チューニング→選択器学習→価値関数学習の順で重くする。

### 段階E：クライアント

- 形状別の移動・回転・蹴り・出現位置を `path` に実装する。
- ブリッジ側にフィーバー用のメモリプロファイルと状態遷移を追加する。
