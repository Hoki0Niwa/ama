# フィーバー潰しの現行仕様

2026-10-09。通常盤面からの戦術判断と、自分がFever中の種探索で共有する。原因調査の当時の挙動は [調査記録](FEVER_DISRUPTION_INVESTIGATION_2026-10-09.md) に残す。

## 攻撃の使い分け

通常／Feverの確定／未確定予告は引き続き4値で別々に扱う。既知の相手連鎖を最後まで精算し、その後のFever予告について無送信時から増えた量をextraとする。normalの保留予告をFeverへ送った量として加点しない。

| 種類 | 条件・評価 |
| --- | --- |
| ジャブ (`jab`) | 自分の連鎖終了が相手の既知の連鎖終了～26F後に収まる。初回突入は送信先切替～最初の操作開始を含む実測由来の窓を使う。副砲、または開始時24個未満の小盤面で本線を使える。加点比率はextra/12、最大1。1個は1/12、6個は1/2、12個以上は1。通常の静かな場面で構築を変える最低比率は1/2とし、1～5個だけのジャブを目的に発火しない。 |
| 火力で上回る (`overpower`) | 資源を残す副砲で、観測済みの現在の攻撃を精算した後に新規12個以上を残す。または相手の次の種の返し見積もりより6個以上多く残し、新規送信も6個以上ある。量に応じて比率1～3。ジャブの時機窓は不要。現在の攻撃だけを上回る判定には観測した得点イベントが必要。 |
| 本線による継続圧力 (`main_pressure`) | 通常構築側が目標到達・容量など自身の発火方針で現在の発火を選んだ場合に限り、相手の次の種より6個以上多く残し、新規送信も6個以上あることを追加評価する。潰しだけで未完成の本線を発火させない。次の一種を上回るだけでは構築目標を解除しない。 |
| 突入直後・伸ばし中 (`extension_pressure`) | 現在の相手種へ実際にその個数のお邪魔を落とし、可視3ツモ以内のどの合法経路でも規定連鎖が発火できないことを確認できた場合、6個以上の新規送信を評価。副砲・小盤面を使い、ジャブの26F窓には限定しない。規定連鎖を維持して返せる種にはこの加点をしない。対象の種が交換されたり連鎖が始まった場合はこの目的の先読みを失効させる。 |

既に無送信時の予告だけで「次の種の返し＋6個」以上が残るなら、追加の潰し加点は付けない。毎回小消しを足すより、再構築へ資源を回す。

本線・副砲の資源分類自体はmain由来のまま。その分類を、Feverへの攻撃目的と同一視しない。通常盤面で本線を潰しに使うのは原則避け、初回・セカンドの目標へ構築する。例外は24個未満の小盤面で時機を合わせるジャブ／実盤面確認済みの伸ばし妨害、構築側が通常の発火方針で選んだ発火、生存に必要な相殺・緊急発火。自分自身がFever中の種消化には通常盤面の未完成本線保護を適用しない。

構築返答のfireを戦術へ渡し、「構築と同じ配置で何かが消える」と「構築が発火を選んだ」を区別する。24個以上の通常盤面で、構築が選んでいない本線を含む経路へは潰し・倒せる見込み・全消し目的の加点を付けない。可視の次手で本線を撃てることを理由に、現在の単発や準備手を潰しとして採用する経路も抑える。通常の非消去構築キャッシュと目標設定は維持する。

少量予告の受入れ許容量・中央高さの条件は相手がFeverでも使用する。安全に受けられる予告を理由に本線を壊さない。許容量を超える予告、十分な返し、生存上の緊急判断は残す。未確定の未来色で生存を保証したものではない。

大きい通常盤面（24個以上）で、相手の次の種以下の本線しかなく、急いで相殺する必要もなく、安全な非消去配置がある場合は温存する (`tactics_hold_for_fever_counter`)。まだ到着していない相手攻撃より先にその弱い本線を消してしまう十分返しの優先も抑える。実際に予告を相殺できる時機では従来の返し・ゲージ判断を使う。安全な配置がない場合の緊急発火を一律禁止しない。

## でかぷよ・最後の種の例外

相手の次の可視ツモがでかぷよで、時計と種の連鎖時間からその次の種でFeverが終わる見込みなら、次の種で返せる程度のジャブ加点を無効にする。返しを上回る攻撃は維持する。次ツモは連鎖中の可視列では次スロット、種待ち／操作中では現在スロットを使う。

これは種の標準得点・幾何タイムラインによる見積もりであり、そのでかぷよで必ず発火できることや、相手が種を伸ばさないことを証明してはいない。

## 相手の種レベルの記憶

ブリッジContextは、観測できた `seed_last_chain` の3～15を両者別々に記憶する。盤面・可視ツモが読めず完全なviewを作れない時でも記憶を更新する。無効な値しか読めない間は最後の有効値を使い、一度も観測していなければ値を捏造しない。ラウンドとモード境界で履歴を区切る。

エンジンへは従来の `seed_chain` で渡す。次の種の返し量は相手キャラのFever倍率と種レベルから計算する。相手の発火盤面から全連鎖を予測できた場合は、その実連鎖数・全消しを使って次の種のレベルを保持する（伸ばした分、失敗、全消しの加算を反映）。予測がない合成の終了イベントでは従来のレベル＋1を近似として使う。次の実観測値が得られればそちらを使う。

Fever連鎖の終了フレームも、こちらへの未確定予告があるかに依存せず記憶する。相手が種を組んでいて既知終了時刻がない場合、ジャブの時刻は推定しないが、火力で上回る攻撃は比較できる。

## 全種の形状と返しの確認

種探索と独立した `seed_defense` は、実際の相手の固定盤面・色・可視3ツモ・特殊形状で、非消去設置後に最大30個のお邪魔が落ちた後の発火経路を調べる。端数列が未知なら全列組合せを相手に有利な側で扱う。規定連鎖が発火できる経路とその最大得点を記録し、可能なら次の成長種の標準得点も返し見積もりへ含める。規定連鎖を維持できる証拠がある低連鎖の階段・座布団へ、二段程度の少量攻撃を伸ばし妨害として加点しない。

伸ばし中の標準返し見積もりには現在の種と次の成長種を含める。お邪魔落下後の実探索が完了した個数では、その最大反撃得点と次の成長種の見積もりを使う。最大反撃量が未確定なら、過小見積もりで火力攻撃を加点しない。

既存の公開参照は4系統（平積み、挟み込み、階段、座布団）50盤面。階段4・座布団6は参照データが未収録で、Steam全パターン照合済みではない。判断は名前やこの50盤面への一致を必要とせず、未収録・色置換・伸ばし後の実盤面も同じ処理で調べる。同じ形の種は名前を推定せず複数候補として診断する。

実機の調査予算は1判断あたり最大8ms・16000配置で、盤面・ツモ・ゲージ列位置をキーに結果をキャッシュする。同じ観測フレームに繰り返し調べず、後の観測で未完了の個数を追加する。時間切れは「カウンター不可」としない。可視ツモの先、相手が落下前に何手積むか、送信中に種を交換する場合の全未来盤面は確定予測ではない。「伸ばしを続けると発火が妨げられる」圧力として評価し、早期発火を強制できる可能性を含む。新しい分析が入った分、戦術探索の残り時間を構築後に取り直し、既存の判断時間予算へ収める。

## 時機検査と操作の継続

ジャブ返答に `disruption_timing` を付け、目標と締切を対戦の絶対フレームとして保存する。先読みの準備、早期返答のauthorize、Fever種の発火、到達可能配置への復旧発火で同じ検査を使う。古い122Fの幅を現在から再び数えない。対象モード・種が別のものに進んだ場合も失効させる。

現在のターゲット情報を使った追加検査も保存窓でなく現在の幅を使う。通常の構築・火力攻撃は、相手の得点リンクが進んだだけでこの時機検査から捨てない。失効したジャブのみ改めて配置を判断し、単独構築のキャッシュは維持する。相手の確定済み連鎖を毎回探索し直す方式ではない。

相殺・全消しなど独立した理由で発火する配置には、付随するジャブ加点の締切を適用しない。ジャブの時機が過ぎたことだけで必要な発火を取り消して操作をやり直す経路を防ぐ。

診断は返答とplanningログの `fever_disruption`（種類、種レベル、次の返し量、ジャブ例外）と `disruption_timing` を使う。

### 2026-10-09 相手Fever解析をイベント時に固定

追加指示により、相手Feverの解析は突入・タネ到着・発火に限定する。mode_engineのenemy_analysisは相手盤面、可視ツモ、種防御、送信先別ストック、対策情報をそのイベント時点で保存する。途中の移動、残り時間、予告変更、レート変更では種防御を再探索しない。発火は新しいイベントとして更新し、次のタネまで保持する。

発火時に連鎖リンクと終了時刻を絶対フレームへ変換して保存する。連鎖終了は送信の確定時刻であり、自盤面への落下時刻と同一とは扱わない。落下はこの確定時刻と、自分の非消去手の固定から既存arrival規則で求める。途中で得点済みのリンクを除外し、絶対フレームから現在との差分を取るが、リンクの観測時刻で連鎖終了を再び先へずらさない。自分の配置探索、実際の自盤面・予告・期限の検査は継続する。

bridgeは配置判断直後に独立プロセスで先読みを開始する。準備状態と相手解析状態をJSONで主プロセスへ移送し、新しい相手解析を古いものに戻さない。盤面・ツモ列・モード・種・設定の既存照合を通った準備だけを使う。

test_fever_event_analysisの5回帰で、解析頻度、突入とタネの区別、固定終了時刻、JSON移送後の探索0ms再利用、試合更新を検査する。Fever339件・26ファイル、通プロトコル13件が成功。実機の待ち時間と落下時刻の精度は未確認。
