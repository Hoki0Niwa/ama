## 6. 統計と合格・保留・不採用

主解析は新群の@40だけ。キャラ別Wilson95%と対応gain/lossを出す。両キャラの平均差は、同じseedを1クラスタとして扱う。

```text
d[s,c] = success_S0(s,c) - success_B0(s,c)
q[s] = d[s,raffina] + d[s,rafisol]       # -2..2
Delta = sum(q) / (64*2)
```

64クラスタを10000回再標本化するbootstrap95%（解析RNGは固定0x540）を併記する。128件を独立とみなして区間を狭めない。主検定は方向を事前固定したseedクラスタの対応sign-flip検定とし、各非零`q`の符号を1/2ずつ反転した`sum(q*) >= observed sum(q)`の確率を整数DPで正確に計算する。これはクラスタ単位の交換可能性を仮定した検査で、Steamの母集団を保証しない。キャラ別McNemar二側は説明用、@30/@35は保護指標とし、良い結果の検定だけを選ばない。

次の全条件を満たした場合だけ`eligible_for_next_research_baseline`とする。

| 判定項目 | 事前固定の条件 |
| --- | --- |
| 完了・正当性 | 256/256完了、source/settings/binary不変、unfinished/error 0、観測漏洩・遷移／得点不一致0。必要テストと既知再現が成功 |
| @40の実用的な差 | 両キャラ平均で**+5 percentage points以上**。128対応のため純増7件以上。各キャラで少なくともgain1、B0成功を失ったlossは両キャラとも0 |
| 偶然変動 | seedクラスタの一側sign-flip p≤0.05。信頼区間も全て表示し、検定だけで効果量を置き換えない |
| 早期達成 | @30／@35の成功件数が、各キャラでB0を下回らない |
| 安全・手順 | 各キャラのdeadとnomoveがそれぞれB0以下。両条件のtimeout 0。Fを出した試行は最初の証明期限Dまでに実成功し、期限の延長・破綻0 |
| 費用 | 成功応答の総choose観測250ms超0。S0のP95は各キャラでB0のP95+25ms以下。全関連process CPU／判断の平均は各キャラでB0比+15%以内。最大・失敗応答遅延・CPU全量・メモリも報告 |

+5ptは、この工程を次へ進めるための工数上の最低改善幅であり、ユーザーの最終目標を下げるものではない。CPU+15%も採用判断用の事前許容値で、達成予測ではない。異なる盤面へ進むため平均CPUには試行経路の差が含まれる。固定観測のprobe費用も併記する。

S0は証明済みの発火だけで介入するため、この段階ではlossをgainと相殺する設計を採らない。交換可能性の検定でも、同一seedの両キャラにだけgainが集中した場合は独立な2件と扱わない。数ポイントの改善では64seedでも保留になり得る。保留は効果ゼロの証明ではない。

## 7. 意味的テストで固定するもの

- 点数・初回停止・30/35/40/41・死亡優先・整理と累積の非混同は既存テストを維持する。
- H1を含まない2条件でも正式S0C gateが動く。旧H1 gateや旧仕様のhashを出力したら失敗する。
- seed／未来色をActorに送らない。環境だけが列を持ち、再生は保存の公開履歴だけで作る。
- 保存Fの残りd−1、次の最短発火期限、同時死亡、途中目標未満10以上を検査する。未完了probeを「解なし」へ変換しない。
- 25msの協調打切りと総250ms timeoutを区別する。timeoutでも失敗1件と直前Observation／planner状態が残り、成功した再試行で置換されないことをfake workerで検査する。実機の厳密な250ms返却保証テストとはしない。
- 統計は対応キー不一致・重複・不完全組を拒否する。両キャラの結果が同じseedで動いた例を1クラスタとして扱う。零差だけならp=1、正の非零クラスタ5個なら片側p=1/32となる例を検査する。
- 新出力先は未存在を要求し、過去のbaseline・source archive・v4 binaryを上書きしない。

## 8. 成果物と工数

保存先は新しい`data/fever/baselines/<実行日>-firstscore40-s0-confirm/`。本書コピー、manifest、設定、source/build snapshot、seed監査、既知1095再生、8smoke、256実試行、全steps、時間／CPU／メモリ、F継続監査、gain/loss反例、テストログ、SHA inventoryを保存する。未開始・未完了も明記する。結果文書は`doc/FEVER_FIRSTSCORE40_S0_CONFIRMATION_RESULT_<実行日>.md`とし、README／計画／WORK_LOGから辿れるようにする。
