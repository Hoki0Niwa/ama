# 対戦の時間モデル

ゲーム内部のフレームで扱う。通常盤面とFever盤面の時間は別で、CPUの探索時間とも分ける。定数は `data/fever/timing.json`、計算は `fever_battle/timing.py` を参照。

## 連鎖と操作再開

消去後に落下する各列について、最大落下距離をd、動くぷよ数をnとする。

```text
列の接触時間 = 2*d - 1 + (n > 1 ? ceil(3*(n-1)/2) + 1 : 0)
F = 動く全列の接触時間の最大（動くぷよなしなら0）
```

| 区間 | 通常盤面 | Fever盤面 |
| --- | --- | --- |
| リンク間隔 | 55 + F + 14 | 43 + F + 11 |
| 最終リンク→連鎖終了 | F>0なら上と同じ、F=0なら55 | F>0なら上と同じ、F=0なら43 |
| 確定→最初のリンク | 15 + ちぎり増分（Steamのリンク開始は14） | 13 + ちぎり増分（同12） |
| 非消去確定→次の操作 | 28 + ちぎり増分 | 26 + ちぎり増分 |
| 連鎖終了→次の操作 | 13 | 次タネ交換の予算100（下記） |

得点は各リンク開始時に発生し、予告確定は連鎖終了時。観測済みリンクを二重送信しない。相手の連鎖予測には誤差を含め、連鎖終了と実際の予告落下を区別する。

## ちぎりと入力

通常のちぎり増分は段差0〜9で `0/13/18/22/25/28/30/33/35/37F`。9段は1例のみ。10〜13段の `39/41/43/45F` は `ceil(37*sqrt(段差/9))` による推定。

Fever中の小段差は0〜3段の増分 `0/10/14/17F` を使う。4段以上は通常時の参照値を推定として使う。独立シミュレーターの実機の記録では、Feverの7段が25F（通常の値÷1.31の四捨五入と一致。1〜3段も同じ規則で一致）で、シミュレーターはrevision 13からこの規則を使う。Ama側の値は変えていない。

上の段での確定（独立シミュレーターのrevision 14〜15、記録に合わせた規則）：一番上（fy −2.0）で止まってから下を押し続けて確定した手は、確定→次の判定が通常1F・Fever 2F短い。組ぷよが13段目から1段ちぎれ、確定のtickだけ下を押した手は1F短い。記録の消えない手611件が一致した。Ama側の値は変えていない。入力経路14F、次タネ交換100F、Feverのおじゃま落下後の操作再開80Fは汎用の実測上限ではない。

操作間隔は同一モードで連鎖を挟まない直近9回の中央値 `pace_frames` を使い、3例集まるまで渡さない。モデルの最速値との大きい方で期限内のツモ数を見積もる。配置の速度と、CPUの通信待ちを混同しない。

## おじゃま判定と時計報酬

消さない設置では、通常の接地＋ちぎり＋16F、Feverの接地＋ちぎり＋14Fを判定時刻の基準にする。予告確定がその時刻までに来れば落下候補へ移す。消去する手ではその設置の落下を抑える。

連鎖時間加算は終了時に `max(0, chain-2)*30F`。全消しの300Fは終了16F後の別イベント。時計0から報酬で復活させない。開始済みの連鎖の得点を、時計0で途中切断しない。表示の秒と内部期限の違いは [観測仕様](FEVER_MODE_OBSERVATION.md)。

マージンによるレート変化は現在のゲーム時刻と要求から扱う。既定の曲線（192秒開始、8秒刻み、27段の係数表）は [対戦ルール](FEVER_BATTLE_RULES.md) と `margin_reference.json`。実際の部屋設定・停止条件を観測なしに確定しない。

## 突入・交換・復帰の区間（独立シミュレーターの導出）

独立シミュレーターがSteamのフェーズ捕捉（`fever-simulator/data/phase_timing.json`、1セッション）と元コードから導出した区間。Eは連鎖終了境界（場phase8）、Mはタネまたはおじゃまの生成・落下運動。値は `timing.json` の `transition_structure` に置いた。

| 区間 | 導出 | 根拠 |
| --- | --- | --- |
| 通常の連鎖終了→次の操作 | 13F（phase8の1F＋phase0＋生成待ち11F） | 捕捉。上表の13と同じ |
| 全フェーズ後の制御末尾 | 12F（場phase0の1F＋生成待ち11F） | 捕捉。旧13F／1Fの推定は廃止 |
| 突入 | E+16でモード切替・時計開始、E+37でタネ生成、M＋12Fで再開（捕捉M=63で112F。52タネではM=41〜69で90〜118F） | 捕捉 |
| 復帰 | E+16で通常へ、E+33で保留予告の落下判定、落下運動＋12Fで再開（30個で117F）。落下なしは45F。Feverが連鎖の途中で時間切れになった復帰は、落とさない（連鎖した手のフラグ） | 捕捉（30個）、落下なしと時間切れの復帰は実機の記録（2026-10-17） |
| Fever交換 | 消え残りの飛散と待ち（約12F）の遅い方＋M（速度1.31）＋12F（捕捉M=56で80F） | 捕捉＋コード |
| 通常全消し交換 | 1F＋M（速度1.0）＋12F | コード、実機の記録で一致（2026-10-17） |
| 時計0の連鎖の終わり | タネ交換の処理（消え残りの飛散と待ち）が走り、タネの抽選の1F前に復帰を始める。全消しのときは飛散が無い | 実機の記録（2026-10-17） |

Fever交換の100Fは、飛散のない場合の最大（12＋69＋12＝93F）と実測91〜98Fを覆う計画用の予算として残す。飛散の寿命はプレイヤー乱数（1個5回）に依存し、Amaは推定しない。レベル別のMの最大は `transition_structure.fever_seed_motion_max_by_level`。Feverのおじゃま落下後の80Fも同様に計画用の予算で、実際はおじゃま運動＋12F（30個72F＋12F）。

## 校正範囲

Steam build 15209927の同一フレーム観測とnative遷移を照合。通常は4310配置・1202リンク、最終リンク→操作再開896件。リンク予測誤差は−1〜+2F、操作再開は−2〜+2F。Feverは49リンク・6最終リンク、次タネ再開3例（91〜98F）で照合した。全キャラ・全盤面の誤差保証ではない。

Feverのおじゃま判定14Fは3例（ちぎりなし2例、1段1例）。落下後の再開は1/4/12/30個で46/50/55/71Fの4例。大段差、全消し交換、全量のおじゃま、入力時間、配送順には未校正部分がある。

採取はブリッジの時間プローブ、再集計は `python -m fever_battle.calibrate`、`calibrate_mode`、`calibrate_deadlines` を使う。生ログ・SHA256付き集計はGit除外のローカル `data/fever/baselines/` に置く。独立シミュレーター側の校正値を、このAIの時間予測・入力の検証結果として流用しない（上の導出区間は仕様の参照に使う）。

## 通常盤面の確認余裕

`battle_policy.json` の `timing.nuisance_check_margin`（現在10F）を標準の通常判定16Fへ足す。Feverと明示的な線形モデルには足さない。0で無効。既定は試作値で、実機の降下回避効果は未確認。

実機ログの降下60局面を余裕0/10で再投入した配置は全て同じ。独立シミュレーターの100seed×2席順では、10対0が178/200完走・勝ち89対89、降下量3403対3420。未完走22局は出現列が塞がった際の現在姿勢を接続が渡さない制約を含む。降下・死亡への効果は測定できず、シミュレーターの降下時刻は実機と未照合。

返答の `arrival` に `split_rows`、`split_extra`、`model_lock_in`、`model_check_in` を含め、観測した降下と照合する。再現は [DEBUGGING.md](DEBUGGING.md)。
